# truesight-seo-backend × seo-loop 架构对比与集成路径 ## 背景与场景 在分析 `~/work/truesight-seo-backend` 的 SEO 增长引擎时，发现它包含两个名字容易混淆的模块——"蜘蛛池"和"泛目录"——它们共用同一套代码生成器但职责完全不同。同一时期存在另一个项目 `~/work/seo-loop`，是自研的闭环 SEO 运营机，两者都涉及 SEO 页面批量生成，自然产生了集成需求。核心问题是：**同一个 growth 引擎里的两种 campaign 是怎么协作的，以及两个定位迥异的项目能不能拼在一起用。** --- ## 核心结论 **1. 蜘蛛池和泛目录没有代码直接耦合，配合靠运营流程** 两者都是 `internal/growth/model.go` 里 `campaign.kind` 的枚举值（`"spider"` / `"directory"`），共用 `BuildGrowthBundle`（`output.go:80`）同一套流水线，产物都是 ZIP（`.html` + sitemap + robots-snippet + manifest + README.txt）。部署、关联、指向哪里完全由人工填写，代码层没有互相引用。 **2. 两者的核心差异在"部署位置"和"每页作用"** | | 泛目录 `directory` | 蜘蛛池 `spider` | |---|---|---| | 部署域名 | 目标站自己的域名（`output.go:116`，`origin = "https://"+hostname`） | 单独的资源站（`PoolOrigin`，`output.go:96`） | | 输入 | 关键词行 + 模板（`{{keyword}}` 等变量替换，`output.go:219-235`） | 链接列表（URL + Anchor + Description） | | 每页作用 | 一个关键词一个落地页，自带正文 | 一个页面只放一条外链，锚文本=关键词（`output.go:274`） | | `rel` 属性 | 不适用 | 可设 `nofollow`/`sponsored`，默认 follow（`output.go:264`） | | 上限 | 每 campaign 1–200 页 | 同左 | **3. truesight 是"油印机"，seo-loop 是"带刹车和仪表盘的车"** truesight 只产静态 ZIP，不负责发布，`Check()`（`service.go:291`）只用 `safeweb` 验证链接存在；seo-loop 有真实 CMS adapter 契约（`publish` / `unpublish` / `setDraft` / `previewHtml`）、GSC/GA4 28/56 天反馈窗口、层次 Beta bandit 自动决策，日硬上限 5 发布 / 1 新建。 **4. 集成的核心障碍：三处哲学冲突** - **规模反向**：truesight 一次可产 200 页；seo-loop 日硬上限 5 页，`MAX_*` 只从 env 读、策略引擎只读。 - **内容合规硬底线**：seo-loop CLAUDE.md 第 19 行锁死"每页独有事实"；truesight `directory` 的 `{{keyword}}` 模板替换在 seo-loop GATE-A 里属于近重复必拒。 - **不可撤回即不可发布**：truesight 人手部署后无 `unpublish`；seo-loop adapter 契约 `E4` 要求 `unpublish`，truesight 产物不满足。 **5. 可行的最小集成：observation 单向打通，不共用发布通道和策略引擎** 把 truesight 部署的 URL 拉进 seo-loop 的 GSC 查询，只写 `observations`，不喂 `outcomes`、不喂 `arms`。两边的自我约束全部保留。 --- ## 实现方案 ### 现有运营配合流程（truesight 内部） **关键点**：`Links[].URL` 和泛目录的 `PathPrefix` 之间**没有代码关联**，蜘蛛池指向哪个 URL 完全靠人填写。 --- ### 推荐集成方案：路径 A 变种（observation 单向打通） **具体步骤：** 1. **seo-loop `publications` 表加 `source_system` 列** 2. **truesight ZIP 部署后导出 URL 清单** 在 `build-manifest.json` 基础上导出一份对账文件： 3. **运营上传 URL 清单到 seo-loop** 4. **seo-loop `9.OBSERVE` 拉 GSC 时带入 truesight URL** 只写 `observations` 表： 5. **面板加只读视图** 在 seo-loop 面板（端口 8810）添加 `GET /satellites` 路由，列出 truesight URL 的 GSC 曝光/点击/索引状态，仅供人工查阅。 --- ## 避坑指南 **1. 不要把 truesight 泛目录 URL 喂进 seo-loop 的 bandit arms** seo-loop 的层次 Beta bandit 假设所有 `arms` 都经过 GATE-A 的独有事实审查。truesight 模板页是高方差低质量样本，混入会污染 bandit 置信区间，让 seo-loop 错误降低自己真正优质内容的发布预算。如果非要学，单独开 `arms(kind='satellite_template')` 完全隔离。 **2. 不要接通 truesight `behavior` 模块的点击/停留计划到 seo-loop runner** truesight `service.go:331` 的 `Plan()` 生成"搜索→停留→内部点击"任务计划，但 `runner/` 未实现。seo-loop CLAUDE.md 自注："自动发布 + GSC 反馈 + bandit 没有业界先例"，`independentlyVerified:false` 是明确留的后路。在此之上叠刷点击行为直接触发 Google "manipulative behavior" 条款，会把 seo-loop 现有安全设计全部废掉。**这条路径禁止走。** **3. truesight 静态页不满足 seo-loop adapter E4 契约，不要试图注册为 CMS site** seo-loop CMS adapter 要求 `unpublish` / `setDraft` / `previewHtml` 三个方法。truesight 产物是 ZIP 文件，人手部署后没有下线机制。强行适配会让 seo-loop 以为自己能下线这些页面，实际上调用 `unpublish` 什么都不会发生，导致数据状态不一致（`publications.live=false` 但页面实际还在线）。 --- ## 底层机制 **truesight 的生成器为何不耦合两个模块** `BuildGrowthBundle`（`output.go:80`）的设计哲学是"后端只产包，不管发布"。两种 `kind` 共用同一套文件命名规则（`prefix/slug/index.html`）和 ZIP 结构，是为了让运维只需要一套部署流程（解压→上传）处理所有类型的 campaign。把"蜘蛛池指向哪些泛目录 URL"的决策放在运营侧而非代码侧，意味着同一套 truesight 实例可以服务多个不相关的业务域，不需要为每个业务定制代码逻辑。这是有意为之的"哑管道 + 人工决策"模式。 **seo-loop 的 bandit 为何只降预算不升** seo-loop 设计文档里明确这是**保守偏置（conservative bias）**：内容质量信号的噪声极高（GSC 数据有 48h 延迟 + 季节性），用 bandit 自动加注意味着在噪声里放大错误。只降（惩罚明确差的）不升（不奖励不确定的好），等于在探索空间上手工加了一个非对称约束。这让系统在统计意义上更慢，但在操作意义上更安全——人工发现某个方向真的有效后，运营直接调高 `MAX_DAILY_BUDGET` 给策略引擎升天花板，而不是让 bandit 自己发现并扩大这个方向。
