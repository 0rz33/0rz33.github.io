Cloudflare Tunnel 实现 MMS 支付系统双机热备

2026-11-19
# Cloudflare Tunnel 替代 DNS 切换实现 MMS 支付系统双机热备 ## 背景与场景 MMS 支付系统单点部署在 `139.162.39.128`，新增 site4（`172.104.51.20`）作备机，需要对支付 API、收银台、管理后台、演示站四个生产域名实现自动故障切换。传统做法是改 DNS A 记录或双 A round-robin，但两种方案都有硬伤：TTL 等待（最快 60s）、故障时客户端仍有概率命中故障节点、真实 IP 对外暴露。本文记录用 Cloudflare Tunnel 替代传统 DNS 切换的完整实施路径，实现毫秒级故障转移且服务器不暴露公网 IP。 --- ## 核心结论 1. **同一 Tunnel Token 可在多台服务器同时运行**：两台服务器都跑同一个 Token 的 cloudflared，Cloudflare 视为同一 Tunnel 的两个 connector，自动做健康检测和故障转移，这是实现双机热备的关键机制。 2. **DNS 切换由 Cloudflare 控制面完成，不依赖 TTL**：域名绑定 Tunnel 后，DNS 记录变成 CNAME 指向 `.cfargotunnel.com`，故障时 Cloudflare 毫秒级感知 connector 断开，立即停止路由，客户端无感知。 3. **服务器零入站端口**：cloudflared 主动向 Cloudflare 边缘建立出站长连接（QUIC/HTTP2），服务器不开任何入站端口，真实 IP 完全不可见。 4. **迁移分四阶段，生产 DNS 变更是最后一步**：建 Tunnel → 两台接入 → 测试域名验证 → 验收后统一切换 Public Hostname，全程不影响生产流量。 5. **Docker 部署加 `--network=host` 才能访问宿主机端口**：cloudflared 容器内的 `localhost` 是容器自身网络，服务跑在宿主机时必须加 `--network=host` 或改用宿主机网关 IP `172.17.0.1`。 --- ## 实现方案 ### 阶段一：Cloudflare 控制台创建 Tunnel（运维操作） 1. 登录 `dash.cloudflare.com` → 选 `a3owc.com` 账号 2. **Zero Trust** → **Networks** → **Tunnels** → **Create a tunnel** - Connector 类型：**Cloudflared** - Tunnel 名称：`mms-ha` 3. 安装方式选 **Docker**，页面生成命令含 Tunnel Token： **将 Token 通过密码管理工具私下交给开发，不要在公开频道传输。** --- ### 阶段二：两台服务器接入同一 Tunnel（开发操作） 在 `139.162.39.128` 和 `172.104.51.20` **各执行同一条命令**： 两台服务器跑同一 Token → 同一 Tunnel → Cloudflare 自动轮询两个 connector，任意一台下线流量自动切到另一台。 --- ### 阶段三：测试域名验证（不动生产 DNS） 在 Tunnel 的 **Public Hostname** 标签页添加临时测试域名： 验证两台服务器均能通过该测试域名正常响应后，进入下一阶段。 --- ### 阶段四：验收通过后统一切换四个生产域名（运维操作） 在 Tunnel **Public Hostname** 标签页添加四条记录： | Domain | Service | |--------|---------| | `mms-api.a3owc.com` | `http://localhost:支付API端口` | | `guodong.a3owc.com` | `http://localhost:收银台端口` | | `zqadmin.a3owc.com` | `http://localhost:管理后台端口` | | `zqpay.a3owc.com` | `http://localhost:演示站端口` | Cloudflare 自动将 DNS 改为： 原 A 记录（`139.162.39.128`）由 Cloudflare 自动替换，无需手动删除。 --- ## 避坑指南 **1. 不要在验收前改生产 DNS，也不要同时挂两个 A 记录** 双 A round-robin 不等于热备。DNS 层面没有健康检查，故障时客户端仍有概率（取决于本地 TTL 缓存）命中故障节点，且切换最快也要等 TTL 过期（60s 起）。Cloudflare Tunnel 的切换在控制面主动探测，与 TTL 完全无关。 **2. Token 泄露即失控，必须走私密渠道传递** Token 是这个 Tunnel 的唯一凭证，泄露后任何人都能接入该 Tunnel 并暴露服务。泄露后立即在 Cloudflare 控制台 **Rotate Token**（旧 Token 立即失效，需在两台服务器重新部署新 Token）。不能出现在 Slack 公开频道、Git 仓库、工单系统。 **3. 忘加 `--network=host` 导致服务 502** cloudflared 容器内 `localhost` 是容器自身的回环地址，不是宿主机的。应用跑在宿主机时，`http://localhost:8080` 在容器内打不到任何东西，表现为 Tunnel 建连成功但访问域名返回 502。 - **解法 A**（推荐）：加 `--network=host`，容器共享宿主机网络命名空间 - **解法 B**：Service 改为 `http://172.17.0.1:8080`（Docker bridge 网关 IP，实际以 `ip route` 输出为准） --- ## 底层机制 Cloudflare Tunnel 的核心是**反向代理建连**：cloudflared 进程启动后主动向 Cloudflare 边缘节点建立若干条持久化 QUIC/HTTP2 长连接（默认 4 条）。外部请求到达 Cloudflare 边缘时，通过这些已建立的连接将流量推送到 cloudflared，再由 cloudflared 转发给本地服务——整个方向是从外到内通过已建好的出站连接传输，服务器从不监听公网端口。 当同一 Tunnel 存在多个 connector 时，Cloudflare 控制面持续检测每个 connector 的长连接健康状态。某台服务器宕机或网络断开时，对应的所有长连接在秒级内断开，Cloudflare 立即将新请求只路由到存活的 connector。整个切换过程完全在 Cloudflare 内部完成，不涉及任何 DNS 变更，客户端侧无感知。这是 Tunnel 切换速度（毫秒级）相较传统 DNS 切换（TTL 至少 60s）存在数量级差异的根本原因。
