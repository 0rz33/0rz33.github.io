Cloudflare Tunnel 双机热备 操作步骤

2026-11-19
KB 里已有这条记录（score=0.74，今天刚存），内容和对话原文一致，无需重复存。直接输出蒸馏文档： --- # Cloudflare Tunnel 替代 DNS 切换实现双机热备：MMS 支付系统 HA 迁移实践 ## 背景与场景 MMS 支付系统部署在单台服务器（`139.162.39.128`），新增 site4（`172.104.51.20`）作为备机，需要实现双机自动故障切换。涉及四个生产域名：支付 API（`mms-api.a3owc.com`）、收银台（`guodong.a3owc.com`）、管理后台（`zqadmin.a3owc.com`）、演示站（`zqpay.a3owc.com`）。传统方案是改 DNS A 记录指向备机 IP，但 TTL 等待 + 真实 IP 暴露 + 手动切换是三个硬伤。本文记录用 Cloudflare Tunnel 替代传统 DNS 切换的完整实施路径。 --- ## 核心结论 1. **同一个 Tunnel Token 可以同时在多台服务器运行**，Cloudflare 自动对多个 connector 做负载均衡和故障转移，这是实现双机热备的关键机制。 2. **DNS 不需要手动切换**：域名绑定到 Tunnel 后，DNS 记录变成 CNAME 指向 `.cfargotunnel.com`，故障切换由 Cloudflare 控制面完成，TTL 等待问题消失。 3. **服务器不需要开放任何入站端口**：cloudflared 进程主动向 Cloudflare 建立出站连接，真实 IP 对公网不可见，消除了传统 HA 方案的 IP 暴露风险。 4. **迁移分两阶段，DNS 变更是最后一步**：先建 Tunnel → 两台服务器接入 → 测试域名验证 → 验收通过后统一切换 Public Hostname，全程生产流量不受影响。 5. **Docker 部署是最简安装方式**：一行 `docker run --restart=always` 命令，含自动重启，无需管理 systemd service 或 binary 路径。 --- ## 实现方案 ### 阶段一：在 Cloudflare 控制台创建 Tunnel（运维/非开发操作） 1. 登录 `dash.cloudflare.com` → 选择 `a3owc.com` 账号 2. 左侧菜单：**Zero Trust** → **Networks** → **Tunnels** 3. 点击 **Create a tunnel** - Connector 类型选 **Cloudflared** - Tunnel 名称填 `mms-ha` 4. 安装方式选 **Docker**，页面生成的命令中含 Tunnel Token： **将这个 Token 私下交给开发，不要在公开频道传输。** --- ### 阶段二：两台服务器接入同一 Tunnel（开发操作） 在 **现有服务器**（`139.162.39.128`）和 **site4**（`172.104.51.20`）各执行： 关键点： - `--restart=always`：服务器重启后容器自动拉起 - 两台服务器跑同一个 Token → 同一个 Tunnel → Cloudflare 视为两个 connector - Cloudflare 会自动轮询两个 connector，任意一台下线，流量自动切到另一台 --- ### 阶段三：用测试域名验证（开发操作，不动生产 DNS） 在 Cloudflare Tunnel 的 **Public Hostname** 标签页，先添加一个临时测试域名（如 `mms-test.a3owc.com`），指向某台服务器的本地端口： 验证两台服务器均能通过该测试域名正常响应后，进入下一阶段。 --- ### 阶段四：验收通过后统一切换四个生产域名（运维操作） 在 Tunnel 的 **Public Hostname** 标签页，添加四条记录（端口号由开发提供）： | Domain | Service | |--------|---------| | `mms-api.a3owc.com` | `http://localhost:支付API端口` | | `guodong.a3owc.com` | `http://localhost:收银台端口` | | `zqadmin.a3owc.com` | `http://localhost:管理后台端口` | | `zqpay.a3owc.com` | `http://localhost:演示站端口` | Cloudflare 会自动将上述域名的 DNS 记录改为： **原 A 记录（`139.162.39.128`）由 Cloudflare 自动替换，无需手动删除。** --- ## 避坑指南 **1. 不要在验收前修改生产 DNS，也不要同时添加两个 A 记录** 传统 round-robin 双 A 记录不等于热备。DNS 层面的多 A 记录在某台服务器故障时，客户端仍会有概率命中故障节点（取决于客户端 TTL 缓存），且没有健康检查。Cloudflare Tunnel 的故障切换是控制面主动探测，不依赖客户端 TTL。 **2. Token 是隧道唯一凭证，泄露即失控** Token 相当于这个 Tunnel 的 root 权限，任何人拿到 Token 都能接入该 Tunnel 并暴露服务。应通过私信或密码管理工具传递，不要出现在 Slack 公开频道、git 仓库、工单系统。泄露后立刻在 Cloudflare 控制台 Rotate Token。 **3. `localhost` 指的是容器内的 localhost，不是宿主机** cloudflared 在 Docker 容器内运行时，`http://localhost:8080` 指向**容器内部**的端口，不是宿主机。如果应用跑在宿主机，需要用宿主机网关 IP（通常是 `172.17.0.1`）或使用 `--network=host` 模式： 加了 `--network=host` 后，`http://localhost:8080` 才等同于宿主机的 8080 端口。 --- ## 底层机制 Cloudflare Tunnel（原 Argo Tunnel）的核心是**反向代理建连**：cloudflared 进程启动后，主动向 Cloudflare 的边缘节点建立若干条持久化 QUIC/HTTP2 长连接（默认 4 条）。Cloudflare 收到外部请求后，通过这些已建立的连接将流量推送到 cloudflared，再由 cloudflared 转发给本地服务。 当同一个 Tunnel 有多个 connector（即多台服务器都跑了同 Token 的 cloudflared）时，Cloudflare 控制面持续检测每个 connector 的连接健康状态。某台服务器断开时，Cloudflare 在毫秒级内检测到连接中断，自动将新请求只路由到存活的 connector，整个切换过程不经过 DNS，客户端无感知。这是它相较传统 DNS 切换在切换速度上存在数量级差异的根本原因（DNS TTL 最快也是 60 秒，Tunnel 切换是毫秒级）。
