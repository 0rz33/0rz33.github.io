已蒸馏完成，KB 已存入（`d9eaf213`）。 --- # 网关视觉透传：OpenAI Vision API 兼容层的两阶段路由实现 ## 背景与场景 shanggu 作为统一 LLM 网关，对外暴露 OpenAI 兼容接口。在此之前，客户端发来带图的 `content` 数组消息（标准 OpenAI vision 格式）时，网关无法解析图片字段，视觉能力形同虚设。业务上 Gemini / Sonnet 两个主力模型都支持视觉，网关却是瓶颈——需要一次性打通消息解析、图聚合、provider 路由三段，同时保证纯文本路径零行为变更。 --- ## 核心结论 1. **OpenAI vision content 数组必须在消息层反序列化，不能在路由层猜**：`content` 可能是 `string`（纯文本）或 `[]ContentPart`（含图），用自定义 `UnmarshalJSON` 在 `chat.Message` 层做分叉，快车道/慢车道各自处理，上层不感知。 2. **图聚合必须幂等**：`Normalize` 阶段将所有消息的 `Images` 聚合进 `req.Images`（复用已有 vision 通道）时，要防止中间件多次调用导致图片二次累加。 3. **provider 路由分两阶（Path 1 → Path 2 fallback）**：Path 1 尝试 OpenAI 兼容网关（GPTProto）的原生 `image_url` 透传；Path 2 是 provider 级联（Anthropic image block / 本地），把原始问题 + 图直接投给 vision 模型。两阶独立，本机无 GPTProto 时不 bail，直接走 Path 2。 4. **`ModelSupportsVision` 注册表加族前缀回落**：精确 model ID 未命中时，按 `gemini-*` / `sonnet` / `opus` 前缀判断，避免动态别名（如 `gemini-flash-latest`）漏判。 5. **vision 调用不能带 agent/SKU prompt**：把完整 ~7KB 系统提示词喂给 vision 调用，模型会进入 agent 模式，返回空响应或「没收到图」。vision 路径只给最小引导语（「看图直答」），问题 + 图本身就是完整输入。 --- ## 实现方案 ### 1. 消息反序列化 — `internal/service/chat/model.go` ### 2. 图聚合 — `internal/service/chat/messages.go` ### 3. 两阶 vision 路由 — `internal/adapter/zhukesi/chat_vision_native.go` ### 4. 能力注册表族前缀回落 — `internal/shared/capabilities.go` ### 5. Body 上限 — `internal/adapter/zhukesi/chat.go` ### 6. 验证探针 实测结果（`f56304ad` 部署，mac-mini `:8010`）： - `shanggu-gemini` → ✅ 「共 4 条：红、绿、蓝、黄」 - `shanggu-sonnet` → ✅ 同上 - `shanggu-gemini` 纯文本 `1+1=?` → ✅ `2`（纯文本路径不受影响） --- ## 避坑指南 **1. vision 路径绝对不能注入 agent/SKU 系统提示词** 表现：模型收到 `~7KB` agent prompt 后进入 agent 模式，把图当作「不存在的附件」，返回「我没有收到图片」或空流。修法：vision 调用的 `system` 只放最小引导语，user 消息只含原始问题 + 图，不带任何工具描述 / SKU 路由上下文。 **2. Path 1 不可用时不能静默成功** 原始实现 `getGPTProtoGateway() == nil` 时 `return nil`，函数签名的 `nil` 在调用方被判为成功，图片无声丢弃，客户端收到空流。区分三种状态：`gw == nil`（跳过）、`err != nil`（降级）、`err == nil`（真正成功），任何一种都不能混淆。 **3. 功能分支合 PR 后必须手动切回 main** `./ai.sh deploy` 执行 `git pull`，分支感知由当前 HEAD 决定。若 mini 停在 `claude/vision-passthrough-4764ad`，后续所有合进 main 的变更对该机器不可见。合 PR 后立即执行： --- ## 底层机制 **OpenAI vision content 的两种形态与解析责任归属** OpenAI Chat Completions API 规范允许 `messages[].content` 是 `string` 或 `ContentPart[]`，大多数代理网关只处理字符串形态。shanggu 在 `chat.Message` 层（`UnmarshalJSON`）完成分叉，纯文本快车道不改任何字段，数组慢车道提取文本段合并进 `Content`、图段收入 `Images`。上层路由、缓存、日志全部不感知格式差异。图聚合（`Normalize`）复用已有 `req.Images` vision 通道，无需修改路由核心。 **两阶 fallback 的设计取舍** Path 1（GPTProto 原生透传）model 路由精确，用户钉定的 model 就是实际跑的 model；代价是对网关可用性强依赖，网关挂则整个 vision 断。Path 2（provider 级联）model 精确性退化——`shanggu-gemini` 的图在无 GPTProto 的部署上实际由 Anthropic Sonnet 执行——换来的是任何有 vision 能力的 provider 都能兜底。日志明确标记走的是哪条路径（`👁️ 原生 vision 成功 (provider 级联直接看图答)`），运维排查时可立即区分真实 provider 与路由 model 名的差异。
