Docker Compose Named Volume 迁移 Bind Mount 全流程

2026-11-14 运维
**原问题**: Docker Compose 项目如何从 named volume 迁移到 bind mount，保留 PostgreSQL 数据和产出文件 **答案**: # Docker Compose 从 Named Volume 迁移到 Bind Mount：数据持久化改造 ## 背景与场景 seo-loop 是一套 SEO 自动化流水线（Vue SPA + Node daemon + PostgreSQL + Redis），部署在一台 worker 机器上。原始部署不是通过 `git clone` 拉取的（目录中没有 `.git`），且数据存储使用的是 Docker named volume。这导致两个问题：一是代码更新无法 `git pull`，只能手动覆盖文件；二是数据和项目目录解耦，整目录迁移或备份时 named volume 里的 PostgreSQL 数据和产出文件会被遗漏。本次改造的目标是将 named volume 替换为 bind mount（`./data/`），使数据跟着项目目录走。 ## 核心结论 1. **先导出数据再拆容器**：`docker compose exec -T postgres pg_dump` 导出 SQL，`docker cp` 拷出 daemon 产出文件，然后才能安全 `docker compose down` 删除旧 named volume。 2. **`docker compose ps -q` 在容器停止后返回空**：`docker cp $(docker compose ps -q daemon):/app/out/. data/seo-out/` 会报 `must specify at least one container source`，因为 `-q` 只返回运行中容器的 ID。必须用硬编码容器名 `docker cp seo-loop-daemon-1:/app/out/. ...`。 3. **Bind mount 路径统一到 `./data/` 子目录**：PostgreSQL → `./data/postgres`，daemon 产出 → `./data/seo-out`。整个 `data/` 目录可以 tar 打包迁移，不再依赖 `docker volume`。 4. **非 git 仓库的部署环境用 `cat > file <<'EOF'` 覆盖配置**：没有 `.git` 就没法 `git pull`，直接 heredoc 写入 `docker-compose.yaml` 是最快的更新方式。 5. **数据恢复顺序：先起 postgres，等 healthy，再灌 dump，最后起全栈**。不能 `up -d` 一把梭——daemon 启动时会连 DB，如果数据还没灌完会导致 schema 不匹配。 ## 实现方案 ### 1. 停服并导出数据 ### 2. 覆盖 docker-compose.yaml 将 named volume 替换为 bind mount，关键改动： - `postgres` 的 volume: `./data/postgres:/var/lib/postgresql/data` - `app` 和 `daemon` 共享: `./data/seo-out:/app/out` - 底部删除 `volumes:` 声明段 ### 3. 恢复数据并启动 ## 避坑指南 1. **`docker compose ps -q ` 在容器未运行时返回空字符串** — 用 `-a` 或硬编码容器名 2. **`pg_dump` 导出时不要先 `docker compose down`** — 导出需要 postgres 在运行 3. **Bind mount 目录权限** — PG 容器以 uid 999 运行，手动 mkdir 并设 root-only 权限会导致启动失败 4. **非 git 仓库长期维护** — heredoc 覆盖是应急，长期应 `git init && git remote add && git reset --hard origin/main` ## 底层机制 Named volume 由 Docker 引擎管理，数据在 `/var/lib/docker/volumes//_data`，生命周期独立于 compose 项目。Bind mount 将宿主机目录直接映射进容器，数据是普通文件。对于单机部署小型项目，bind mount 到 `./data/` 几乎总是更好——数据可见、可 git-ignore、可整目录迁移，符合"项目即目录"的运维心智模型。
