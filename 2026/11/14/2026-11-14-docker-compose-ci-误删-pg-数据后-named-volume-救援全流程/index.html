Docker Compose CI 误删 PG 数据后 Named Volume 救援全流程

2026-11-14 运维
**原问题**: Docker Compose CI 部署把 PostgreSQL 数据清空了怎么恢复？named volume 救援步骤？pg_dumpall 从孤立 volume 提取数据？ **答案**: # Docker Compose CI 误删 PostgreSQL 数据后的 Named Volume 救援 ## 背景与场景 `seo-loop` 项目使用 Docker Compose 部署，PostgreSQL 数据通过 bind mount (`./data/postgres`) 挂载到宿主机。多次 `git push dev` 触发 CI 时，CI 流程未排除 `./data/` 目录，导致 `docker compose down -v` + 重建过程中 `./data/postgres` 被反复清空。用户在面板中配置的站点接口（API Token、GSC 服务账号、站点 URL）全部丢失，回到初始状态。 项目此前曾使用 Docker named volume (`seo-loop_pg-data`)，该 volume 残留在 Docker Engine 中未被显式删除，成为唯一的数据恢复来源。 ## 核心结论 1. **Docker named volume 在 `docker compose down` 不加 `-v` 时不会被删除**。即使 compose 文件已改为 bind mount，旧 named volume 仍保留在 `/var/lib/docker/volumes/`，是灾难恢复的最后防线。 2. **CI 流程必须显式排除数据目录**。`.dockerignore` 和 CI 脚本需要 `exclude ./data/`，否则每次部署都可能覆盖有状态数据。 3. **从孤立 named volume 提取数据无需启动原服务**。用一次性 `docker run --rm` 挂载该 volume，在容器内启动临时 PG 实例执行 `pg_dumpall`，完全不影响正在运行的服务。 4. **用 `pg_dumpall` 而非 `pg_dump`**。需要恢复所有数据库 + 角色，`pg_dumpall` 是正确选择；`pg_dump` 只导单库，丢角色定义。 5. **恢复后必须做数据完整性校验**。至少验证：用户表行数（`panel_users`）、关键配置（`project_context` 中的 `site_api_config`）。 ## 实现方案 ### Step 1：确认 named volume 存活 ### Step 2：从 named volume dump 全库 关键参数： - `listen_addresses=`（空串）：不对外监听，避免端口冲突 - `-w`：等待 PG 完全启动/停止 - `--rm`：容器自动销毁 ### Step 3：清空当前库并导入 ### Step 4：数据完整性校验 ## 避坑指南 1. **`docker compose down -v` 会删除 named volume** — 生产/dev 永远不用 `-v` 2. **bind mount 在项目目录内 = 隐蔽数据丢失点** — `git clean -fdx`、CI rsync --delete 都会清空；最佳实践是 PG 数据放项目树之外或用 named volume 3. **`pg_dumpall -U` 必须是 superuser** — 非 superuser 静默跳过无权限对象，dump 不完整 ## 底层机制 Docker named volume 生命周期独立于容器和 compose 项目，存储在 `/var/lib/docker/volumes//_data/`，只有 `docker volume rm` 或 `docker compose down -v` 才删除。`pg_ctl start -o "-c listen_addresses="` 启动隔离模式 PG：不监听 TCP，只接受 Unix socket，不与宿主机 PG 冲突。
