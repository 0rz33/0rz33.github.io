# P99 延迟飙升诊断：CPU/内存/QPS 均正常时的系统化根因推演 ## 背景与场景 线上服务 P99 延迟从 50ms 突然飙到 2s，但监控大盘上 CPU、内存、QPS 三项核心指标全部正常。这是一个极具迷惑性的场景——传统的"扩容/重启"本能反应在这里往往无效。核心线索恰恰藏在"三项正常"本身：**不是整体过载，是少数请求被卡住了**。这类问题在微服务架构、数据库密集型后端和 Go/JVM 服务中高频出现，定位不当容易浪费数小时。 --- ## 核心结论 **结论 1：P99 恶化而 P50 正常，锁竞争是第一嫌疑** 锁（DB 行锁、Go `sync.Mutex`、Redis 单线程脚本）的特征就是"少数持锁请求影响大量排队请求"。QPS 越高，尾部排队越长，P99 越烂。先查 `information_schema.innodb_lock_waits`（MySQL）或 `pg_locks`（PG），以及 Go 的 `db.Stats().WaitCount/WaitDuration`。 **结论 2：P99 值恰好等于某个超时配置，大概率是外部依赖问题** P99 ≈ 1s 或 P99 ≈ 2s 且呈"阶梯分布"（不是随机散点），说明是某个 timeout 配置在兜底。常见来源：下游服务偶发慢响应、容器内 DNS `ndots=5` 导致每次域名解析多跑 5 次无效查询。先看 `cat /etc/resolv.conf`，再用 `tcpdump -i any port 53` 抓 DNS 包确认。 **结论 3：GC 暂停在 CPU 指标上是隐形的** Go GC 和 JVM GC 的 Stop-the-World 阶段不计入请求线程的 CPU 时间，但会冻结所有 goroutine/线程。用 `GODEBUG=gctrace=1` 输出 GC 日志，对比 wall time 列与 P99 spike 的时间点是否吻合。Go GC 暂停 >50ms 即需关注。 **结论 4：重启短暂恢复后再度劣化，定性为资源泄漏** goroutine 泄漏或 FD 泄漏的特征是单调增长然后耗尽。访问 `/debug/pprof/goroutine?debug=2`，大量处于 `semacquire` 或 `chan receive` 状态的 goroutine 堆积 = 泄漏确认。goroutine 总数趋势图单调增长也是铁证。 **结论 5：Tracing 瀑布图是最快定位工具，30 秒内缩圈** 在 Jaeger/Tempo 里直接捞 P99 请求的 span 瀑布图。如果某个 span 有大段"空白"（span 存在但没有子 span 覆盖），说明是在等连接池或等锁，而不是真正在执行。这一步通常 30 秒内能把根因从六类缩到两类。 --- ## 实现方案 ### Step 1：用 Tracing 快速缩圈（首选） ### Step 2：DB 锁等待排查 ### Step 3：GC 暂停排查 ### Step 4：Goroutine 泄漏排查 ### Step 5：DNS 超时排查（容器内高发） ### Step 6：网络层排查 --- ## 避坑指南 **坑 1：不要在 P99 spike 时才开始收集数据** pprof block profile 和 goroutine dump 要在问题发生期间采集，之后 goroutine 可能已经退出、锁已经释放，dump 出来是正常状态。正确做法：在 service 里提前埋好 `/debug/pprof` 端点，问题复现时立刻采集，或者配置持续 profiling（如 Pyroscope）。 **坑 2：Go pprof block profile 默认关闭，不提前开启则无法采集** **坑 3：P99 恰好等于超时配置值时，不要只看"下游服务是否挂了"** 下游没挂不代表没超时。超时可能是偶发的（1% 请求慢了 1.9s，刚好没超 2s 超时，但 P99 就是这 1%）。正确的排查是：在 Tracing 里把下游调用的 latency 分位数单独拉出来看，不要只看 P50。DNS 超时尤其容易被忽视，因为它不出现在应用层 Tracing 里（DNS 在 `net.Dial` 里面，Go 标准库默认没有 span）。 --- ## 底层机制 **为什么 CPU/内存/QPS 正常，P99 还能烂？** P99 衡量的是"最慢的 1% 请求"，CPU/内存/QPS 衡量的是"整体均值/总量"。锁竞争的本质是串行化：持锁的请求在 CPU 上正常执行，等锁的请求在内核 futex 上休眠（不占 CPU），但它的 wall time 在增长。99 个请求中有 1 个等了 1.95s，整体 QPS 和 CPU 丝毫不受影响，但 P99 就被这 1 个拉到 1.95s。这就是为什么"三项正常"不代表服务健康，P99/P999 才是用户体验的真实镜像。 GC 暂停的机制类似：Go 的三色标记 GC 大部分工作与应用并发执行，CPU 利用率看起来只是略微升高。但 mark termination 阶段必须 STW（全部 goroutine 暂停），这个暂停时间不会体现在请求线程的 CPU 时间里，却直接叠加到所有正在处理中的请求的 latency 上。一次 200ms 的 STW = 当时所有在途请求各自增加 200ms 延迟，全部打进 P99。
