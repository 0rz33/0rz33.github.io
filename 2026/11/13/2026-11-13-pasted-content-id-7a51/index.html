# Docker Compose CI 误删 PostgreSQL 数据后的 Named Volume 救援 ## 背景与场景 `seo-loop` 项目使用 Docker Compose 部署，PostgreSQL 数据通过 bind mount (`./data/postgres`) 挂载到宿主机。在多次 `git push dev` 触发 CI 部署的过程中，CI 流程未排除 `./data/` 目录，导致每次部署执行 `docker compose down -v` + 重新拉取时，宿主机上的 `./data/postgres` 被反复清空（wipe）。用户配置好的站点接口（API Token、GSC 服务账号、站点 URL 等）全部丢失，面板回到初始状态。 项目此前曾从 bind mount 迁移到 Docker named volume (`seo-loop_pg-data`)，该 volume 残留在 Docker Engine 中未被显式删除，成为唯一的数据恢复来源。 ## 核心结论 1. **Docker named volume 在 `docker compose down` 不加 `-v` 时不会被删除**。即使 compose 文件已改为 bind mount，旧的 named volume 仍保留在 Docker Engine 中（`/var/lib/docker/volumes/`），是灾难恢复的最后一道防线。 2. **CI 流程必须显式排除数据目录**。`.dockerignore` 和 CI 脚本中需要 `exclude ./data/`，否则每次部署都可能覆盖或清空有状态数据。修复提交：`1ed6052`。 3. **从孤立 named volume 中提取数据无需启动原服务**。可以用一次性 `docker run --rm` 挂载该 volume，在容器内启动临时 PostgreSQL 实例执行 `pg_dumpall`，完全不影响正在运行的服务。 4. **`pg_dumpall` 而非 `pg_dump`**。因为需要恢复所有数据库 + 角色（`seo_loop` 用户本身也在 dump 中），`pg_dumpall` 是正确选择；`pg_dump` 只导单库，会丢角色定义。 5. **恢复后必须做数据完整性校验**。至少验证：用户表行数（`panel_users`）、关键配置（`project_context` 中的 `site_api_config`）是否包含预期的站点 URL。 ## 实现方案 ### 前置条件 - SSH 到部署 server - 确认 Docker Engine 中旧 named volume 是否存在 ### Step 1：确认 named volume 存活 如果 `inspect` 返回空 / 报错，说明 volume 已被删除，需要转入 bind mount 残留扫描（见避坑指南）。 ### Step 2：从 named volume dump 全库 **核心行解读**： - `listen_addresses=`（空）：临时 PG 不对外监听，避免端口冲突 - `-w`：等待 PG 完全启动/停止后再执行下一步，防止 dump 时 PG 未就绪 - `-s`：静默模式，减少日志噪音 ### Step 3：清空当前库并导入 ### Step 4：数据完整性校验 校验通过后刷新面板即可看到恢复的站点配置。 ## 避坑指南 ### 1. `docker compose down -v` 会删除 named volume 这是最常见的数据丢失根因。`-v` flag 的语义是 "remove named volumes declared in the volumes section"。CI 脚本中如果写了 `down -v` 做 clean deploy，**每次都会清空数据库**。正确做法： - 生产/dev 环境永远不用 `-v` - 需要 clean 时只删除无状态容器：`docker compose down`（不带 `-v`） - 在 CI 中用 `.dockerignore` 或 rsync `--exclude` 保护 `./data/` ### 2. bind mount 被 git/CI 覆盖的隐蔽风险 bind mount 路径（如 `./data/postgres`）位于项目目录内时，以下操作都会清空它： - `git clean -fdx`（清除未跟踪文件） - CI 做 `rm -rf` 或 `rsync --delete` 同步代码 - Docker Desktop 的 file sharing 在 macOS 上可能有缓存延迟 **最佳实践**：PG 数据目录放到项目树之外（如 `/var/lib/seo-loop/pgdata`），或始终使用 named volume。 ### 3. `pg_dumpall` 的 `-U` 必须是 superuser `pg_dumpall` 需要读取所有数据库和全局对象（roles、tablespaces）。如果 `-U` 指定的用户不是 superuser，会静默跳过无权限的对象，导致 dump 不完整。在容器内的默认 PG 中，`seo_loop` 通常是创建数据库时的 owner（即 superuser），但如果不是，需要用 `postgres` 用户。 ## 底层机制 Docker named volume 的生命周期独立于容器和 compose 项目。创建后存储在 `/var/lib/docker/volumes//_data/`，只有显式 `docker volume rm` 或 `docker compose down -v` 才会删除。即使 `docker-compose.yml` 中不再引用该 volume，它依然存在于 Docker Engine 中——这是本次救援成立的前提。 `pg_ctl start -o "-c listen_addresses="` 启动的是一个"隔离模式"的 PostgreSQL 实例：不监听任何 TCP 端口，只接受 Unix domain socket 连接。这意味着它不会与宿主机上正在运行的另一个 PG 实例产生端口冲突（都监听 5432 的问题），也不会被外部访问到。`pg_dumpall` 通过同一容器内的 Unix socket 连接这个临时实例，完成 dump 后 `pg_ctl stop` 干净退出，容器随 `--rm` 自动销毁，不留痕迹。
