SEO证书自动化方案探讨

2026-11-21 SEO
# OpenResty + Certbot 多域名 SSL 自动化：三条路的选型与实现 ## 背景与场景 在 SEO 卫星站场景下，业务要求频繁上线新域名（每批少则数个、多则数十个），每次都需要手动三步操作：改 nginx vhost 配置 → 执行 `certbot --nginx -d xxx` → `nginx -s reload`。随着站点规模增长，手工操作变成瓶颈，需要一套自动发证 + 自动配置的机制。当前环境：OpenResty 跑 443 端口按 `server_name` 分流，certbot 已在 VPS 上，`seo.a3owc.com` 和 `hub.daslgwni.top` 均已用 certbot 签发证书。 ## 核心结论 1. **不改架构的最小方案（方案 A）**：后端暴露 `GET /api/satellites/manifest` 返回所有启用域名列表，VPS 上跑 `sync-satellites.sh` 轮询该接口、自动生成 vhost + 签证书 + reload。权限干净，容器不碰 nginx。 2. **方案 A 的关键顺序约束**：ACME HTTP-01 挑战必须先有 nginx vhost 把 `/.well-known/acme-challenge/` 路由对，才能让 Let's Encrypt 回调验证。脚本必须**先写 vhost、再调 certbot**，顺序不可反。 3. **Caddy on-demand TLS（方案 B）** 是长期最优：一行 `on_demand_tls { ask ... }` 配置，新域名 DNS 指向服务器后自动签发、零手动干预。代价是引入新组件，需设计 `openresty → caddy → upstream` 的双 proxy 链路。 4. **DNS-01 + Cloudflare API（方案 C）** 彻底与 nginx 解耦：`certbot --dns-cloudflare` 插件不依赖 vhost 存在，支持通配符 `*.yourdomain.com`，但要求所有域名托管到 Cloudflare 且服务器持有 CF API token（权限收敛到 `Zone:DNS:Edit`）。 5. **DNS A 记录是所有方案的前提**：域名注册商控制台的 A 记录指向，无论哪条路都无法绕过，除非所有域名全托管到 CF 并给后端 API token。 ## 实现方案 ### 方案 A：后端清单 + 服务器端脚本（推荐起步） **Step 1：后端加 manifest 接口** **Step 2：编写 `scripts/sync-satellites.sh`** **Step 3：加 cron** --- ### 方案 B：Caddy on-demand TLS（长期方案） 在 `Caddyfile` 中加： 后端实现 `/api/satellites/check`：域名在启用列表里返回 `200`，否则 `403`，Caddy 只对 `200` 的域名自动签发。 OpenResty 侧将卫星域名流量 proxy 到 Caddy（以免改动 admin panel 的现有配置）： --- ### 方案 C：DNS-01 + Cloudflare ## 避坑指南 **1. HTTP-01 挑战顺序陷阱（方案 A 最常踩）** 错误做法：直接调 `certbot --nginx -d xxx` 而没有先写好 vhost。 表现：`certbot` 返回 `Connection refused` 或 `404`，Let's Encrypt 无法访问 `/.well-known/acme-challenge/`，签发失败。 正确顺序：**写 vhost → `nginx -s reload` → certbot**，三步缺一不可。 **2. certbot `--expand` vs 单独签发** `--expand` 会把新域名追加到已有证书的 SAN 列表里，导致证书越来越大、续签时所有域名必须同时在线可达。卫星站场景下建议**每个域名单独签发独立证书**，避免一个域名 DNS 失效拖垮全部续签。 **3. Caddy on-demand TLS 必须有 `ask` 鉴权** 不加 `ask` 直接开 on-demand，任何 SNI 请求都会触发自动签发，会瞬间打爆 Let's Encrypt 频率限制（同 IP 每小时 5 个失败请求限制，每注册域名每周 50 张证书）。`ask` 接口必须严格白名单，不能返回 `200` 给未知域名。 ## 底层机制 **ACME HTTP-01 挑战的工作流**：客户端（certbot）向 Let's Encrypt CA 请求签发 → CA 下发一个 token → 客户端把 `token:thumbprint` 写到服务器的 `/.well-known/acme-challenge/` 路径 → CA 通过 HTTP 访问该 URL 验证控制权 → 签发证书。这意味着 **nginx 必须在挑战期间能响应该路径**，所以 vhost 必须先于 certbot 存在，reload 也不可省略（nginx worker 重载前新 `server_name` 不生效）。 **Caddy on-demand TLS 的 TLS 握手拦截机制**：Caddy 在 TLS ClientHello 阶段拦截 SNI，调用 `ask` 接口确认该域名是否被授权，通过后异步触发 ACME 流程并缓存证书。首次握手会有 2-5 秒延迟（等证书签发），此后命中缓存毫秒级响应。这与 HTTP-01 的"先有 vhost"约束完全不同——Caddy 在 TCP 层就介入，不依赖任何预配置路由。
