# 多域名卫星站群：OpenResty 反代分流 + Certbot 自动签证的完整方案 ## 背景与场景 在一台 Linux 服务器上同时运行 SEO 管理面板（`9401`）和卫星站渲染服务（`9402`）时，需要让 OpenResty/Nginx 在 443 端口统一接入，按域名分流到不同后端。新买的卫星域名挂上去打 404，根因是 `9402` 没有对应的 vhost，所有请求都落进了默认兜底规则，而 `9401` 的面板是独立 vhost 早已配好。这类"多 Docker 容器 + 单 IP 多域名"的站群场景是个典型的反代分流问题。 --- ## 核心结论 1. **每个端口/后端服务都必须有对应的 `server {}` 块**，`proxy_pass` 到 `127.0.0.1:端口`；缺 vhost 的域名命中不了任何规则，Nginx 返回 404。 2. **`proxy_set_header Host $host;` 是必须的**，省掉它，后端容器拿到的 Host 是 `127.0.0.1:9402`，无法按域名做内部分流，所有站都会渲染成同一个。 3. **容器端口绑定要限制到 loopback**，`docker-compose.yaml` 里 `"9402:8812"` 改成 `"127.0.0.1:9402:8812"`，否则公网直连绕过 CF/Nginx，域名→站点映射全暴露。 4. **新增域名用 `--expand` 追加到现有证书**，`certbot --nginx -d 新域名.com --expand`，不要为每个域名单独签，同一证书 SAN 扩展最简洁。 5. **不要用 `default_server` 兜底整个 `9402`**，catch-all 会让扫描器、SSRF 请求命中站群，`server_name` 显式白名单是正确做法。 --- ## 实现方案 ### 现状拓扑（问题状态） ### 目标拓扑 ### 第一步：新增卫星站 vhost 新建 `/etc/nginx/conf.d/satellites.conf`： ### 第二步：签 SSL 证书 首次签，把所有已知卫星域名一起加进去： certbot 会自动修改 `satellites.conf`，插入 `ssl_certificate` 路径并配置 HTTP→HTTPS 重定向。 以后每新增一个域名，`--expand` 追加到同一证书的 SAN 列表： ### 第三步：锁端口 修改 `docker-compose.yaml`，把 `9402` 绑到 loopback： 重启容器使端口绑定生效： 如果不改 compose，临时用防火墙封堵（两者都做更保险）： ### 第四步：验证并重载 验证反代是否生效： --- ## 避坑指南 **1. 不要用 `default_server` 兜底 9402** 后果：扫描器用随机 `Host` 访问你的 IP，全部命中站群。攻击者可以枚举所有 `Host` 值，收集完整的「域名 → 站点内容」映射，变相暴露站群结构。 **2. 忘写 `proxy_set_header Host $host` 导致所有域名渲染同一站** Nginx 默认转发给后端的 Host 头是 `proxy_pass` 目标的地址（`127.0.0.1:9402`），而不是客户端请求的域名。后端容器收到统一的 `127.0.0.1:9402` 作为 Host，无法做域名分流，所有请求都会返回默认站或报错。**只要后端需要按 Host 路由，这行必须有。** **3. `--expand` 加新域名时 certbot 需要域名已解析** certbot ACME 验证会向新域名发 HTTP 请求。如果域名 DNS 还没生效，或者域名走 CF proxy 但 origin 防火墙拦了 80 端口，验证会失败。操作顺序：先确认 `dig site3.com` 解析到本机 IP，再跑 certbot。走 CF 的域名需要临时关 proxy（橙云→灰云）让 certbot 完成 HTTP-01 验证，签完再开。 --- ## 底层机制 OpenResty/Nginx 处理请求时，第一步是按 `listen` 端口和 `server_name` 匹配 `server {}` 块。同一端口下有多个 server block 时，Nginx 拿请求的 `Host` 头做精确匹配、前缀匹配、正则匹配，全不命中才落进 `default_server`（没显式标记则用第一个 server 块）。正是这个匹配顺序，要求每个对外提供服务的域名必须有对应的 `server_name` 条目，新域名漏配就等于不存在。 `proxy_set_header Host $host` 的作用是将客户端原始请求的 `Host` 头透传到后端，而不是替换成 `proxy_pass` 里写死的地址。对于一个容器内同时承载多个站点的"多租户"架构，后端服务正是依赖这个 Host 头来区分请求属于哪个站，拿掉它，整个域名分流机制就断了。
