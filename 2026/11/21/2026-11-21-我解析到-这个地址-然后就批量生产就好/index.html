# Caddy On-Demand TLS：批量域名 SaaS 的自动证书架构 ## 背景与场景 做卫星站 / 白标 SaaS 时，用户绑定自定义域名是核心功能。传统做法是 openresty + certbot：用户绑域名后，运维人员 SSH 上去手跑 `certbot -d xxx` 再 reload nginx，完全不可能批量化。当产品要支持「用户解析 CNAME → 面板点批量生成 → 自动上线 HTTPS」的零手工流程时，certbot 模型根本撑不起来，需要换成 Caddy 的 on-demand TLS 架构。 ## 核心结论 1. **certbot 是预签发模型，无法覆盖首次握手**：TLS 握手发生在 HTTP 请求之前，certbot 要求证书事先存在磁盘上；对于批量陌生域名，每次都要人工介入 `certbot -d xxx`，无法自动化。 2. **Caddy on-demand TLS 通过 `ask` 接口实现按需签发**：Caddy 在首次 TLS 握手时向你指定的 HTTP 接口询问「这个域名允许签吗」，接口返回 2xx 则立刻走 ACME 签发证书并缓存，之后复用；返回非 2xx 则拒绝握手。 3. **`ask` 接口必须严格过滤，防止 ACME 配额被打爆**：Let's Encrypt 每个注册域名每周限 50 张证书；`ask` 接口若不校验，扫描器随便拿一批域名轮询就能耗尽配额，导致所有真实域名也无法签发。 4. **迁移路径是「openresty 让出 443，Caddy 接管，openresty 变内部反代目标」**：openresty 从监听 `0.0.0.0:443` 改成监听 `127.0.0.1:9400`，Caddy 接管公网 443，对 admin 子域名直接反代到 `:9401`，对其他域名走 on-demand TLS 后反代到 `:9402`（sites 容器）。 5. **`ask` 接口响应必须 < 100ms**，否则 TLS 握手超时（通常客户端超时 10s，但握手阶段网络 RTT + ACME 签发本身已经很长，不能再让 `ask` 拖后腿）。 ## 实现方案 ### 1. 后端加 `/api/satellites/check` 端点 **Rate limit 保护**（防止扫描器耗尽配额）： ### 2.
