进程级 inflight 计数治本地 LLM 生成慢

2026-11-20 AI
# 前台优先门：用进程级 inflight 计数治本地 LLM 生成慢 ## 背景与场景 mac-mini M4 16GB 是 shanggu 的本地推理节点，只跑单个 7B 模型（MLX/Ollama 各一路），内存预算极紧。用户反馈「发完一条消息、下一条明显卡顿」。最初怀疑夜间蒸馏/探活任务抢资源，全量排查后发现假设错误——真凶是 **Layer A pattern sink**：每条 chat 结束后起 goroutine 直连本地 HTTP 跑 `qwen3:4b` 做模式沉淀，前后台共用同一个推理入口，前台 chat 请求打到已被后台占满的 MLX/Ollama 进程上，表现为「发完卡 1-2 秒才开始回复」。 此 PR（`ai-agent#314`，分支 `claude/sleepy-hofstadter-7824ee`）借鉴 linger 项目的「前台优先调度」思路，在进程层引入零锁、非饿死的前台让路门，7 文件 +317/-1 行。 --- ## 核心结论 **1. 夜间任务根本不碰本地模型，排查生成慢不要怀疑它们。** `nightly-reflect`/`nightly-expand`（`CloudGenerate`/claude-CLI）、brain consolidate（Haiku）、subscription sentinel（claude-CLI）、llm probe（Gemini Flash）、红队 review（Gemini→Haiku）全走云端路由；`nightly-prune` 是纯 DB 写。 **2. 真正和前台 chat 抢本地 7B 的只有两路。** ① `internal/agent/pattern/pattern.go` 的 `Sinker.Sink`——每条 chat 完成后异步调本地模型，**头号元凶**；② Gemini 配额耗尽时 `internal/adapter/zhukesi/http_background.go:301` 的 `GenerateLocal` 兜底——偶发低频。 **3. 前台优先门核心数据结构：inflight 计数 + lastActive 时间戳。** 新文件 `internal/shared/fg_gate.go`：一个 `atomic.Int32` inflight 计数 + `atomic.Int64` lastActive UnixMilli，前台生成时 `MarkForegroundBusy()`，后台入口调 `WaitForForegroundIdle()` 轮询让路，封顶 `FG_PRIORITY_MAX_WAIT_MS`（默认 120s）不饿死。 **4. 挂点只有四处，前台路径零延迟零锁。** `mlx.go:GenerateStream`、`ollama.go:streamGenerate`（各覆盖 Generate+Stream 两路）、`pattern.Sink` 入口、crawler 本地兜底入口。`accelerator.go` 预热 ctx 打 `WithBackground` 标。云端 chat 不经本地推理路径，完全不受影响。 **5. 全部 env 开关，默认开启。** `FG_PRIORITY`（0 关）、`FG_PRIORITY_COOLDOWN_MS`（6000）、`FG_PRIORITY_MAX_WAIT_MS`（120000）、`FG_PRIORITY_POLL_MS`（250）。 --- ## 实现方案 ### 1. `internal/shared/fg_gate.go`（核心，零外部依赖） ### 2. 前台挂点：`internal/registry/llm/mlx.go` `ollama.go:streamGenerate` 完全对称，不赘述。 ### 3. 后台挂点：`internal/agent/pattern/pattern.go` crawler 兜底（`http_background.go:GenerateLocal`）同理。 ### 4. 预热打标：`internal/registry/llm/accelerator.go` ### 5. 验证命令 --- ## 避坑指南 **1. 不要用互斥锁替代 inflight 计数** 互斥锁会让前后台完全串行——后台拿锁后，前台必须等它跑完整个推理（可能 10-30s）才能开始。inflight 计数 + cooldown 是「让路」而非「阻塞」：前台永远不等后台，后台等前台。两者语义截然不同，误用互斥锁反而让前台体验更差。 **2. `TestDispatchRemote_LocalPath` 偶发失败与此 PR 无关，不要因它卡合入** 该测试查真实 Ollama `/api/ps` 判断常驻显存 vs 30% RAM 预算，在两个 session 同跑时内存紧张会失败。关掉前台门（`FG_PRIORITY=0`）照样失败——环境相关，实锤非此 PR 引入。 **3. embed / placement-bench / pentest cascade 不纳入门控** embed 耗时极短（向量化，毫秒级），placement-bench 是独立进程，pentest cascade 触发极罕见。过度纳入会让门控逻辑变重，违反「初阶别过度工程」原则。只管头号元凶 pattern sink 和 crawler 兜底，够用。 --- ## 底层机制 **为什么 cooldown 比 `inflight=0` 更重要** MLX 的流式推理增量写管道，inflight 计数在 `GenerateStream` 完整 stream 结束才通过 `defer` 归零。但即便 stream 结束，MLX 进程的 GPU/ANE 权重释放有几百毫秒尾部。cooldown（默认 6000ms）确保模型权重从加速器缓存中完全腾出后，后台任务再上。如果只判断 `inflight=0`，后台可能在前台最后一个 token 刚输出的瞬间插进来，依然产生抖动。 此外，agent loop 多轮推理之间存在自然间隙：前一轮 stream 结束，下一轮 prompt 还没打过来，`inflight` 瞬间为 0。cooldown 窗口覆盖了这段间隙，防止后台在两轮之间抢入再让下一轮前台请求延迟。这是 `fgLastActive` 时间戳的核心用途。 **为什么后台不饿死** `maxWait`（默认 120s）是安全网：用户持续聊天时，pattern sink 不可能永远等——超时后强制放行。实践中 6s cooldown + 自然发消息停顿（通常 3-10s）的场景，后台几乎不会等超过 15s。极端情况（用户连续快速发 100 条）下，后台最多积压 120s 后批量执行，不影响前台体验，KB 质量也不会因延迟降级。
