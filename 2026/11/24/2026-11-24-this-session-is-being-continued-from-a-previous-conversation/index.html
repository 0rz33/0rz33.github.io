# shanggu KB 双轨架构：从对话到训练集的 $0 闭环 ## 背景与场景 随着 shanggu 被频繁使用，KB 面临两个工程问题：**膨胀**（无限制写入导致检索噪声增大）和**同质化**（所有 pattern 堆进同一个桶，检索不区分领域）。同时存在更深的战略需求：能否让"用得越多"自动产出微调训练集，使本地 7B 越来越贴合用户行为——而不烧一个 token？ 本文档记录了解决这三个问题的完整架构决策和实现路径，以及随本轮一并落地的：**模型谱系版本化**、**自适应内存预算**、**本地降级诚实横幅**、**CLI 底部模型选择器**。 --- ## 核心结论 1. **KB 分两条完全不同的轨道**：`知识（hanlin_<域>）`= 人读 + RAG；`泛化（patterns_<域>）`= 机器复用 + SFT 种子。二者用途、膨胀机制、维护手段均不同，混在一起会让 nightly-expand 误用 Opus 扩写本该压缩的 pattern。 2. **pattern Sink 分域存储**：Sink 入口调 `knowledge.ClassifyWithFallback(uq)`（`internal/knowledge/taxonomy.go`），BM25 关键词匹配，< 1ms 无模型，分不出 fallback 到 `patterns`。对应写入 `patterns_code / patterns_devops / …`，检索只扫相关域。 3. **slug-exact 去重是第一道闸**：`crossVerify`（`internal/agent/pattern/quality.go`）对 `` slug=`...` `` 字段做精确比对，命中即 upsert 而非 insert。用 `strings` 解析，零 regexp 依赖（避免给文件加新 import）。 4. **SFT 种子导出是真 $0**：`GET /admin/finetune/export?format=sft` 纯规则拼 JSONL。**当前缺口**：PatternGenSamples 源尚未把 `patterns_*` 接进导出管道，接上后「用 → 蒸 → 导出即训练集」才真正闭环。 5. **模型谱系版本化实现端到端**：每个 shanggu SKU 对标具体 Claude 版本，`--model` 标志从 SKU 表穿透到 `claude CLI` 命令行，master→worker 转发路径全程携带 model 字段，不再靠 CLI 默认值猜。 --- ## 双轨全景图 --- ## 实现方案 ### 1. slug-exact 去重（`internal/agent/pattern/quality.go`） ### 2. pattern 域分类（两个 Sink 调用点） ### 3. 模型谱系版本化（`internal/shared/constants.go` + SKU 表） **master→worker 穿透路径**（此前是版本漏洞的关键点）： ### 4. 自适应内存预算（`internal/registry/llm/mem_budget.go`） 测试时注入：`t.Setenv("LLM_AVAIL_RAM_MB", "100000")` 避免真实 vm_stat 造成 flaky test。 ### 5. 本地降级诚实横幅（`internal/registry/llm/llm_generate.go`） --- ## 避坑指南 **1. patterns 和 hanlin 绝不能混用** - 混入后 nightly-expand 会误把 pattern（本该压缩）用 Opus 扩写放大，造成 KB 质量污染，且不可撤销。 - 判断标准：有来源引用、深度分析 → `shanggu_learn` → `hanlin_*`；从对话蒸馏的套路步骤 → pattern Sink → `patterns_*`。 **2. slug 去重依赖 LLM 生成 slug 字段** - 若本地 qwen3:4b 蒸馏时没输出 `` slug=`...` ``，`extractContentSlug` 返回空，去重退化为 rerank 软去重，同一知识点会重复写入。 - 验证：`grep "slug-exact" /var/log/shanggu/agent.log`；无命中则检查蒸馏 prompt 是否强制要求 slug 字段。 **3. 模型版本穿透的 5 个调用点都要改** - `proxyToWorker` 签名加 `model string` 后，有 5 处调用：`llm_cloud.go`、`anthropic.go`、`subscription_sentinel.go`、`cascade.go`、worker `router_domains.go`。漏改任意一处，对应路径版本固定为空字符串（CLI 用 default 而非指定版本）。 - 验证命令：`claude --model claude-opus-4-8 -p "say ok"` 和 `--model claude-opus-4-7` 均应返回正常响应（模型自报版本可能幻觉，以 `--model` 被 accept 无报错为准）。 --- ## 底层机制 **为什么泛化轨要"压缩"而知识轨要"扩写"** 知识轨面向人读和大模型补充上下文（RAG），越详细越好，所以 nightly-expand 用 Opus 把短条目扩写成 2000 字 blog。泛化轨面向 SFT 训练：训练数据要紧凑、格式统一、去噪，pattern Sink 把整段对话蒸成 `{Type, Steps, slug}` 三字段种子，就像教科书的例题解法——不要废话。两个方向相反，底层是对"机器消费 vs 人消费"的不同优化目标。 **$0 分类怎么做到的** `knowledge.ClassifyWithFallback` 不调任何 LLM。它维护 `domainKeywords map[string][]string`，对问题做 tokenize + 关键词交集计数，取 top-1 域。速度 < 1ms，纯内存，零网络。代价是对混领域问题（"用 Go 写金融 API"）准确率有限，这就是为什么有 `patterns` fallback 桶兜底，并建议 nightly-prune 优先清理 fallback 桶里的低命中条目。 --- ## 部署检查清单 > **当前状态**：slug-exact 去重（a73ca1a0）和域分类（600a6344）已推 main，mini 需再跑一次 `./ai.sh deploy` 才生效。PatternGenSamples 接 patterns_* 进 SFT 导出管道是下一个明确缺口，3090 到货前不急。
