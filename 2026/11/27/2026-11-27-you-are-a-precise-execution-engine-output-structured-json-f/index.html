# JumpServer 统一入口：所有机器 22 端口只对跳板机开放 ## 背景与场景 原有运维环境中，多台 Linode/AWS 机器对外开放了 22 端口，依赖 PAM OTP（`libpam-google-authenticator`）做双因子认证。这套方案的隐患在于：OTP 验证在每台目标机上各自配置，自动化脚本无法应答验证码弹窗，且多人共用 root 时 OTP 密钥同一把无法区分操作者。需要一套集中入口：用户只通过 JumpServer 进来，目标机 22 端口不对外暴露，审计日志统一管理。 ## 核心结论 1. **OTP 移到 JumpServer，目标机不再挂 PAM OTP**：JumpServer 自动化登录无法应答目标机的验证码弹窗，双因子在 JumpServer 层（系统设置 → 安全设置 → MFA 全局强制）一次解决。 2. **目标机 sshd 改为纯公钥认证**：`AuthenticationMethods publickey`，同时 `PasswordAuthentication no`、`KbdInteractiveAuthentication no`、`PermitRootLogin no`，写进 `/etc/ssh/sshd_config.d/99-jms.conf`。 3. **三层防火墙同时收紧**：云防火墙（AWS 安全组 / Linode Cloud Firewall）是主要手段，主机 `ufw` 是兜底，两者都把 22 端口来源限制为 `JMS_IP/32`，只靠其中一层不够。 4. **Docker 端口绕过 ufw**：JumpServer 用 Docker 部署，80/443/2222 要靠云防火墙限源，ufw 对这些端口无效。 5. **JumpServer 是新单点，是最高价值目标**：私钥和 `config.txt`（含 `SECRET_KEY`）加密备份，数据库定期备份；`SECRET_KEY` 丢失则托管的凭据无法解密。 ## 实现方案 ### 0. 动手前 ### 1. 安装 JumpServer 首次登录后立即执行： 1. 改管理员密码 2. 系统设置 → 安全设置 → **MFA 全局强制** 3. 配置 HTTPS，证书放 `/opt/jumpserver/config/nginx/cert/` 4. 备份 `/opt/jumpserver/config/config.txt`（含 `SECRET_KEY`） ### 2. 准备 JumpServer 访问目标机的密钥 在 JumpServer 控制台：**账号管理 → 账号模板 → 新建**，用户名 `jmsops`，类型 SSH 密钥，粘贴私钥内容。 ### 3. 在每台目标机上创建账号并放入公钥 ### 4. JumpServer 录入资产与授权 1. **资产管理 → 资产列表 → 创建 Linux 主机**：填 IP、端口 22、账号选 `jmsops` 模板 2. **用户管理**：每人独立账号（解决原手册"共用 root OTP 密钥"问题），强制绑定 MFA 3. **权限管理 → 资产授权**：用户组 → 节点/资产 → 账号 `jmsops` 4. 开启**会话录像**和**命令记录** ### 5. 验证连通（此时 22 端口还未关） **所有目标机验证通过后，才继续下一步。** ### 6. 收紧三层防火墙 #### 第 1 层：云防火墙（主要手段） **AWS 安全组**：入站 22，源改为 `JMS_IP/32`，删除 `0.0.0.0/0`。 **Linode Cloud Firewall 入站规则**： - 允许 TCP 22，来源 `JMS_IP/32` - 入站默认策略：Drop #### 第 2 层：主机防火墙 ufw（兜底） #### 第 3 层：sshd 加固（目标机） 验证实际生效值（`sshd -T` 展示的才是运行时值，不是文件里写的）： ### 7. 最终验证 ## 避坑指南 **1. ufw 对 Docker 端口无效，JumpServer 的 Web/SSH 端口必须在云防火墙收紧** JumpServer 通过 Docker 发布端口（`-p 443:443`），Docker 直接修改 iptables，绕过了 ufw 的 `INPUT` 链。如果只在目标机上加 ufw 规则而没有配云防火墙，80/443/2222 实际对全网开放。正确做法：云防火墙只放行运维固定 IP 访问这三个端口。 **2. 改 sshd 配置后不要 `systemctl restart`，要 `reload`** `restart` 会关闭所有现有 SSH 连接，包括你正在操作的会话。`reload` 让 sshd 重读配置、只对新连接生效，不影响已建立的会话。在改配置未验证时断开会话会有锁出门的风险。操作顺序：`sshd -t`（语法检查）→ `systemctl reload ssh` → 另开新会话验证 → 验证通过后才断旧会话。 **3. JumpServer IP 变化会导致所有目标机全部失联** 所有云防火墙和 ufw 规则都基于 `JMS_IP/32`。如果 JumpServer 机器重启、浮动 IP 漂移或迁移，22 端口白名单失效，只能靠带外控制台救援。部署前务必绑定固定 IP（Linode 的 Static IP、AWS 的 EIP），并在密码管理器里记录带外控制台入口。 ## 底层机制 **为什么原 PAM OTP 和 JumpServer 不兼容**：JumpServer 的 SSH 组件（koko）以自动化方式登录目标机，它持有私钥，登录时走 `publickey` 认证通道，整个流程没有人工交互。而 PAM `pam_google_authenticator.so` 要求在 `keyboard-interactive` 通道里弹出验证码提示并等待用户输入。两者相遇的结果是：koko 收到验证码提示但不知道如何应答，直接返回 `Permission denied`，表现为原手册的坑点 1/2。解决方式是把 OTP 层上移到 JumpServer 本身——用户登录 JumpServer 时完成 MFA，之后 JumpServer 对内部目标机的连接走纯公钥，完全自动化。 **三层防火墙的分工**：云防火墙（安全组/Cloud Firewall）在数据包到达虚拟机网卡之前就丢弃，是主要隔离手段，完全不依赖目标机的操作系统状态；ufw 在操作系统 iptables 层过滤，是系统被入侵后的最后一道防线；sshd 配置（禁密码、仅公钥）是认证层面的加固，三者功能互补，不可互相替代。
