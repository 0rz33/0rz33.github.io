[expanded] CloudFront distribution 跨账号迁移最容易踩的坑

原始问题: CloudFront distribution 跨账号迁移最容易踩的坑

CloudFront Distribution 跨账号迁移技能点清单

场景占位: 从 迁移 distribution 到 ,保持 CNAME 不变
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 先在目标账号创建 distribution 并添加 CNAME,再删除源账号 CNAME

  • 规则: 在 新建 distribution 时直接配置 CNAME,此时会报错 CNAMEAlreadyExists,这是预期行为
  • 为什么: CloudFront CNAME 全局唯一锁由 API 调用时刻决定而非 DNS 生效时刻,必须先删源再加目标会导致 30-90 秒窗口期被其他账号抢占
  • 踩坑: 以为”先删旧 CNAME 再加新 CNAME”是安全顺序,实际这个窗口期 CNAME 处于全局未锁定状态
  • 例外: 使用 CloudFormation StackSets 跨账号部署时可原子化操作,但需提前配置 trust relationship

2. 用 ACM 证书时必须在 us-east-1 申请并跨账号共享

  • 规则: 目标账号 的 ACM 证书必须在 us-east-1 region 存在,即使 distribution 是全球服务
  • 为什么: CloudFront 底层证书存储只认 us-east-1,其他 region 的证书在 distribution 配置界面不可见
  • 踩坑: 在 ap-southeast-1 申请了通配符证书,CloudFront 控制台下拉列表为空,以为是权限问题反复检查 IAM policy
  • 例外: 使用自定义 SSL 证书上传到 IAM 时不受此限制,但需额外管理证书轮换

3. 迁移前必须导出完整 distribution config 为 JSON,不能依赖控制台截图

  • 规则: 用 aws cloudfront get-distribution-config --id <DIST_ID_OLD> 导出完整配置,包含 ETag 用于后续 update 操作
  • 为什么: 控制台隐藏了 20+ 个默认参数(如 MinTTL=0, SmoothStreaming=false),手动重建会丢失 cache behavior 优先级顺序和 lambda@edge 关联
  • 踩坑: 只记录了 origin domain 和 cache policy,迁移后发现 gzip 压缩失效、query string 转发行为变化
  • 例外: 纯静态 S3 源站且无自定义 header 时可简化,但仍建议全量导出做 diff

4. Lambda@Edge 函数必须先复制到目标账号 us-east-1 并重新关联

  • 规则: Lambda@Edge 函数无法跨账号引用,需在 us-east-1 重新部署函数,获取新 ARN 后更新 distribution config
  • 为什么: Lambda@Edge 的 IAM principal 绑定在源账号,CloudFront 服务角色无法 AssumeRole 到其他账号执行函数
  • 踩坑: 直接复制旧 distribution config 的 LambdaFunctionAssociations ARN,部署时报 AccessDenied 但错误信息不明确指向跨账号问题
  • 例外: 使用 CloudFront Functions(CFN)时可直接在目标账号重建,因其代码存储在 distribution 配置内

5. Origin Access Identity 迁移需同步更新 S3 bucket policy 的 Principal

  • 规则: 在 创建新 OAI,更新 S3 bucket policy 允许新 OAI 的 CanonicalUser ID,保留旧 OAI 权限直到迁移完成
  • 为什么: OAI 是账号级资源,其 CanonicalUser ID 在跨账号后完全不同,S3 bucket policy 必须显式授权新 ID
  • 踩坑: 只更新了 CloudFront distribution 的 OAI 配置,忘记改 S3 bucket policy,导致所有请求 403 但 CloudFront 日志显示 200
  • 例外: 源站是 public S3 bucket 或自定义 origin(ALB/API Gateway)时不涉及 OAI

6. 切换 DNS 前必须验证目标 distribution 的所有 edge location 已部署完成

  • 规则: 新 distribution 状态显示 Deployed 后,再等待 5-15 分钟,用 curl -H "Host: <DOMAIN>" https://<DIST_DOMAIN>.cloudfront.net 从多个地理位置测试
  • 为什么: Deployed 状态只表示配置已推送到控制平面,边缘节点的实际部署是异步的,过早切换 DNS 会导致部分地区 502/504
  • 踩坑: 状态变 Deployed 后立即修改 Route53 记录,亚太区用户大量报错但美东正常,回滚后发现是边缘节点未同步
  • 例外: 使用 CloudFront continuous deployment 蓝绿发布时可自动处理,但需 Enterprise Support 计划

7. 保留源 distribution 的 access logging 配置并对比新旧日志流

  • 规则: 迁移前后各保留 7 天日志,用 Athena 查询对比 request count、cache hit rate、4xx/5xx 比例,确认行为一致
  • 为什么: 很多配置差异(如 origin timeout、cache key 参数)不会导致明显错误,但会静默改变缓存效率和回源模式
  • 踩坑: 迁移后业务方未投诉,3 周后发现 origin 流量增加 40%,排查发现新 distribution 的 query string whitelist 配置错误导致缓存失效
  • 例外: 日志量极大(>1TB/天)时可采样对比,但至少要覆盖高峰时段

8. 使用 Route53 加权路由策略实现灰度切换而非直接 CNAME 切换

  • 规则: 创建两条 A record(alias 到新旧 distribution),初始权重 99:1,每 10 分钟调整权重直到 0:100
  • 为什么: 直接修改 CNAME 的 DNS TTL 无法控制客户端缓存,灰度切换可在发现问题时秒级回滚且只影响小比例用户
  • 踩坑: 修改 CNAME 指向新 distribution 后发现问题,但 DNS TTL 300 秒导致 5 分钟内无法完全回滚,期间错误率累积
  • 例外: 非 Route53 托管的域名需在 DNS 提供商支持加权路由,或使用 CloudFront continuous deployment 的流量分割功能

9. 提前 24 小时降低 DNS TTL 到 60 秒,迁移完成后再恢复

  • 规则: 迁移前一天将 的 A/CNAME record TTL 从默认 300 改为 60,迁移后 24 小时再改回 300
  • 为什么: 降低 TTL 可缩短 DNS 缓存窗口,但需提前操作以清空全球递归 DNS 服务器的旧 TTL 缓存
  • 踩坑: 迁移当天才改 TTL,实际生效时间仍受旧 TTL(300 秒)约束,导致 5 分钟双写窗口
  • 例外: 使用 Route53 alias record 指向 CloudFront 时,TTL 由 CloudFront 控制(固定 60 秒),无需手动调整

10. 迁移 WAF Web ACL 时注意 rate-based rule 的计数器不会迁移

  • 规则: 在 重建 Web ACL 后,rate-based rule 的计数器从 0 开始,需临时提高阈值或禁用规则 1 小时
  • 为什么: WAF 计数器是运行时状态,存储在源账号的边缘节点内存中,新 distribution 关联新 Web ACL 时无历史数据
  • 踩坑: 迁移后立即遭受 DDoS 攻击,rate-based rule 因计数器重置未能及时触发,导致 10 分钟服务降级
  • 例外: 使用 AWS Shield Advanced 时可保留部分攻击特征,但仍建议迁移时段避开业务高峰

11. 源站是 ALB 时需更新 security group 允许新 distribution 的 AWS managed prefix list

  • 规则: 在 ALB security group 添加入站规则,source 为 com.amazonaws.global.cloudfront.origin-facing,同时保留旧规则直到迁移完成
  • 为什么: CloudFront 到 origin 的请求来自 AWS 骨干网特定 IP 段,新旧 distribution 可能使用不同边缘节点 IP
  • 踩坑: 只在 ALB 配置了旧 distribution 的 custom header 验证,新 distribution 请求被 security group 拒绝但 CloudFront 日志显示 504 timeout
  • 例外: 源站是 S3 或 API Gateway 时由 AWS 内部路由处理,不涉及 security group

12. 对于使用 signed URL/cookie 的场景,需双写密钥对到新旧 distribution

  • 规则: 在 上传相同 public key 创建新 key pair,更新应用层签名逻辑同时支持新旧 key pair ID,保留 7 天重叠期
  • 为什么: Signed URL 中的 key pair ID 必须匹配 distribution 关联的 trusted key groups,跨账号后 key pair ID 会变化
  • 踩坑: 迁移后所有已签发的 URL(如邮件中的下载链接)立即失效,用户投诉激增但无法快速修复
  • 例外: 使用 CloudFront key groups(推荐)而非 legacy key pairs 时,可在迁移前将两个账号的 public key 都加入 key group

13. 迁移窗口期禁用 auto-invalidation 流水线,改为手动双写失效请求

  • 规则: 暂停 CI/CD 中的 aws cloudfront create-invalidation 步骤,改为脚本同时向 和 发送相同 invalidation
  • 为什么: 自动化流水线通常硬编码 distribution ID,迁移期间只失效一个 distribution 会导致新旧缓存不一致
  • 踩坑: 发布新版本后,旧 distribution 缓存已失效但新 distribution 仍返回旧内容,灰度切换时用户看到版本回退
  • 例外: 使用 cache policy 的 TTL 控制而非 invalidation 时影响较小,但仍建议双写

14. 提前确认目标账号的 service quota 足够,特别是 distributions per account 和 invalidations per second

  • 规则: 在 Service Quotas 控制台检查 的 CloudFront limits,如不足提前 3-5 个工作日申请提升
  • 为什么: 默认每账号 200 个 distributions,大型组织迁移时可能超限,且 quota 提升需人工审批
  • 踩坑: 迁移当天创建第 201 个 distribution 时报 LimitExceeded,紧急提交 quota 申请但需等待 2 个工作日
  • 例外: 使用 AWS Organizations 的 delegated administrator 可集中管理 quota,但需提前配置

15. 迁移完成后保留源 distribution 7-14 天再删除,期间监控其流量归零

  • 规则: 用 CloudWatch metrics 监控 的 Requests 指标,确认连续 7 天为 0 后再执行 disable + delete
  • 为什么: 部分客户端(如企业代理、CDN 厂商)的 DNS 缓存可能超过 TTL,过早删除会导致长尾流量 404
  • 踩坑: 迁移后 3 天删除旧 distribution,一周后收到某企业客户投诉无法访问,排查发现其网络设备缓存了 7 天 DNS
  • 例外: 紧急安全事件(如证书泄露)需立即删除时,可配合 Route53 health check 强制 DNS 故障转移

🔥 5 秒必记 5 条

  1. 先在目标账号添加 CNAME 再删源账号,避免全局锁竞争窗口
  2. ACM 证书必须 us-east-1,Lambda@Edge 必须重新部署到目标账号
  3. 用 Route53 加权路由灰度切换,不要直接改 CNAME
  4. 导出完整 distribution config JSON,控制台隐藏 20+ 参数
  5. 保留源 distribution 7 天并监控流量归零再删除
