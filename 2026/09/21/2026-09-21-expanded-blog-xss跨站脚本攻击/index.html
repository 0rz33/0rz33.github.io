原始问题: [blog] XSS跨站脚本攻击

XSS 跨站脚本攻击技能点清单

场景占位: 攻击者向 注入脚本，受害者 浏览页面触发执行，窃取
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 把管理员当首要攻击目标而非普通用户

  • 规则: XSS 攻击优先瞄准网站管理员账户，而非普通访客
  • 为什么: 管理员权限可操作文件系统和数据库，XSS 从”客户端攻击”升级为”服务端攻击跳板”，普通用户只能窃取自己的 Cookie
  • 踩坑: 认为 XSS 只是偷 Cookie 的低危漏洞，忽略管理后台的 XSS 可直接 GetShell
  • 例外: 金融类网站普通用户 Session 劫持也是高危（涉及资金操作）

2. 输出点比输入点更关键

  • 规则: 检测 XSS 时先定位数据在哪里输出（HTML/JS/属性），再倒推输入点
  • 为什么: 同一个输入可能在多处输出，每个输出上下文的闭合方式完全不同（HTML 标签内 vs JS 字符串内 vs 属性值内）
  • 踩坑: 只盯着表单输入框测试，遗漏 URL 参数、Referer、Cookie 等非表单输入在页面其他位置的回显
  • 例外: DOM 型 XSS 的输出点在前端 JS 代码中，不经过服务端

3. 用”特殊字符+唯一标识”组合探测而非直接打 Payload

  • 规则: 第一轮提交 <>"'%;)(&+唯一ID12345，在源码中搜索唯一 ID 定位上下文
  • 为什么: 直接打 <script>alert(1)</script> 被过滤时无法判断哪个字符被处理，唯一 ID 能精准定位输出位置和周围语法结构
  • 踩坑: 盲目尝试各种 Payload 却不看响应源码，浪费时间在已经被实体化编码的场景
  • 例外: 自动化扫描工具已内置此逻辑，手工测试时必须遵守

4. 反射型 XSS 的危险度取决于传播方式

  • 规则: 反射型 XSS 标记为中危的前提是需要诱骗用户点击恶意链接，若能结合钓鱼或内部系统自动触发则升高危
  • 为什么: 单纯的反射型需要社会工程学配合，但内网 OA 系统的反射型 XSS 可通过邮件通知自动触发，无需用户点击
  • 踩坑: 看到”反射型”就写中危报告，忽略实际利用场景（如管理员必访问的报表页面）
  • 例外: 存储型 XSS 无需传播直接高危

5. 存储型 XSS 的持久化位置决定影响面

  • 规则: 检查恶意脚本存储在数据库、日志文件还是缓存，以及被哪些页面读取
  • 为什么: 存在个人资料的 XSS 只影响查看该资料的用户，存在公共评论区的 XSS 影响所有访客，存在管理日志的 XSS 专打管理员
  • 踩坑: 发现存储型 XSS 就直接定高危，实际该字段只在用户自己的设置页显示（自己打自己）
  • 例外: 即使自 XSS，若能配合 CSRF 强制受害者修改自己资料也可利用

6. DOM 型 XSS 绕过所有服务端防护

  • 规则: 当输入数据通过 location.hash、document.referrer 等直接被前端 JS 操作 DOM 时，服务端过滤完全无效
  • 为什么: 数据流从未经过服务端（URL 的 # 后内容不发送到服务器），innerHTML、eval、document.write 直接执行
  • 踩坑: 看到服务端有 WAF 和输入过滤就认为安全，忽略前端 JS 代码中的 element.innerHTML = location.hash.substring(1)
  • 例外: 若前端使用了 CSP 且配置正确，可部分缓解

7. 闭合语法比 Payload 本身更重要

  • 规则: 根据输出点的上下文构造闭合：HTML 标签内闭合标签、JS 字符串内闭合引号、属性值内闭合属性
  • 为什么: <script>alert(1)</script> 在 <input value="用户输入"> 中无效，需要 "><script>alert(1)</script><" 先闭合属性和标签
  • 踩坑: 背了一堆 Payload 字典却不分析输出位置，所有测试都失败
  • 例外: 在 <script>var user="输出点";</script> 中需要 ";alert(1);// 闭合 JS 语法

8. 工具扫描的漏报率极高

  • 规则: AWVS/AppScan 只能发现 30-50% 的 XSS，复杂场景（多步操作、异步加载、富文本）必须手工测试
  • 为什么: 工具无法理解业务逻辑（如先发帖再审核通过才显示），无法处理需要登录态的深层页面，无法测试 WebSocket 等非 HTTP 协议
  • 踩坑: 扫描器没报 XSS 就认为安全，实际富文本编辑器、文件上传后的预览页面、导出的 Excel 宏都可能存在 XSS
  • 例外: 简单的 GET 参数反射型 XSS 工具能有效发现

9. 黑名单过滤必有绕过

  • 规则: 遇到过滤 <script> 的防护，尝试大小写混淆、双写、编码、其他标签（<img>、<svg>、<iframe>）
  • 为什么: 黑名单需要穷举所有危险模式，HTML 和 JS 的灵活性导致绕过方式无穷（<scr<script>ipt>、<ScRiPt>、<img src=x onerror=alert(1)>）
  • 踩坑: 看到 <script> 被过滤就放弃，实际 <svg/onload=alert(1)> 可绕过
  • 例外: 白名单+严格的 HTML 解析器（如 DOMPurify）较难绕过

10. HttpOnly 只防 Cookie 窃取不防 XSS 本身

  • 规则: HttpOnly 标志使 JS 无法读取 Cookie，但 XSS 仍可发起 AJAX 请求、修改页面、钓鱼、键盘记录
  • 为什么: XSS 的危害不止窃取 Session，还包括以受害者身份执行操作（转账、发帖、改密码），HttpOnly 对此无效
  • 踩坑: 设置了 HttpOnly 就认为 XSS 不可利用，实际攻击者可用 XSS 发起 AJAX 请求到敏感接口
  • 例外: 纯静态展示页面且无敏感操作时，HttpOnly 确实大幅降低危害

11. CSP 是最后一道防线但配置常错

  • 规则: Content-Security-Policy 可阻止内联脚本和外部恶意域，但 unsafe-inline、unsafe-eval、过宽的白名单会失效
  • 为什么: 开发者为了方便常加 unsafe-inline 导致 CSP 形同虚设，或白名单包含 *.googleapis.com 等可被利用的 CDN
  • 踩坑: 看到响应头有 CSP 就认为 XSS 不可利用，实际 script-src 'unsafe-inline' 完全不防
  • 例外: 严格的 CSP（仅允许特定 nonce 或 hash）可有效防御

12. 富文本编辑器是 XSS 重灾区

  • 规则: 所有允许用户输入 HTML 的富文本编辑器（TinyMCE、CKEditor、UEditor）默认配置都可能存在 XSS
  • 为什么: 富文本需要保留部分 HTML 标签（加粗、链接、图片），过滤逻辑复杂且常有遗漏（如 <a href="javascript:alert(1)">）
  • 踩坑: 认为用了知名编辑器就安全，实际需要配置白名单且定期更新版本
  • 例外: Markdown 编辑器若正确转义输出则相对安全

13. 测试时用 alert(document.domain) 而非 alert(1)

  • 规则: Payload 使用 alert(document.domain) 或 alert(document.cookie) 证明可执行任意 JS
  • 为什么: 某些场景 alert(1) 可能被拦截但 alert(document.domain) 能绕过，且能证明在目标域执行（非沙箱）
  • 踩坏: 用 alert(1) 测试成功但写报告时无法证明危害，甲方质疑”弹个框有什么用”
  • 例外: 生产环境测试用 console.log 代替 alert 避免影响用户

14. 二次注入型 XSS 最隐蔽

  • 规则: 数据在 A 页面输入时被安全存储，但在 B 页面（如导出、打印、邮件）输出时未过滤
  • 为什么: 开发者只在输入点做了防护，认为数据库中的数据”已安全”，在其他输出场景忘记转义
  • 踩坑: 在表单提交页面测试未发现 XSS 就结束，实际在管理后台的用户列表页面存在 XSS
  • 例外: 导出的 PDF、Excel 若包含恶意公式也属于此类

15. 测试账号权限要覆盖所有角色

  • 规则: 用普通用户、VIP 用户、管理员、超级管理员分别测试同一输入点
  • 为什么: 某些输入点对普通用户有严格过滤，但管理员发布公告时为了支持富文本而放松过滤
  • 踩坑: 只用普通测试账号扫描，遗漏管理后台的高危 XSS
  • 例外: 若无法获取高权限账号，在报告中说明测试覆盖范围

🔥 5 秒必记 5 条

  1. 管理员是 XSS 的首要目标，可从客户端攻击升级为服务端跳板
  2. 先找输出点看上下文，再构造闭合，别盲目打 Payload
  3. DOM 型 XSS 绕过所有服务端防护，数据流不经过后端
  4. HttpOnly 只防 Cookie 窃取，XSS 仍可发 AJAX 和钓鱼
  5. 富文本编辑器和二次输出页面（导出/打印）是重灾区
