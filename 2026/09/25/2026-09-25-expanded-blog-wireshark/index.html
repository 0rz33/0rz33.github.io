Wireshark 网络抓包分析技能清单

场景占位: 用 表示本机地址, 表示远端地址, 表示服务端口
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 过滤器写在捕获前还是捕获后决定性能和完整性

  • 规则: 捕获过滤器(Capture Filter)丢弃不符合条件的包且不可恢复,显示过滤器(Display Filter)仅隐藏但数据仍在
  • 为什么: 捕获过滤器用 BPF 语法在内核层丢包,显示过滤器用 Wireshark 语法在应用层过滤,90% 的人混用导致抓不到关键包或文件过大
  • 踩坑: 生产环境用捕获过滤器 host <REMOTE_IP> 后发现漏抓了中间代理的包,因为真实通信经过
  • 例外: 排查未知问题时先全量捕获再用显示过滤器,避免过早丢弃线索

2. ip.addr 是双向匹配会抓到意料外的流量

  • 规则: ip.addr == <TARGET_IP> 匹配源地址或目的地址,需要单向过滤必须用 ip.src 或 ip.dst
  • 为什么: 大部分协议是双向的,用 ip.addr 会同时抓到请求和响应,导致包数量翻倍且难以区分主动连接方
  • 踩坑: 想抓客户端主动发起的连接用了 ip.addr == <CLIENT_IP>,结果把服务端响应也抓进来,误判为客户端发包频率异常
  • 例外: 分析完整会话时 ip.addr 更方便,配合 tcp.stream eq <N> 追踪单条流

3. 包编号(No.)在过滤后不连续是正常的

  • 规则: Wireshark 的 No. 列是捕获时的全局序号,应用显示过滤器后编号会跳跃但不会重新编号
  • 为什么: 编号对应 pcap 文件中的物理位置,重新编号会导致无法与原始文件对应,这是设计而非 bug
  • 踩坑: 过滤后看到 No. 从 1234 跳到 5678,以为中间的包丢失了,实际是被过滤条件隐藏
  • 例外: 导出过滤后的包为新文件时,新文件会重新从 1 开始编号

4. TCP 三次握手的 Seq 不是从 0 开始是安全机制

  • 规则: SYN 包的 Seq 是随机初始序列号(ISN),Wireshark 默认显示相对序列号(从 0 开始),需要看真实值要关闭 “Relative sequence numbers”
  • 为什么: 随机 ISN 防止序列号预测攻击,相对序列号是 Wireshark 为了方便人类阅读做的转换
  • 踩坑: 对比两端抓包时发现 Seq 不一致,因为一端开了相对序列号显示,另一端显示的是绝对值
  • 例外: 分析 TCP 劫持或序列号预测攻击时必须看绝对序列号

5. Len=0 的包不是空包而是控制包

  • 规则: TCP 包的 Len 字段表示有效载荷长度,SYN/ACK/FIN 等控制包 Len=0 但仍然消耗序列号
  • 为什么: TCP 头部的控制标志位(SYN/FIN)本身占用 1 个序列号,但不计入 Len,这是协议设计
  • 踩坑: 看到大量 Len=0 的包以为网络空转,实际是正常的 keepalive 或连接管理
  • 例外: ACK 纯确认包既不消耗序列号也 Len=0,但会推进确认号(Ack)

6. 时间戳格式影响问题定位效率

  • 规则: 默认时间戳是相对第一个包的偏移量,排查超时问题改用 “Time of Day” 格式对照日志
  • 为什么: 相对时间适合看包间隔,绝对时间适合与应用日志、数据库慢查询日志对齐
  • 踩坑: 应用日志显示 14:32:15 超时,但 Wireshark 显示 +125.334s 无法快速定位到对应的包
  • 例外: 分析重传间隔、RTT 时相对时间更直观

7. 同一个 TCP 流的包可能分散在文件各处

  • 规则: 使用 “Follow TCP Stream” 或过滤 tcp.stream eq <N> 聚合同一条连接的所有包
  • 为什么: Wireshark 按时间顺序捕获所有网卡流量,多条并发连接的包会交错出现
  • 踩坑: 手动用 ip.addr and tcp.port 过滤后仍看到多条连接混在一起,因为客户端用了不同的源端口
  • 例外: UDP 没有流的概念,需要用 ip.addr and udp.port 手动组合过滤

8. 抓包文件过大时先用 editcap 切割再分析

  • 规则: 超过 500MB 的 pcap 文件会导致 Wireshark 卡顿,用 editcap -c <包数> <输入> <输出前缀> 按包数切割
  • 为什么: Wireshark 会将整个文件加载到内存建索引,大文件会耗尽内存或导致 GUI 无响应
  • 踩坑: 直接打开 5GB 的抓包文件,Wireshark 卡死 10 分钟后系统 OOM
  • 例外: 只需要统计信息时用 capinfos 或 tshark -q -z 无需加载完整文件

9. 显示过滤器支持逻辑运算但优先级反直觉

  • 规则: and 优先级高于 or,复杂条件必须加括号,如 (ip.src == <IP_A> or ip.src == <IP_B>) and tcp.port == <PORT>
  • 为什么: 不加括号时 ip.src == <IP_A> or ip.src == <IP_B> and tcp.port == <PORT> 会被解析为 ip.src == <IP_A> or (ip.src == <IP_B> and tcp.port == <PORT>)
  • 踩坑: 想过滤两个 IP 的 80 端口流量,写成 ip.addr == <IP_A> or ip.addr == <IP_B> and tcp.port == 80,结果把 的所有端口都抓进来了
  • 例外: 单一条件无需考虑优先级

10. 重传包(Retransmission)出现不一定是网络问题

  • 规则: TCP 重传可能由接收窗口满、应用层处理慢导致,需结合 “TCP Window Full” 和 “TCP ZeroWindow” 分析
  • 为什么: 网络丢包和接收端来不及处理都会导致重传,但根因不同,前者查网络设备,后者查应用性能
  • 踩坑: 看到大量 Retransmission 就升级带宽,实际是数据库查询慢导致应用接收缓冲区满
  • 例外: 无线网络环境下少量重传(< 1%)是正常的

11. Expert Info 的 Warning 不等于故障

  • 规则: Expert Info 中的 “TCP Previous segment not captured” 可能是抓包点不完整,不一定是真丢包
  • 为什么: 在客户端抓包时看不到服务端发出但未到达的包,在中间设备抓包时可能因端口镜像丢包
  • 踩坑: 在负载均衡器后的服务器抓包,看到大量 “Previous segment not captured”,实际是流量分散到其他服务器了
  • 例外: 在发送端抓包仍出现此告警,大概率是真丢包

12. 解密 HTTPS 流量需要提前配置不能事后补救

  • 规则: 必须在抓包前设置环境变量 SSLKEYLOGFILE=<路径> 让应用记录会话密钥,或导入服务器私钥(仅 RSA 且无前向保密)
  • 为什么: TLS 1.3 和使用 ECDHE 的 TLS 1.2 有完美前向保密,抓包后无法通过私钥解密
  • 踩坑: 抓完包才想起来要解密 HTTPS,即使有服务器私钥也解不开,因为用了 ECDHE 密钥交换
  • 例外: 中间人代理(如 mitmproxy)可以实时解密,但会改变证书链

13. 协议解析错误时手动指定 “Decode As”

  • 规则: 非标准端口的协议(如 8080 跑 HTTP)需要右键包选择 “Decode As” 指定协议类型
  • 为什么: Wireshark 默认靠端口号判断协议,自定义端口会被识别为 TCP 原始数据
  • 踩坑: 抓到 的流量显示为乱码,实际是 HTTP 协议但 Wireshark 不认识
  • 例外: 部分协议有特征字节(如 HTTP 的 “GET”),Wireshark 会启发式识别

14. 导出对象功能只对完整流有效

  • 规则: “File -> Export Objects -> HTTP” 导出文件时,如果 TCP 流不完整(缺 SYN 或 FIN)会导出失败
  • 为什么: Wireshark 需要完整的 HTTP 请求响应对才能重组文件,中途开始抓包会缺少流的起始部分
  • 踩坑: 抓包过程中才打开 Wireshark,想导出传输的文件时发现列表为空
  • 例外: 使用 “Follow TCP Stream” 手动复制 payload 可以绕过此限制

15. 统计功能比逐包分析更快定位瓶颈

  • 规则: 用 “Statistics -> Conversations” 找出流量最大的连接,”Statistics -> IO Graph” 看流量趋势
  • 为什么: 逐包分析 10 万个包需要数小时,统计视图 10 秒内就能发现异常连接或流量突刺
  • 踩坑: 网络慢但不知道哪个服务占带宽,逐个过滤 IP 查了半天,用 Conversations 按 Bytes 排序 5 秒找到
  • 例外: 分析协议细节(如异常标志位)时仍需逐包检查

🔥 5 秒必记 5 条

  1. 捕获过滤器丢包不可恢复,显示过滤器仅隐藏,排查未知问题先全抓
  2. ip.addr 是双向匹配,单向过滤必须用 ip.src/dst
  3. 重传包需结合 Window Full 判断是网络丢包还是接收端慢
  4. 解密 HTTPS 必须抓包前配置 SSLKEYLOGFILE,事后无法补救
  5. 大文件先用 editcap 切割,统计用 Conversations 比逐包快 100 倍
