Wireshark 网络抓包分析技能清单

场景占位: 用 表示本机地址, 表示远端地址, 表示端口号
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 过滤器用 ip.addr 而非 ip.src or ip.dst 做双向流量分析

  • 规则: 查看与某 IP 相关的所有流量时直接用 ip.addr == <LOCAL_IP>, 不要写 ip.src == <LOCAL_IP> or ip.dst == <LOCAL_IP>
  • 为什么: ip.addr 是双向匹配的语法糖, 自动包含源和目标, 减少 50% 输入且避免括号优先级错误
  • 踩坑: 多条件组合时忘记加括号, 导致 ip.src == A or ip.dst == B and tcp.port == 80 被解析成 (ip.src == A) or (ip.dst == B and tcp.port == 80)
  • 例外: 需要明确区分请求方向时必须分开写 ip.src 和 ip.dst

2. 包编号 (No.) 在过滤后不变, 用于跨过滤器追踪同一个包

  • 规则: 记住可疑包的编号 (如 #12345), 切换过滤器后直接 Ctrl+G 跳转到该编号
  • 为什么: 编号是抓包时的全局唯一标识, 不受显示过滤器影响, 比时间戳更可靠 (时间戳可能重复到微秒级)
  • 踩坑: 以为过滤后编号会重新从 1 开始, 导致用相对位置 “第 3 个包” 描述问题时团队无法复现

3. TCP 三次握手只看 Seq=0 的 SYN 包, 不要被相对序列号迷惑

  • 规则: 判断连接建立时, 只认 Flags: SYN 且 Seq=0 (Wireshark 默认显示相对序列号)
  • 为什么: Wireshark 自动将真实 ISN (Initial Sequence Number) 归零显示, 真实 ISN 是随机 32 位数, 人类无法直接比对
  • 踩坑: 看到 SYN 包 Seq=3284756291 以为异常, 实际这是原始序列号, 需在 Edit → Preferences → Protocols → TCP 关闭 “Relative sequence numbers”
  • 例外: 分析序列号预测攻击时必须查看真实 ISN

4. Len=0 的包不是空包, 是控制包 (SYN/ACK/FIN)

  • 规则: 看到 Len: 0 不要认为是异常或丢包, 检查 Flags 字段确认是否为握手/挥手包
  • 为什么: TCP 控制包不携带应用层数据, 但消耗一个序列号 (SYN 和 FIN 各占一个 Seq), 这是协议设计的可靠性保证
  • 踩坑: 统计传输字节数时把 Len=0 的 ACK 包当成传输失败, 实际它只是确认包

5. 时间戳默认是相对时间, 排查延迟时必须切换到 “自上一个包的时间”

  • 规则: 分析响应延迟时, View → Time Display Format → Seconds Since Previous Displayed Packet
  • 为什么: 默认的 “自抓包开始” 时间戳需要人工做减法, 容易算错毫秒级差异
  • 踩坑: 用默认时间戳对比两个包, 发现 “0.523s - 0.521s = 2ms”, 实际应该是 “Delta time: 0.348s” (中间被过滤掉了其他包)

6. 捕获过滤器 (BPF) 和显示过滤器语法完全不同, 不能混用

  • 规则: 抓包前设置的是 BPF 语法 (host <LOCAL_IP>), 抓包后界面输入的是 Wireshark 语法 (ip.addr == <LOCAL_IP>)
  • 为什么: BPF 在内核层过滤 (高性能但功能少), 显示过滤器在应用层 (功能强但不减少磁盘写入)
  • 踩坑: 在捕获选项里输入 ip.addr == <LOCAL_IP> 导致抓包失败, 正确应该用 host <LOCAL_IP>
  • 例外: 远程抓包时必须用 BPF 减少网络传输量

7. Follow TCP Stream 会丢失重传包, 排查丢包必须看原始包列表

  • 规则: 右键 → Follow → TCP Stream 只显示成功传输的数据, 不显示乱序/重传/重复 ACK
  • 为什么: Stream 视图是应用层重组后的结果, 自动过滤了传输层的异常, 看不到网络质量问题
  • 踩坑: 用 Follow Stream 看到完整 HTTP 响应就认为网络正常, 实际中间有 15 次重传导致 3 秒延迟

8. Expert Info 的 “Warning” 不一定是问题, “Note” 可能才是致命错误

  • 规则: 点击左下角彩色圆点查看 Expert Information, 优先看 “Chat” 和 “Note” 里的 “Connection reset”
  • 为什么: Wireshark 的严重等级是基于协议规范, 不是业务影响, 比如 “Previous segment not captured” 是 Warning 但可能只是抓包开始时机问题
  • 踩坑: 只看 Error 和 Warning, 忽略了 Note 里的 “TCP Port numbers reused”, 导致没发现连接被中间设备重置

9. 统计流量时用 Statistics → Conversations, 不要手动加 Length 列

  • 规则: 分析哪个连接占用带宽时, Statistics → Conversations → TCP 标签页, 按 Bytes 列排序
  • 为什么: 手动筛选包再加 Length 会漏掉 TCP 重传和分片重组, Conversations 自动处理了这些边界情况
  • 踩坑: 用过滤器 ip.addr == <REMOTE_IP> 统计流量, 发现只有 2MB, 实际 Conversations 显示 15MB (重传了 13MB)

10. 抓包文件超过 100MB 时先用 editcap 切割, 不要直接打开

  • 规则: 命令行执行 editcap -c 10000 large.pcap split.pcap 按包数切割, 或 -i 60 按秒切割
  • 为什么: Wireshark 加载时会建立全文索引, 大文件可能导致内存溢出或 GUI 假死 5 分钟
  • 踩坑: 直接打开 2GB 文件, 等待 10 分钟后系统 OOM 被杀, 丢失了所有过滤器设置

11. 解密 HTTPS 流量需要 SSLKEYLOGFILE, 不是服务器私钥

  • 规则: 设置环境变量 export SSLKEYLOGFILE=/tmp/ssl.log 后启动浏览器, 再在 Wireshark 配置该文件路径
  • 为什么: 现代 TLS 用 ECDHE 等前向保密算法, 服务器私钥无法解密会话密钥, 必须从客户端导出 session keys
  • 踩坑: 拿到服务器证书私钥后配置 RSA keys list, 发现 HTTPS 仍然无法解密, 因为协商用了 TLS 1.3
  • 例外: 老旧系统用 RSA 密钥交换时可以用私钥解密

12. 看到大量 TCP Dup ACK 和 Fast Retransmission 先查接收端, 不是发送端网卡问题

  • 规则: 出现连续 3 个重复 ACK 触发快速重传时, 用 tcp.analysis.duplicate_ack_num == 3 过滤, 检查接收端是否有应用层阻塞
  • 为什么: 重复 ACK 是接收端发出的, 说明它收到了乱序包 (中间包丢失或延迟), 发送端只是响应重传
  • 踩坑: 看到本机发出大量重传包, 就认为本机网卡有问题, 实际是对端防火墙丢包率 5%

13. 用 IO Graph 可视化流量波动, 比盯着包列表快 10 倍定位突发

  • 规则: Statistics → I/O Graph, Y 轴选 “Bits/s”, X 轴设置 1 秒间隔, 添加过滤器对比不同流
  • 为什么: 人眼无法从包列表直接识别 “第 37 秒开始流量突增”, 图表可以秒级定位时间点
  • 踩坑: 发现 “偶尔卡顿” 问题时逐包翻看 2 小时抓包, 实际用 IO Graph 3 秒就能看到每 5 分钟一次的流量尖刺

14. 抓本机回环流量 (127.0.0.1) 在 Linux 要指定 lo 接口, Windows 需要安装 Npcap

  • 规则: Linux 上选择 “Loopback: lo” 接口, Windows 需勾选 Npcap 安装时的 “loopback support”
  • 为什么: 回环流量不经过物理网卡, 默认抓包驱动捕获不到, 需要特殊的虚拟接口支持
  • 踩坑: 在 Windows 上抓 localhost:8080 的流量, 选择了 “以太网” 接口, 结果一个包都抓不到

15. 保存过滤后的包用 File → Export Specified Packets, 不是 Save As

  • 规则: 应用显示过滤器后, File → Export Specified Packets → “Displayed” 单选框
  • 为什么: Save As 默认保存所有包 (包括被过滤隐藏的), 会把 5GB 原始文件完整保存
  • 踩坑: 过滤出 50 个关键包想发给同事, 用 Save As 保存后文件还是 5GB, 同事打开后看到 200 万个包

🔥 5 秒必记 5 条

  1. ip.addr 是双向过滤, 不要写 ip.src or ip.dst
  2. 包编号 (No.) 不受过滤影响, 用于跨过滤器追踪
  3. Follow TCP Stream 看不到重传, 排查丢包必须看原始列表
  4. Len=0 是控制包 (SYN/FIN), 不是空包或异常
  5. 大文件先用 editcap 切割, 不要直接打开导致 OOM
