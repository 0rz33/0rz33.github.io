Ollama 本地大模型运行框架：从部署到生产级 MCP 集成实践

一、背景：为什么需要本地 LLM 运行时

在生产环境中，依赖外部 LLM API 存在三大痛点：数据隐私泄露风险（敏感代码/日志不能上传）、成本不可控（高频调用月账单可达数千美元）、网络依赖（内网环境或离线场景无法使用）。Ollama 作为 Go 实现的轻量级模型运行时，通过 GGUF 量化格式将 7B-70B 模型压缩至 4-40GB，使单机部署成为可能。

典型场景包括：代码补全（Tabby/Continue）需要毫秒级响应、日志分析需要批量处理敏感数据、边缘设备（NAS/树莓派）需要离线推理能力。相比 vLLM/TGI 等推理框架，Ollama 牺牲了部分并发性能，换取零配置启动和跨平台一致性（macOS Metal/Linux CUDA/Windows ROCm）。

关键权衡：Ollama 适合单用户/小团队快速验证，生产级高并发场景仍需 vLLM + KServe；模型选择需平衡质量与资源，7B 模型（如 Llama3.2/Qwen2.5）在 16GB 内存设备上可达 GPT-3.5 80% 能力。

四、常见坑：五大典型故障模式

4.1 内存泄漏导致 OOM Killer

现象：运行数小时后进程被 kill，dmesg 显示 Out of memory: Killed process ollama。

根因：默认 OLLAMA_KEEP_ALIVE=5m 导致模型频繁加载/卸载，碎片化内存未释放。

修复：设置 OLLAMA_KEEP_ALIVE=-1（永久驻留）或配置 swap：

4.2 macOS Metal 性能退化

现象：M1/M2 Mac 推理速度仅 5 tok/s，远低于预期 30 tok/s。

根因：Rosetta 2 转译开销，或未启用 Metal Performance Shaders。

修复：强制使用 ARM64 原生二进制 + 验证 Metal 后端：

4.3 模型文件损坏（Checksum 不匹配）

现象：ollama run 报错 invalid model format 或 unexpected EOF。

根因：下载中断或磁盘写入错误导致 blob 损坏。

修复：删除损坏的 blob 并重新拉取：

4.4 并发请求导致推理队列阻塞

现象：第二个请求等待超过 60 秒无响应。

根因：默认 OLLAMA_NUM_PARALLEL=1，串行处理请求。

修复：根据显存调整并发数（每个实例约占用 1.5 倍模型大小）：
