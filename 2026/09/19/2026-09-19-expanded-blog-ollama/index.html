深度解析 Ollama 本地大模型运行框架：从部署到生产级实践

一、背景：为什么需要本地化大模型运行框架

在云端 LLM API 成本高昂、数据隐私合规要求严格的场景下，本地化部署大语言模型成为刚需。典型场景包括：金融机构处理敏感客户数据、医疗系统分析病历信息、企业内部知识库问答系统。传统方案需要深度学习工程师手动配置 CUDA 环境、模型量化、推理优化，运维成本极高。

Ollama 作为 Go 实现的轻量级框架，将模型下载、量化、推理服务封装成类似 Docker 的命令行工具。其核心价值在于：统一的模型格式（GGUF）、自动硬件检测（CUDA/Metal/CPU）、开箱即用的 REST API。对比 vLLM 需要 Python 环境和复杂依赖，Ollama 单二进制文件即可运行，适合快速验证和边缘部署。

关键技术选型考量：模型大小与硬件匹配（7B 模型需 16GB 内存）、推理延迟要求（CPU 推理 token/s < 10）、并发处理能力（单实例 QPS < 5）。生产环境需评估是否需要 GPU 加速、是否支持流式输出、API 兼容性（OpenAI 格式）。

四、模型微调与优化实战

4.1 LLaMA-Factory 微调流程

硬件选型：Mac M1/M2 使用 MPS 后端（Metal Performance Shaders），Linux 优先 CUDA。7B 模型全量微调需 40GB+ 显存，LoRA 微调降至 16GB。

关键参数调优：gradient_accumulation_steps 模拟大 batch（显存不足时）、warmup_ratio=0.1 稳定训练初期、fp16=True 减半显存占用。训练过程监控 GPU 利用率（应 > 80%）和损失曲线（应平滑下降）。

五、常见坑与排查手册

5.1 模型加载失败

现象：ollama run 卡住或报错 failed to load model

误判：认为是网络问题，反复 ollama pull

根因：磁盘空间不足或 inode 耗尽

5.2 内存溢出（OOM）

现象：系统卡死，dmesg 显示 Out of memory: Kill process

误判：增加 swap 分区

根因：并发请求超过 NUM_PARALLEL 限制，多个模型同时加载

5.3 GPU 未被识别

现象：nvidia-smi 正常但 Ollama 使用 CPU

误判：重装 CUDA 驱动

根因：Docker 未配置 GPU 运行时或 nvidia-container-toolkit 缺失

5.4 API 响应超时

现象：curl 请求 30s 后超时

误判：增加 Nginx proxy_read_timeout

根因：模型首次加载耗时长，未启用流式输出

5.5 模型输出质量差

现象：回答不连贯或重复内容

误判：认为模型太小，换更大模型

根因：采样参数不当（temperature 过高或 top_p 过低）
