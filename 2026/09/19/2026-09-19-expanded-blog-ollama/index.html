Ollama 本地大模型运行框架：从部署到生产级实践

一、背景：为什么需要本地 LLM 运行时

在云端 LLM API 成本高企、数据隐私合规要求严格的场景下，本地部署大语言模型成为刚需。典型场景包括：金融机构内网环境无法访问公网 API、医疗行业需满足 HIPAA 合规、研发团队需要离线代码补全能力、以及高频调用场景下云端 API 成本不可控。Ollama 作为轻量级 LLM 运行时，通过 Go 实现跨平台支持（macOS/Linux/Windows），内置模型量化与推理优化，提供 REST API 与 CLI 双接口，成为本地部署的首选方案。

相比传统方案（如直接使用 Transformers + PyTorch），Ollama 的核心优势在于：开箱即用的模型管理（pull/run/rm）、自动内存管理（根据硬件动态调整量化策略）、统一的 API 接口（兼容 OpenAI Chat Completions 格式）。但需注意其局限性：模型选择受限于官方仓库、推理性能不如 vLLM 等专用框架、缺乏分布式推理能力。在选型时需根据实际场景权衡易用性与性能。

二、诊断步骤：验证环境与模型可用性

在正式部署前，必须通过 read-only 命令验证硬件资源与模型兼容性，避免运行时 OOM 或性能瓶颈：

关键指标：模型加载时间（应 < 30s）、首 token 延迟（应 < 2s）、内存占用（7B 模型约 4-6GB）。若加载超时或 OOM，需切换更小模型（如 3B）或调整量化参数。

三、生产部署：容器化与高可用配置

3.1 Docker Compose 标准部署

生产环境必须配置：健康检查（/api/tags 端点）、日志轮转（避免磁盘打满）、资源限制（防止单容器耗尽宿主机资源）。模型文件通过 volume 持久化，避免容器重启后重新下载。

3.2 模型预热与版本管理

通过别名机制实现模型版本管理：生产流量指向 llama3-stable，新模型验证使用 qwen-canary，验证通过后通过 ollama cp 原子切换。

3.3 反向代理与限流

生产环境必须通过 Nginx/Envoy 实现：请求限流（防止单用户打爆服务）、超时控制（长文本生成需调整 timeout）、连接复用（keepalive 减少握手开销）。

关键指标：

  • 推理延迟：P50/P95/P99（目标：P95 < 3s）
