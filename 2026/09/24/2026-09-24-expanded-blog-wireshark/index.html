Wireshark 网络封包分析技能清单

场景占位: 抓取 与 间的 HTTP/TCP 流量,定位 超时问题
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 用 ip.addr 而非 ip.src/dst 做双向流量初筛

  • 规则: 首次定位问题时用 ip.addr == <TARGET_IP> 捕获所有相关流量
  • 为什么: 网络问题常出现在响应方向,单向过滤会漏掉对端的 RST/ICMP 错误包,导致误判为”无响应”实际是”主动拒绝”
  • 踩坑: 用 ip.src == <CLIENT_IP> 只看到请求发出,看不到服务端返回的 TCP RST,误以为丢包
  • 例外: 确认问题在单向时(如只关心出流量速率)才用 src/dst

2. 包编号(No.)在过滤后不变是定位时间线的锚点

  • 规则: 记录关键包的 No. 编号,切换过滤器时用编号快速跳转
  • 为什么: 时间戳会因显示格式改变,但 No. 是抓包顺序的绝对索引,跨过滤器对比时唯一可靠
  • 踩坑: 用相对时间戳对比两个过滤结果,发现时间对不上,实际是过滤后时间基准被重置

3. Len=0 的包才是纯协议控制,Len>0 才有业务数据

  • 规则: 排查应用层超时时先过滤 tcp.len > 0,跳过三次握手/心跳等噪音
  • 为什么: SYN/ACK/FIN 等控制包 Len 恒为 0,大量心跳包会淹没真正的数据传输,导致看不清业务交互时序
  • 踩坑: 看到大量包以为有数据传输,实际全是 TCP Keep-Alive(Len=0)

4. Seq 号突变说明中间有数据但未被抓到

  • 规则: 对比连续包的 Seq 号,若增量 > 前一包的 Len,说明有包在抓取点之前就被过滤或丢失
  • 为什么: Seq 是累计发送字节数,不连续意味着抓包点的过滤器或网卡丢包,不是网络丢包
  • 踩坑: 看到 Seq 跳跃就认为是网络丢包,实际是本地 BPF 过滤器配置错误

5. 三次握手的 Seq 是随机数,不要用绝对值判断

  • 规则: 关注 Seq 的相对增量,不要期望 SYN 包的 Seq 从 0 或 1 开始
  • 为什么: RFC 要求 ISN(初始序列号)随机化防 TCP 劫持,Wireshark 默认显示绝对值会看到巨大随机数
  • 踩坑: 看到 SYN 包 Seq=2847362901 以为异常,实际是正常随机 ISN

6. FIN 包出现但连接未关闭,检查是否半关闭状态

  • 规则: 看到 FIN 后继续有数据传输,说明是 TCP 半关闭(一端关闭写但仍可读)
  • 为什么: 应用层可能只关闭发送方向,接收方向仍在等数据,这在 HTTP/1.1 pipeline 或数据库连接池中常见
  • 踩坑: 看到 FIN 就认为连接结束,实际对端还在发送大查询结果,导致误判为”连接过早关闭”

7. 用 tcp.analysis.flags 快速定位 TCP 层异常

  • 规则: 过滤 tcp.analysis.flags 直接看重传/乱序/零窗口等 Wireshark 自动标记的问题
  • 为什么: 手动分析 Seq/Ack 关系容易漏掉边界情况,Wireshark 的启发式分析已覆盖 90% 常见异常
  • 踩坑: 盯着 Seq 号看半天没发现问题,实际 Wireshark 已标记 “TCP Retransmission” 但未注意到

8. 时间戳格式切换到”距前一包时间”排查延迟

  • 规则: View → Time Display Format → Seconds Since Previous Displayed Packet,直接看每包间隔
  • 为什么: 默认绝对时间需要人工计算间隔,切换后直接看到 0.523s 延迟,立即定位慢在哪两包之间
  • 踩坑: 用绝对时间手动减法,算错小数点导致误判延迟来源

9. Follow TCP Stream 会丢失重传包的真实时序

  • 规则: 初步看数据内容用 Follow Stream,定位重传/乱序问题必须回到包列表看原始序列
  • 为什么: Follow Stream 会合并重传包并重排序,看起来”正常”但掩盖了网络层的真实问题
  • 踩坑: Follow Stream 看到完整 HTTP 响应,误以为传输正常,实际有 30% 重传率

10. 捕获过滤器(BPF)和显示过滤器语法不同且不可互换

  • 规则: 捕获前用 BPF 语法(host <IP>),捕获后用 Wireshark 语法(ip.addr == <IP>)
  • 为什么: BPF 在内核层过滤(高性能但语法受限),显示过滤在应用层(功能丰富但不能减少磁盘写入)
  • 踩坑: 在捕获过滤器里写 ip.addr == <IP> 导致捕获失败,报语法错误

11. 抓包时网卡混杂模式未开启会漏掉非本机流量

  • 规则: 在交换网络抓其他主机流量时,必须开启 Promiscuous Mode 且配置端口镜像
  • 为什么: 现代交换机默认只转发目标 MAC 匹配的帧,混杂模式只是让网卡接受,还需交换机配合镜像
  • 踩坑: 开了混杂模式但只抓到本机流量,忘记在交换机上配置 SPAN/镜像端口

12. 用 Conversations 统计功能快速找流量 Top N

  • 规则: Statistics → Conversations → TCP 标签,按 Bytes 排序找出最大流量的连接
  • 为什么: 包列表逐个看效率低,Conversations 直接聚合显示哪个五元组传输了多少数据
  • 踩坑: 在包列表里翻半天找大流量连接,实际 Conversations 一秒就能排序出来

13. 彩色标记规则优先看黑色和红色包

  • 规则: 默认配色中黑底红字是错误(RST/ICMP 错误),深色背景是重传,优先关注这些
  • 为什么: Wireshark 默认配色方案已将异常包高亮,比手动过滤更快发现问题
  • 踩坑: 盯着绿色(正常)包看,忽略了中间零星的黑色 RST 包,导致漏掉连接被拒的根因

14. 导出特定对象(HTTP/SMB)比手动拼接流更可靠

  • 规则: File → Export Objects → HTTP,直接提取传输的文件,不要手动从 Follow Stream 复制
  • 为什么: 手动复制容易包含协议头或因编码问题损坏二进制文件,Export Objects 自动处理分片和解码
  • 踩坑: 从 Follow Stream 复制 JPEG 文件,保存后无法打开,实际包含了 HTTP 头部

15. 用 IO Graph 可视化流量波动定位突发时刻

  • 规则: Statistics → I/O Graph,Y 轴选 Bytes,快速看到哪个时间点流量突增
  • 为什么: 包列表看不出宏观趋势,图形化后 5 秒就能定位”14:23:17 开始流量暴增”
  • 踩坑: 在包列表里凭感觉判断”好像变慢了”,实际 IO Graph 显示带宽打满发生在 3 分钟前

🔥 5 秒必记 5 条

  1. ip.addr 抓双向,ip.src/dst 会漏对端错误包
  2. Len=0 是控制包,Len>0 才有业务数据
  3. Seq 号跳跃先查本地过滤器,不一定是网络丢包
  4. Follow Stream 会隐藏重传,定位问题必须看原始包列表
  5. 捕获过滤器用 BPF 语法(host),显示过滤器用 Wireshark 语法(ip.addr)
