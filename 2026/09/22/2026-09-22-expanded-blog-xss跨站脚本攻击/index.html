XSS 跨站脚本攻击防御与检测技能清单

场景占位: 攻击者向 注入脚本, 受害者 浏览触发, 管理员 成为提权跳板
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 把管理员当首要攻击目标而非普通用户

  • 规则: XSS 防御优先保护管理后台和高权限用户入口
  • 为什么: 管理员是客户端攻击转服务端攻击的跳板, 一个管理员 Cookie 等于拿下整站文件和数据库权限
  • 踩坑: 只防护前台留言板/评论区, 忽略后台日志查看/用户管理等管理员必访问页面
  • 例外: 纯静态展示站无后台时可降低优先级

2. 输出点比输入点更关键

  • 规则: 检测时先定位数据在哪里输出到 HTML, 再回溯输入点
  • 为什么: 同一输入可能在多处输出(搜索词显示在结果页/日志/统计面板), 只堵输入点会漏网
  • 踩坑: 在表单提交处加过滤就以为安全, 数据从数据库取出渲染时未转义

3. 特殊字符组合是检测探针不是攻击载荷

  • 规则: 手工测试先提交 <>"'(); + 唯一标识符如 xss9527, 看源码中标识符前后是否被转义
  • 为什么: 直接提交 <script>alert(1)</script> 会被 WAF 拦截且无法定位过滤位置, 特殊字符能快速判断过滤强度
  • 踩坑: 用完整 payload 测试被拦后就认为无漏洞, 实际可能只是 WAF 规则而非代码层防御

4. 反射型 XSS 的危险在 URL 可传播不在持久化

  • 规则: 反射型标记为中危是因为需要诱骗点击链接, 但配合短链/钓鱼邮件传播速度不亚于存储型
  • 为什么: 一条带 payload 的 URL 通过社交工具群发, 受害规模可能超过单个存储型 XSS 的触发次数
  • 踩坑: 认为反射型”不持久”就不紧急修复, 忽略其在钓鱼场景的爆发力

5. DOM 型 XSS 绕过所有服务端过滤

  • 规则: 检测 DOM XSS 必须看前端 JS 如何处理 location.hash / document.referrer 等浏览器对象
  • 为什么: 数据从未发送到服务端, 所有服务端 WAF/过滤函数完全失效, 纯前端 innerHTML 赋值即触发
  • 踩坎: 后端日志里看不到攻击参数就认为安全, 实际 # 后的 hash 参数不会发送到服务器

6. 构造闭合是绕过过滤的核心技巧

  • 规则: 查看输出点的 HTML 上下文, 用引号/标签闭合原有结构再注入新标签
  • 为什么: 即使 <script> 被过滤, 闭合 <input value=" 后可用 " onclick="alert(1) 或 "><img src=x onerror=alert(1)> 绕过
  • 踩坑: 只测试 <script>alert(1)</script> 一种形式, 不分析输出点是在标签属性内还是标签体内

7. 存储型 XSS 的修复窗口极短

  • 规则: 发现存储型 XSS 后 1 小时内必须下线受影响功能或上全局输出转义
  • 为什么: 恶意脚本已写入数据库, 每次页面加载都触发, 管理员一旦中招攻击者立即获得持久后门
  • 踩坑: 按普通 bug 流程排期到下个迭代修复, 期间攻击者已批量收割 Cookie

8. 输出转义必须匹配上下文

  • 规则: HTML body 用 htmlspecialchars, JS 字符串内用 json_encode, URL 参数用 urlencode
  • 为什么: 在 <script>var name="<USER_INPUT>"</script> 中, HTML 转义无法防御 "; alert(1);// 这种 JS 语法闭合
  • 踩坑: 全站统一用一个 escapeHtml() 函数处理所有输出, 在 JS/CSS/URL 上下文中失效

9. CSP 是最后防线不是唯一防线

  • 规则: 配置 Content-Security-Policy 禁止 inline script, 但仍需在代码层做输出转义
  • 为什么: CSP 可被 <meta> 标签覆盖, 且老旧浏览器不支持, 只能作为纵深防御的一层
  • 踩坑: 加了 CSP 就不做输入输出过滤, 遇到 IE11 或 CSP bypass 技巧时全线崩溃

10. HttpOnly 只防 Cookie 窃取不防 XSS 本身

  • 规则: 给敏感 Cookie 加 HttpOnly 标记, 但不能因此降低 XSS 修复优先级
  • 为什么: XSS 仍可读取页面内容(CSRF Token/个人信息)、发起伪造请求、植入键盘记录器
  • 踩坑: 认为 Cookie 偷不走就不算严重漏洞, 忽略 XSS 的其他 10 种利用方式

11. 工具扫描的漏报率高于 60%

  • 规则: AWVS/AppScan 跑完后必须对所有输入输出点做人工验证
  • 为什么: 工具无法理解业务逻辑(如多步骤表单、需登录的接口), 且对 DOM XSS 检测能力弱
  • 踩坑: 扫描报告显示 0 漏洞就通过安全审计, 实际存储型 XSS 藏在需要特定角色才能访问的功能里

12. 黑名单过滤必败白名单也不保险

  • 规则: 禁止用正则删除 <script> 等关键词, 改用白名单允许特定 HTML 标签+属性组合
  • 为什么: <scr<script>ipt> / <svg onload=alert(1)> / <iframe src=javascript:alert(1)> 等绕过手法有上百种
  • 踩坑: 维护一个黑名单正则不断打补丁, 最终正则长达 500 字符仍被绕过
  • 例外: 纯文本场景(如日志)可用黑名单删除所有 <> 字符

13. 富文本编辑器是 XSS 重灾区

  • 规则: 使用 DOMPurify 等成熟库做服务端二次过滤, 不信任前端编辑器的过滤结果
  • 为什么: TinyMCE/CKEditor 的 XSS 过滤可被禁用或存在 0day, 且用户可能直接调 API 绕过编辑器
  • 踩坑: 集成富文本编辑器后认为它会自动防 XSS, 实际存储的 HTML 未经服务端验证

14. JSON 接口也会有 XSS

  • 规则: 返回 JSON 的接口也要检查是否被当作 HTML 解析(如 Content-Type 错误或前端 innerHTML 赋值)
  • 为什么: Content-Type: text/html + JSON 响应体会被浏览器当 HTML 渲染, 或前端 div.innerHTML = jsonData.msg 直接触发
  • 踩坑: 认为返回 JSON 就不存在 XSS, 忽略 Content-Type 配置错误和前端不安全的 DOM 操作

15. 测试账号要覆盖所有权限等级

  • 规则: 用普通用户/VIP 用户/版主/管理员等不同角色分别测试 XSS, 重点测高权限用户可见页面
  • 为什么: 某些输入点只有管理员能触发(如审核备注/系统配置), 这些才是攻击者的真正目标
  • 踩坑: 只用测试账号测前台功能, 管理后台的存储型 XSS 从未被发现直到被利用

🔥 5 秒必记 5 条

  1. 输出点比输入点重要 — 数据在哪渲染就在哪转义
  2. 管理员是 XSS 的真正目标 — 客户端攻击可转服务端沦陷
  3. DOM XSS 绕过所有后端防御 — 必须审计前端 JS 的 DOM 操作
  4. 存储型 XSS 发现后 1 小时内必须处理 — 每次加载都触发
  5. 工具扫描漏报率 >60% — 人工验证所有输入输出点不可省
