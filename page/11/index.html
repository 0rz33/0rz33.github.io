原始问题: [blog] XSS跨站脚本攻击

XSS 跨站脚本攻击防御与利用技能清单

场景占位: 攻击者向 注入脚本,受害者 浏览触发,窃取
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 把管理员当首要攻击目标而非普通用户

  • 规则: XSS 攻击优先瞄准管理员账户,利用其高权限作为跳板
  • 为什么: 管理员拥有文件管理、数据库操作等服务端权限,XSS 可借此从”客户端攻击”升级为”服务端控制”
  • 踩坑: 以为 XSS 只能偷 Cookie,忽略管理后台的 CSRF 配合利用
  • 例外: 目标是批量窃取普通用户凭证时,广撒网更高效

2. 输出点比输入点更关键

  • 规则: 先定位数据在哪里输出(HTML/JS/属性),再倒推输入点
  • 为什么: 同一输入在不同输出上下文需要不同闭合方式,输出决定 Payload 构造
  • 踩坑: 只盯着输入框测试,漏掉 URL 参数、HTTP Header、Cookie 等非表单输入源

3. 用”特殊字符+唯一标识”快速定位过滤规则

  • 规则: 提交 <>"'();--%00<UNIQUE_ID_12345>,在响应源码中搜索唯一标识
  • 为什么: 直接看哪些字符被转义/删除/编码,比盲目尝试 Payload 快 10 倍
  • 踩坑: 用常见 <script>alert(1)</script> 测试,被 WAF 拦截就放弃,实际可能只过滤了 script 关键字

4. 反射型 XSS 不等于”不危险”

  • 规则: 反射型虽需诱导点击,但配合短链、钓鱼邮件、水坑攻击仍是高危
  • 为什么: 分类”中危”是理论评级,实战中管理员点击恶意链接概率远超预期
  • 踩坑: 渗透报告写”仅反射型,危害有限”,客户因管理员被钓鱼导致数据泄露

5. 存储型 XSS 的持久化不止数据库

  • 规则: 检查日志文件、缓存系统、消息队列等所有持久化存储
  • 为什么: Payload 可能写入 Redis、ElasticSearch 日志,在管理后台日志查看页面触发
  • 踩坑: 只测试评论、留言板,漏掉错误日志展示、用户行为分析等后台功能

6. DOM XSS 绕过所有服务端过滤

  • 规则: 当输入直接被前端 JS 操作(innerHTML/eval/location.href)时,服务端过滤无效
  • 为什么: 数据流不经过服务端渲染,Payload 在浏览器本地执行
  • 踩坑: 看到服务端有完善 HTML 转义就认为安全,实际前端代码 div.innerHTML = location.hash.substr(1) 直接引入

7. 闭合语法比 Payload 功能更重要

  • 规则: 先构造闭合(跳出当前 HTML/JS 上下文),再考虑执行什么代码
  • 为什么: <input value="<USER_INPUT>"> 需要 "><script>,<script>var x='<USER_INPUT>'</script> 需要 ';alert(1)//
  • 踩坑: 复制网上 Payload 直接用,不分析输出点的语法结构

8. 手工测试必带 Burp Suite 而非浏览器插件

  • 规则: 用 Burp 拦截修改请求,观察原始响应,不依赖浏览器渲染
  • 为什么: 浏览器 XSS Auditor、CSP 会阻止执行,但漏洞仍存在;Burp 看到的是服务端真实输出
  • 踩坑: 在 Firefox Hackbar 测试无弹窗就判定无漏洞,实际是浏览器保护机制拦截

9. 工具扫描结果需人工验证闭合有效性

  • 规则: AWVS/AppScan 报告的 XSS 必须手工确认 Payload 是否真正闭合执行
  • 为什么: 扫描器只检测特征字符出现在响应中,不验证语法完整性,误报率 30%+
  • 踩坑: 直接把扫描器报告交付,客户复现失败质疑专业性

10. 输入点不只是可见表单

  • 规则: 测试 Referer、User-Agent、Cookie、X-Forwarded-For 等 HTTP 头
  • 为什么: 这些字段常被记录到日志、统计页面,在管理后台展示时触发存储型 XSS
  • 踩坑: 只测试页面上的输入框和 URL 参数,漏掉 HTTP 头注入

11. 单引号双引号都被过滤时用事件属性

  • 规则: 构造 <img src=x onerror=alert(1)> 或 <svg onload=alert(1)>
  • 为什么: 事件属性值可以不加引号,绕过引号过滤;标签闭合只需 >
  • 踩坑: 认为引号被过滤就无法注入,实际 HTML 属性有多种闭合方式

12. 测试时用唯一标识而非 alert(1)

  • 规则: Payload 用 alert(document.domain+'-<TIMESTAMP>') 或 console.log('<UNIQUE_ID>')
  • 为什么: 多人测试同一目标时区分是谁的 Payload;避免 alert 被拦截时误判
  • 踩坑: 所有人都用 alert(1),无法确认是自己触发还是别人的残留

13. CSP 存在时优先找 JSONP 劫持或 unsafe-inline

  • 规则: 检查 CSP 策略是否允许 unsafe-inline 或白名单中的 JSONP 端点
  • 为什么: 严格 CSP 会阻止内联脚本,但配置不当(如信任 CDN 域名)仍可利用
  • 踩坑: 看到 CSP 响应头就放弃,实际策略可能有 script-src 'unsafe-inline'

14. 反射型 XSS 的 URL 需编码伪装

  • 规则: 用短链服务、URL 编码、HTML 实体编码混淆 Payload
  • 为什么: 明文 <script> 在邮件、IM 中会被安全网关拦截或显示警告
  • 踩坑: 直接发送带 <script> 的长 URL,受害者看到就起疑

15. 输出在 JSON 中时需跳出字符串再闭合 script

  • 规则: 当输出在 <script>var data={"key":"<INPUT>"}</script> 时,用 "};alert(1);// 闭合
  • 为什么: 需要先用 " 跳出 JSON 字符串,再用 } 闭合对象,最后 ; 结束语句
  • 踩坑: 只用 </script><script>alert(1)</script>,不理解 JSON 语法导致失败

🔥 5 秒必记 5 条

  1. 输出点决定闭合方式,先看源码再构造 Payload
  2. 管理员是 XSS 的黄金目标,可升级为服务端攻击
  3. DOM XSS 绕过所有服务端过滤,重点审计前端 JS
  4. 用”特殊字符+唯一 ID”快速摸清过滤规则
  5. 工具扫描结果 30% 误报,必须手工验证闭合

决策速查(遇到 X 想 Y)

遇到 想
输入被 HTML 转义 检查前端 JS 是否直接操作(DOM XSS)
引号被过滤 用事件属性不加引号:<img src=x onerror=alert(1)>
script 关键字被过滤 用 <svg onload> <img onerror> 或大小写混淆

原始问题: [blog] VIM

Vim 编辑器核心技能点清单

场景占位: 编辑 , 修改 配置, 查找
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 默认进入命令模式,所有操作从这里开始

  • 规则: 打开文件后处于命令模式,按 i/a/o 进入编辑模式,按 : 进入末行模式,按 Esc 回命令模式
  • 为什么: 新手最大困惑是”为什么按键没反应” — 因为在命令模式下字母是快捷键不是输入字符
  • 踩坑: 在命令模式下狂按字母想输入内容,结果触发了删除/复制等操作把文件改乱
  • 例外: vim -R <FILE> 只读模式下无法进入编辑模式

2. 用 dd 剪切而非删除,删除的内容自动进剪贴板

  • 规则: dd 删除当前行并放入剪贴板,p 粘贴,5dd 删除 5 行
  • 为什么: Vim 没有”纯删除”概念,所有删除都是剪切,这是多数编辑器不同的设计
  • 踩坑: 用 dd 删除后又 yy 复制别的内容,导致刚删的东西被覆盖无法找回

3. 末行模式替换必须理解 % 和 g 的组合含义

  • 规则: :s/old/new/ 只替换当前行第一个,:%s/old/new/g 替换全文所有
  • 为什么: % 表示全文范围,g 表示行内全局,缺一个都达不到”全部替换”效果
  • 踩坑: 用 :%s/old/new/ 以为能全部替换,结果每行只替换了第一个匹配
  • 例外: :5,10s/old/new/g 只替换 5-10 行

4. 撤销用 u,重做用 Ctrl+r,不是 Ctrl+z

  • 规则: 命令模式下按 u 撤销,Ctrl+r 重做(redo)
  • 为什么: Ctrl+z 在 Vim 里是挂起进程(放到后台),不是撤销,新手常按错导致 Vim “消失”
  • 踩坑: 按 Ctrl+z 后终端回到 shell,以为 Vim 崩溃了,实际用 fg 可恢复
  • 例外: :earlier 4m 可回到 4 分钟前的状态,比逐次 u 更高效

5. 强制退出用 :q!,保存退出用 :wq,别混用 :x

  • 规则: :q! 不保存强制退出,:wq 保存后退出,:x 仅在有修改时保存退出
  • 为什么: :x 和 :wq 行为不同 — :x 不会更新文件时间戳如果没修改,影响 Makefile 等依赖时间戳的工具
  • 踩坑: 用 :wq 退出未修改的文件,导致文件 mtime 更新触发不必要的重新编译

6. 行首用 ^ 跳到第一个非空字符,0 才是绝对行首

  • 规则: ^ 跳到行首第一个非空白字符,0 跳到行首第 0 列,$ 跳到行尾
  • 为什么: 代码编辑时 ^ 更实用(跳过缩进),但配置文件有时需要 0 定位到注释符 #
  • 踩坑: 在有缩进的代码里按 0 后按 i 插入,结果在缩进前插入破坏了格式

7. 分屏后用 Ctrl+w 前缀操作,不是 Ctrl+s/v

  • 规则: :sp 横向分屏,:vsp 纵向分屏,Ctrl+w 后按 hjkl 切换窗口,Ctrl+w c 关闭当前窗口
  • 为什么: Ctrl+w 是 Vim 窗口操作的统一前缀,所有分屏操作都从这里开始
  • 踩坑: 按 Ctrl+w 后停顿超过 1 秒,Vim 会等待下一个按键,新手以为卡死了
  • 例外: Ctrl+w w 循环切换窗口,比记忆 hjkl 方向更快

8. 搜索用 / 向下找,? 向上找,n 下一个,N 反向

  • 规则: /pattern 向下搜索,?pattern 向上搜索,n 跳到下一个匹配,N 跳到上一个
  • 为什么: n 的方向取决于你用 / 还是 ?,不是固定”向下”,这是反直觉的
  • 踩坑: 用 / 搜索后按 N 以为是”上一个”,结果是反向(向上)继续找,跳过了下面的匹配

9. 复制整行用 yy,复制到行尾用 y$,不是选中后复制

  • 规则: yy 复制当前行,5yy 复制 5 行,y$ 复制到行尾,p 粘贴
  • 为什么: Vim 的复制是基于动作(motion)而非选区,y 后面跟移动命令决定复制范围
  • 踩坑: 想复制半行内容,用 yy 复制了整行,粘贴时多出换行符
  • 例外: 可视模式下 v 选中后 y 复制,但效率低于直接用 motion

10. 显示行号用 :set nu,永久生效需写 ~/.vimrc

  • 规则: :set nu 临时显示行号,:set nonu 关闭,写入 ~/.vimrc 永久生效
  • 为什么: 末行模式的 set 命令只在当前会话有效,关闭文件后失效
  • 踩坑: 每次打开文件都要 :set nu,不知道可以写配置文件

11. 多文件编辑用 :bn/:bp 切换,不是关了重开

  • 规则: vim <FILE1> <FILE2> 打开多文件,:bn 切换到下一个,:bp 切换到上一个,:files 查看列表
  • 为什么: Vim 的 buffer 机制允许同时打开多个文件在后台,比反复 :q 再 vim 高效
  • 踩坑: 修改了 未保存就 :bn,Vim 会报错阻止切换,需 :w 或 :set hidden 允许

12. 替换单个字符用 r,连续替换用 R 进入替换模式

  • 规则: r 后按新字符替换光标处一个字符,R 进入替换模式连续覆盖输入,Esc 退出
  • 为什么: r 不进入编辑模式,替换后自动回命令模式,改一个字符最快
  • 踩坑: 用 i 删除再输入来”替换”,多按了 3 个键

13. 翻屏用 Ctrl+f/b,翻半屏用 Ctrl+d/u

  • 规则: Ctrl+f 向下翻整屏,Ctrl+b 向上翻整屏,Ctrl+d/u 翻半屏
  • 为什么: 翻半屏时光标保持在屏幕中间,上下文不丢失,查看日志时更实用
  • 踩坑: 只知道 PgDn/PgUp,不知道 Ctrl+d/u 可保留部分上下文

14. 执行外部命令用 :!<COMMAND>,不用退出 Vim

  • 规则: :!ls 执行 shell 命令,:r !date 把命令输出插入到当前位置
  • 为什么: 编辑配置文件时可以 :!systemctl restart <SERVICE> 直接重启服务验证
  • 踩坑: 用 Ctrl+z 挂起 Vim 切到 shell 执行命令再 fg,多了 2 步操作

15. 分屏尺寸调整用 Ctrl+w = 均分,Ctrl+w +/- 微调

  • 规则: Ctrl+w = 让所有窗口等高/等宽,Ctrl+w 10+ 增加 10 行高度
  • 为什么: 对比查看日志时需要调整窗口大小,默认分屏可能一个太小看不清
  • 踩坑: 不知道能调整尺寸,手动关了重新 :sp 试图改变比例

🔥 5 秒必记 5 条

  1. 打开文件在命令模式,按 i 才能输入,按 Esc 回命令模式
  2. :wq 保存退出,:q! 不保存强制退出,别按 Ctrl+z
  3. dd 是剪切不是删除,p 粘贴,u 撤销,Ctrl+r 重做
  4. :%s/old/new/g 全文替换,缺 % 只替换当前行,缺 g 每行只替换第一个
  5. /pattern 搜索,n 下一个,:set nu 显示行号

遇到 想
按键没反应 按 Esc 回命令模式,再按 i 进入编辑模式
想全部替换 :%s/old/new/g 四个符号缺一不可
Vim “消失”了 可能按了 Ctrl+z,输入 fg 恢复

[expanded] [blog] vue2 大文件上传component(做成组件)

原始问题: [blog] vue2 大文件上传component(做成组件)

前端大文件分片上传组件实现技能清单

场景占位: 上传到 ，文件 MD5 用 ，分片索引用
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 批量上传必须串行校验每个文件的 MD5，不能并行

  • 规则: 用 for...of 循环逐个计算文件 MD5，不能用 forEach 或 map
  • 为什么: MD5 计算是异步操作，并行会导致内存爆炸（多个大文件同时读入内存）且无法保证上传顺序，串行能控制内存峰值在单文件大小
  • 踩坑: 用 files.forEach(async file => await getMd5()) 会立即触发所有文件读取，浏览器直接卡死
  • 例外: 小文件（<50MB）且数量少（<5个）可以并行

2. 文件唯一标识必须用”业务键+文件属性”混合 MD5，不能只用文件内容 MD5

  • 规则: md5(uploadkey + name + type + lastModifiedDate + size) 生成 uniqueFileName
  • 为什么: 纯文件内容 MD5 无法区分同一用户上传同一文件的不同批次，会导致秒传逻辑误判（上次上传失败的文件被当作已完成）
  • 踩坑: 只用文件 MD5 会让用户重新上传失败文件时直接跳过，实际服务端没有完整文件
  • 例外: 全局去重场景（如公共资源库）只需文件内容 MD5

3. 分片上传进度必须分两层计算：分片内字节进度 + 已完成分片数

  • 规则: progressPercent = (upchunk / blockNum * 100) + (chunkprogress.percent / blockNum)
  • 为什么: 只统计已完成分片会导致进度条长时间卡在某个百分比（当前分片上传中），用户误以为卡死
  • 踩坑: 直接用 upchunk / blockNum 会让 100MB 文件分 10 片时，每片上传 10 秒进度条都不动
  • 例外: 分片极小（<1MB）时可以忽略分片内进度

4. 文件类型校验必须在切片前做，不能在切片后或上传时做

  • 规则: 在 add() 方法最开始用 mimeTypes.indexOf(ext) 校验并 return
  • 为什么: 切片是 CPU 密集操作，大文件切片可能耗时数秒，校验失败会浪费计算资源且用户体验差（等了半天才提示格式错误）
  • 踩坑: 在切片后校验会让用户选择 1GB 文件后等 5 秒才看到”格式不支持”
  • 例外: 需要读取文件头魔数校验真实格式时必须在切片后

5. 秒传校验必须在服务端做文件级 MD5 比对，前端只做去重

  • 规则: 前端用 files.findIndex(item => item.md5 === fileMd5) 只防止重复添加，真正秒传逻辑在服务端返回”文件已存在”
  • 为什么: 前端无法知道服务端是否真的有完整文件，只能防止同一批次重复上传；服务端可能因存储迁移/清理导致文件丢失
  • 踩坑: 前端判断”MD5 存在就跳过”会导致服务端文件被误删后用户无法重新上传
  • 例外: 纯前端应用（如 IndexedDB 存储）可以前端做秒传

6. 视频时长获取必须用 Promise 包装 loadedmetadata 事件，不能用 async/await 直接读

  • 规则: 创建 video 元素，监听 loadedmetadata 事件，在回调中 resolve(video.duration)
  • 为什么: video.duration 只有在元数据加载完成后才有值，直接读取是 NaN；大视频文件元数据加载可能需要数秒
  • 踩坑: 直接 const duration = video.duration 永远得到 NaN，因为 src 赋值后元数据还没加载
  • 例外: 已知格式良好的小视频（<10MB）可以加 setTimeout 轮询

7. 分片大小必须根据文件大小动态调整，不能固定值

  • 规则: chunkSize = file.size < 100MB ? 2MB : 5MB，超大文件（>1GB）用 10MB
  • 为什么: 小文件用大分片会导致分片数过少无法利用并发；大文件用小分片会导致请求数爆炸（1GB 文件 2MB 分片需 500 个请求）
  • 踩坑: 固定 2MB 分片上传 5GB 文件会产生 2500 个 HTTP 请求，浏览器并发限制导致上传极慢
  • 例外: 服务端强制要求固定分片大小时（如 OSS 分片上传）

8. 断点续传必须存储”已上传分片索引数组”，不能只存已上传数量

  • 规则: 用 uploadedChunks: [0,1,3,5] 记录，不能只用 upchunk: 4
  • 为什么: 网络不稳定时分片可能乱序成功（第 2 片失败但第 3 片成功），只记数量会导致续传时重复上传已成功分片
  • 踩坑: 只用计数器会让第 2 片失败后，续传时从第 5 片开始（以为前 4 片都成功了），实际第 2 片丢失
  • 例外: 服务端强制顺序上传且会拒绝乱序分片时

9. 取消上传必须同时取消 XHR 请求和清理 FileReader，不能只清状态

  • 规则: 保存 xhr 引用调用 xhr.abort()，同时 fileReader.abort() 并清空 fileChunks 数组
  • 为什么: 只改状态不取消请求会导致后台继续上传浪费带宽；FileReader 不清理会持续占用内存（大文件切片会产生大量 Blob 对象）
  • 踩坑: 点取消后进度条停了但网络面板显示还在上传，内存持续增长最终崩溃
  • 例外: 使用 Fetch API 时用 AbortController 替代 xhr.abort()

10. 组件销毁前必须清理所有 Blob URL 和取消上传，不能依赖 GC

  • 规则: 在 beforeDestroy 钩子中遍历 files 调用 URL.revokeObjectURL(file.cover) 和取消上传
  • 为什么: Blob URL 不会自动释放，会导致内存泄漏；未取消的上传会在组件销毁后继续执行回调报错
  • 踩坑: 切换路由后内存不释放，上传 10 个大文件后切换页面内存占用还是 2GB
  • 例外: 单页应用且组件永不销毁时可以不清理

11. 进度条颜色必须根据状态动态变化，不能固定色

  • 规则: customColor = status === '上传中' ? '#409EFF' : status === '失败' ? '#F56C6C' : '#67C23A'
  • 为什么: 固定颜色无法让用户快速识别上传状态，尤其批量上传时需要一眼看出哪些失败
  • 踩坑: 所有进度条都是蓝色，用户以为都在上传，实际有 3 个已经失败了
  • 例外: 设计规范强制单一颜色时

12. 文件列表必须支持单个删除且删除时取消对应上传，不能只清空全部

  • 规则: deleteFile(index) 中先调用 files[index].cancel() 再 files.splice(index, 1)
  • 为什么: 批量上传时用户可能只想删除某个失败文件重新添加，清空全部会导致其他正在上传的文件也被中断
  • 踩坑: 删除一个文件后其他文件的索引错乱，导致删除第 2 个文件实际删了第 3 个
  • 例外: 明确只支持”全部取消”的简化场景

13. 上传完成后必须校验服务端返回的文件大小，不能只看 HTTP 200

  • 规则: 对比 response.fileSize === file.size，不一致时标记为失败并重传
  • 为什么: HTTP 200 只代表请求成功，不代表文件完整；网络中断、代理截断等会导致服务端收到不完整文件但返回 200
  • 踩坑: 上传显示成功但播放视频时发现只有前半段，服务端实际只收到 60% 数据
  • 例外: 服务端强制校验文件完整性且会返回 4xx 错误时

14. 分片上传失败必须重试当前分片，不能直接标记整个文件失败

  • 规则: 单个分片失败时重试 3 次，3 次都失败才标记文件状态为”失败”
  • 为什么: 网络抖动很常见，单次失败不代表文件无法上传；直接失败会让用户重新上传整个文件浪费已上传分片
  • 踩坑: 上传 1GB 文件到 95% 时一个分片失败，整个文件标记失败，用户重新上传又从 0 开始
  • 例外: 服务端返回 4xx 业务错误（如文件格式不支持）时不应重试

🔥 5 秒必记 5 条

  1. 批量上传必须串行计算 MD5，并行会内存爆炸
  2. 进度 = 已完成分片占比 + 当前分片内进度占比，缺一不可
  3. 文件唯一标识用业务键+属性混合 MD5，不能只用内容 MD5
  4. 断点续传存已上传分片索引数组，不能只存数量
  5. 组件销毁前必须清理 Blob URL 和取消上传，不能依赖 GC

Vue2 vs Vue3 核心差异与迁移技能点

场景占位: 组件用 、,数据用 、
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 生命周期钩子在 Vue3 setup 中需显式导入且改名

  • 规则: Vue3 的 setup() 替代 beforeCreate/created,其他钩子加 on 前缀且需从 vue 导入
  • 为什么: setup 在组件实例创建前执行,此时 this 不可用,Vue3 用函数式 API 替代 Options API 避免 this 绑定混乱
  • 踩坑: 在 setup 里写 this.xxx 永远是 undefined,mounted 要改成 onMounted 否则不触发
  • 例外: Vue3 仍支持 Options API 写法,可混用但不推荐(会导致逻辑分散)

2. 响应式初始化从 data() 改为 ref/reactive 且必须 .value 访问

  • 规则: Vue3 用 ref(基本类型) 或 reactive(对象) 替代 data(),ref 在 script 中访问需 .value
  • 为什么: Vue2 的 Object.defineProperty 无法监听新增属性,Vue3 用 Proxy 重写响应式系统,ref/reactive 是显式声明响应式的入口
  • 踩坑: template 中 ref 自动解包不需 .value,但 script 中忘记 .value 会拿到 RefImpl 对象导致判断失效
  • 例外: reactive 对象的属性访问不需 .value,但解构会丢失响应式(需用 toRefs 包裹)

3. 父子通信从 prop+$emit 改为 defineProps+defineEmits 宏

  • 规则: Vue3 setup 中用编译时宏 defineProps/defineEmits 替代 props 选项和 this.$emit
  • 为什么: 宏在编译阶段处理,无需导入且提供更好的 TypeScript 类型推导,避免运行时 this 查找开销
  • 踩坑: defineProps 返回的是响应式对象但不能解构(会丢失响应性),defineEmits 返回函数直接调用即可
  • 例外: Options API 写法仍用 props 配置项和 this.$emit

4. ref 模板引用从字符串改为同名变量声明

  • 规则: Vue3 中 ref=”“ 需在 setup 中声明 const = ref(null) 并返回
  • 为什么: Vue2 的 this.$refs 依赖运行时字符串查找,Vue3 编译时绑定变量提升性能且类型安全
  • 踩坑: 忘记在 setup return 中暴露 ref 变量会导致绑定失败,v-for 中的 ref 在 Vue3 会自动收集成数组
  • 例外: 组合式 API 的 ref 在 onMounted 后才有值,beforeMount 时仍是 null

5. watch 从配置对象改为独立导入函数且默认惰性执行

  • 规则: Vue3 的 watch 需从 vue 导入,默认不立即执行(需配置 immediate: true)
  • 为什么: Vue2 的 watch 选项在组件初始化时就建立依赖,Vue3 按需调用 watch 函数减少初始化开销
  • 踩坑: watch ref 对象需传入 getter 函数 () => .value,直接传 ref 监听不到变化
  • 例外: watchEffect 会立即执行且自动追踪依赖,适合副作用场景

6. 渲染函数从 $mount 改为 createApp 链式调用

  • 规则: Vue3 用 createApp().mount(‘‘) 替代 new Vue({ el })
  • 为什么: Vue2 的全局 Vue 实例会污染原型链,Vue3 的应用实例隔离避免多应用冲突
  • 踩坑: Vue3 移除了 $mount 的返回值链式调用,必须先 createApp 再 mount,且 mount 返回根组件实例而非应用实例
  • 例外: 测试环境可以不 mount 直接操作虚拟 DOM
