基础原理

演变历史


k8s的演变过程：首先从传统的服务–>虚拟机部署–>容器部署–>k8s

不是新轮子,而是运维自动化的集大成者:

  • 自动调度(把Pod 放到合适的机器)
  • 自我修复(Pod 挂了自动重建)
  • 服务发现&负载均衡(Service 自动分配IP和DNS)
  • 滚动更新&回滚(零停机发布)
  • 密钥&配置管理(ConfigMap / Secret)

对研发的意义:

  • 不再关心“部署在哪台机器”,只关心“我要几个副本、暴露什么端口、用什么配置”
  • 环境一致性:开发、测试、生产都跑在同一个抽象层上.

!!!1.32.x 版本各大平台开始支持

Kubernetes 提供能力

服务发现和负载均衡

Kubernetes 可以使用 DNS 名称或自己的 IP 地址来暴露容器。如果进入容器的流量很大, Kubernetes 可以负载均衡并分配网络流量, 从而使部署稳定。

自我修复

Kubernetes 将重新启动失败的容器、替换容器、杀死不响应用户定义的运行状况检查的容器,并且在准备好服务之前不将其通告给客户端。

自动完成装箱计算

你为 Kubernetes 提供许多节点组成的集群,在这个集群上运行容器化的任务。你告诉 Kubernetes 每个容器需要多少 CPU 和内存 (RAM), Kubernetes 可以将这些容器按实际情况调度到你的节点上,以最佳方式利用你的资源。

自动部署和回滚

你可以使用 Kubernetes 描述已部署容器的所需状态,它可以以受控的速率将实际状态更改为期望状态。例如,你可以自动化 Kubernetes 来为你的部署创建新容器,删除现有容器并将它们的所有资源用于新容器。

存储编排

Kubernetes 允许你自动挂载你选择的存储系统,例如本地存储、公共云提供商等。

密钥与配置管理

Kubernetes 允许你存储和管理敏感信息,例如密码、OAuth 令牌和 SSH 密钥。你可以在不重建容器镜像的情况下部署和更新密钥和应用程序配置,也无需在性样配置由星管密钥。

控制平面(control plane)：

集群🧠(比如调度) |master节点 以及检测和响应集群事件(例如资源不足，自动扩缩容)

节点平面(node plane)：

运行实际的负载机器

  • Mater 节点主要有以下组件：

    • kube-apiserver：负责对外暴露 Kubernetes API。
    • etcd：作为保存 Kubernetes 所有集群数据的后台数据库。
    • kube-scheduler：在适当的时候进行调度决策，让 Pod 在合适的节点上创建运行。
    • kube-controller-manager：负责监控调整调整集群的状态，比如故障检测、自动扩展、滚动更新等

  • Node 节点有以下组件：

    • kubelet：主要负责执行、监控由调度器分配的 Pod，相当于是 Master 在每个 Node 节点上的代理。保证 Pod 的运行状态与目标状态一致。
    • kube-proxy：k8s 在每个节点上的网络代理，负责为 Service 提供集群内部的服务发现和负载均衡。

核心架构与稳定性基础

设计核心是“高可用+分布式”:
控制平面(Master)的所有核心组件(Api-server、Etcd、Controller Manager、Scheduler) 都通过集群化、主从选举、负载均衡,避免单点故障,保证“大脑不宕机”。
业务流量通过多层负载均衡+节点群,保证用户能稳定访问业务,且业务能横向扩展。
架构能支撑大规模、高可靠的生产级业务,是企业级 Kubernetes 集群的典型设计思路。

控制平面组件（Control Plane）

组件 功能 类比 研发需知
kube-apiserver 集群所有操作的唯一入口（kubectl / controller / scheduler 都走它） 前台接待 ❗ 出问题 = 整个集群不可操作；所有鉴权、校验、写入都在这里
etcd 分布式键值数据库，存储所有集群状态 中央账本 ❗ 数据丢失 = 集群逻辑性死亡；必须定期备份、谨慎扩容
kube-scheduler 决定新 Pod 调度到哪台 Node 调度员 可通过 taint / toleration、nodeSelector、affinity 干预
kube-controller-manager 运行各种控制器（Deployment / Node / Job 等） 监工 核心职责：确保 实际状态 = 期望状态，问题多为“反复拉起/杀死”

工作节点组件（Worker Node）

组件 功能 类比 研发需知
kubelet Node 代理，负责 Pod 生命周期和健康检查 执行者 / 联络员 Node 宕机或 kubelet 异常 → 该节点上的 Pod 全部不可用
kube-proxy 维护网络规则，实现 Service 虚拟 IP 网络向导 依赖 iptables / ipvs；Service 不通时重点排查对象
Container Runtime
(containerd / CRI-O / Docker*)		 实际运行容器的底层组件 搬运工 是容器能跑起来的基础；K8s 通过 CRI 与其交互

相互之间的通讯

  • 每个Node节点都会启动kubelet进程, 处理Master节点下发到本节点的任务, 管理 Pod和其中的容器。
  • kubelet会在API Server上注册节点信息,定期向Master汇报节点资源使用情况,并通过cAdvisor监控容器和节点资源,可以把kubelet理解成Server/Agent架构中的agent,
  • kubelet是Node上的 pod管家。

Scheduler调度器

1. 核心定义与角色

Scheduler 负责 Pod 的调度，在整个系统中起着 “承上启下” 的作用：

  • 承上：负责接收由 Controller Manager 创建的新 Pod，并为其选择一个合适的 Node（节点）。
  • 启下：调度完成后，目标 Node 上的 kubelet 接管 Pod 的生命周期，负责具体的启动与维护。

2. Pod 分配的核心流程

当一个 Pod 需要被调度时，kube-scheduler 会经历以下五个关键步骤：

  1. 监听待调度 Pod
    通过 kube-apiserver 持续监听（Watch）处于 Pending 状态、且未指定 Node 的 Pod。

  2. 过滤节点（预选 / Predicates）
    排除不符合 Pod 运行条件的节点，例如：

    • 资源不足（CPU / 内存等）
    • 节点标签不匹配
    • 污点与容忍度不满足

  3. 节点打分（优选 / Priorities）
    对通过预选的节点进行评分，综合多种调度策略，选出最优的节点。

  4. 绑定节点（Bind）
    将选定的 Node 信息写入 Pod 对象，并更新到 etcd 中。

  5. kubelet 启动 Pod
    目标节点的 kubelet 监听到调度结果后，在本地拉取镜像并启动容器，正式运行 Pod。

深度解析Scheduler

步骤 1 & 2：启动阶段

步骤 1：Pod 进入「待调度」状态
  • 新创建的 Pod 被写入 API Server
  • Pod 状态为 Pending
  • 尚未分配 spec.nodeName
步骤 2：调度器监听并选择待调度 Pod
  • kube-scheduler 通过 Watch 机制 监听 API Server
  • 获取所有处于 Pending 且未指定 Node 的 Pod
  • 将其加入调度队列，准备调度

步骤 3：预选（Filtering / Predicates）

目标：过滤不符合 Pod 运行要求的节点

常见过滤规则（Predicates）包括：

  • 资源充足性

    • 检查节点剩余 CPU、内存等资源
    • 是否满足 Pod 的 resources.requests

  • 节点标签匹配

    • 若 Pod 配置了 nodeSelector 或 nodeAffinity
    • 节点必须包含对应标签

  • 污点与容忍度（Taints & Tolerations）

    • 检查 Pod 是否能够容忍节点上的污点

  • 端口与存储兼容性

    • hostPort 是否已被其他 Pod 占用
    • 请求的持久化存储卷（PV）是否能在该节点挂载

  • 节点状态

    • 节点必须处于 Ready 状态
    • 不存在 MemoryPressure、DiskPressure 等异常

步骤 4：优选（Scoring / Priorities）

目标：为可行节点打分排序，选出最优节点

主要评分策略包括：

  • 资源均衡性

    • 倾向于让 CPU、内存使用更加均衡
    • 例如：BalancedResourceAllocation

  • 镜像本地性

    • 节点已存在所需容器镜像时获得加分
    • 减少镜像拉取时间，提高启动速度

  • Pod 亲和与反亲和性

    • podAffinity：希望某些 Pod 部署在一起
    • podAntiAffinity：避免某些 Pod 部署在同一节点

  • 节点负载

    • 优先选择 Pod 数量较少、资源更空闲的节点

  • 综合评分

    • 所有策略计算加权总分
    • 得分最高的节点成为最终候选

步骤 5：绑定（Binding）

  • Scheduler 选定最终节点
  • 将节点名称写入 Pod 的 spec.nodeName
  • 通过 API Server 更新 Pod 对象
  • 调度完成

步骤 6：kubelet 启动 Pod

目标节点上的 kubelet 开始接管 Pod 生命周期：

  • 拉取镜像

    • 下载 Pod 所需的容器镜像

  • 创建并启动容器

    • 通过容器运行时（如 containerd、Docker）

  • 持续监控

    • 监控 Pod 和容器运行状态
    • 向 API Server 汇报健康状态与资源使用情况

  • 发现 Pending 状态的 Pod

2. 核心调度阶段

目标：过滤不符合 Pod 运行要求的节点

  • 资源充足性

    • 检查节点 CPU、内存

  • 节点标签匹配

    • 校验 nodeSelector 或 nodeAffinity

  • 污点与容忍度（Taints & Tolerations）

  • 节点状态

最基础的核心对象

Kubernetes 的能力由多种 API 对象组合而成，以下是最基础的构建块：

1. 基础设施与隔离

  • Node

    • 工作节点（物理机或虚拟机）
    • Pod 的 “硬件载体”

  • Namespace

    • 逻辑隔离资源
    • 常用于区分开发 / 测试 / 生产环境

2. 应用与配置

  • Pod

    • K8s 最小部署单元
    • Pod 内容器共享网络与存储

  • ConfigMap / Secret

    • 配置管理，实现配置与 Pod 解耦
    • ConfigMap：非敏感配置（如数据库地址）
    • Secret：敏感信息（如密码、Token）

3. 存储与网络

  • PV / PVC / StorageClass

    • 持久化存储三件套
    • PV：实际存储资源
    • PVC：Pod 的存储申请
    • StorageClass：存储类型（如 SSD），支持动态分配

  • Service / Ingress

    • 服务发现、服务暴露与负载均衡

4. 管理与限制

  • ServiceAccount

    • 为 Pod 中的应用提供身份认证
    • 解决“我是谁、我能做什么”

  • ResourceQuota

    • 限制 Namespace 级别资源总量
    • 防止 CPU、内存被单一业务耗尽

    • 高端（干洗+配送）：主打精致、快捷

  • 调研竞争对手：
    • 收费标准（按件/按公斤）
    • 月客户量、服务品类（洗衣、烘干、熨烫）
  • 估算人流量 × 客单价 = 预期月基础收入（做盈亏平衡模型）

创业思维

2026-09-22 创业

找到个人商业路径：从副业起步到系统化创业

  1. 边工作边探索，用副业试水
  2. 独立的“小业务”其实可以共享我的个人品牌资源和受众池，相互促进。

可操作性强的建议：从副产品到被动收入

  1. 将副业作为起点
  2. 先用最小成本测试市场反应
  3. 在营销方面，作者介绍了**“链式传播”的概念，即注重让用户帮你二次传播（例如转发分享），实现滚雪球式增长
  4. 尽量避开与大公司正面交锋，而是寻找小众且刚需的细分市场，以差异化的定位胜出
  5. 反思自己的项目：与其跟风拥挤的热门领域，不如发挥个人专长，找到尚未被满足的特殊需求，这样才能减少竞争压力，用巧劲取胜。

创业精神与价值观：小而美、优雅独立

  1. “小规模、可持续”，不盲目追求公司做大做快，而是专注把业务做精做好，维持精巧的规模以获取自由
  2. 做让自己和用户都由衷认可的事，财富将自然而然地到来
  3. 持续学习与分享，乐于分享、共同成长

新的认识与激励：从螺丝钉到超级个体的信心

  1. 个人完全可以成为一个“小而全”的公司，最低可行利润，先让副业收入达到养活自己
  2. 迈出体制、独立生存就是胜利的开始
  3. 副业就是最好的练兵场
