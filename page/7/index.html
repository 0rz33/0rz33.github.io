阳台生态循环系统完整方案

🌱 阳台生态循环系统完整方案（低成本 · 低维护 · 无异味）

目标：构建家庭阳台微型生态闭环

  • 厨余 → 肥料 | 肥料水
  • 鱼缸 → 植物营养水
  • 水培 + 土培共存
  • 长期稳定、可持续

肥料获取-厨房废料

获取方法

  1. 多准备土壤
  2. 每次吃饭前，将果渣、菜渣丢进肥料桶
  3. 在废料上铺一层土
  4. 重复：丢果渣/菜渣 → 铺土，直至桶满

桶的准备

  • 桶A：储存土壤
  • 桶B：堆肥桶，用于发酵厨房废料

初阶土培

适合种植：蒜

步骤

  1. 水培阶段
  • 果核 - 清理核上的果肉残渣避免菌种繁殖污染幼苗的水质
  • 根系 - 先用水培方式培育出蔬菜根系
  1. 转入土壤
  • 将水培成苗的蔬菜移入土壤
  • 适量添加自制肥料，提高营养

高阶土培

适合种植：辣椒

  • 记得一定要水

Sealos -> CasaOS -> Home Assistant

SeaOS 是一个专为家庭设计的中控系统（Home Control System / Smart Home Hub），核心目标是把家里的各种智能设备、存储、网络服务整合在一个平台上，实现统一管理和自动化

  • 跨设备支持：可以控制智能灯、智能门锁、摄像头、传感器等。
  • 家庭自动化：支持条件触发、场景设置、定时任务。
  • 本地化存储：可与 NAS 或家庭服务器结合，避免云端依赖。
  • 开放接口：可以与第三方系统或自建程序对接。
所要实现的功能 AI智能管家

AI Agent

层次,核心组件,功能描述,对应你的 Agent OS 模块建议

  1. 接入层 (API),REST / WebSocket,接收自然语言指令（如：“去 GitHub 帮我点个 Star”）。,internal/adapter/http.go
  2. 调度层 (Orchestrator),Task Manager,任务拆解：将大目标拆分为“打开链接、点击、提取、返回”等原子步骤。,internal/core/kernel.go
  3. 执行层 (Executor),Playwright / Chromium,物理操作：真实的浏览器内核，处理页面渲染、JS 执行、Cookie 持久化。,internal/tools/browser/
  4. 理解层 (Cognition),LLM (Ollama / GPT),语义决策：将清洗后的 HTML/DOM 结构喂给模型，让模型决定下一步的动作。,internal/llm/ollama.go

观察 (Observe) -> 思考 (Think) -> 决策 (Decide) -> 执行 (Act) 的闭环。

  • Observe (观察)：提取当前页面的可交互元素列表（Button, Input, Link）。
  • Think (思考)：LLM 根据当前任务目标分析这些元素。
  • Decide (决策)：LLM 输出标准格式的操作指令（例如：{“action”: “click”, “selector”: “#submit-btn”}）。
  • Act (执行)：调用 Playwright 执行动作并等待页面刷新，进入下一轮循环。

初级AI管家

功能要求

外出/在家场景

  1. HomeAssistant 控制室内智能家电
  2. 手机容量不足 可以存储图片在家里
  3. 可云办公 上传下载
  4. 监控植物系统
  5. (在家场景)可呼叫语音助手

硬件需求

树莓派 4B

  • 系统： RPi OS

  • 核心功能：

    • HomeAssistant（家庭自动化核心中枢）
    • MQTT / Zigbee2MQTT 网关
    • 本地语音助手（控制家居 + 调用 AI）
    • Nextcloud（轻量云盘 → 云办公 / 文件同步）
    • AI 前端代理：将语音/文本请求转发到 PC 工作站 AI 模型
    • 控制全家 Zigbee / WiFi 智能家电
    • 外出时通过 VPN 访问树莓派，统一管理家庭设备

  • 需要外壳（配件）：

    • 3D 打印外壳：JVC3100r
    • 显示触摸屏 + 键盘｜（AI 管家界面）
    • pi4 respeaker（声控） + USB 音频（声控 喇叭 ）｜ 已具备：喇叭 + 麦克风（用于语音助手）

PC AI 工作站

  • 系统： Linux / Windows（推荐 Linux）
  • 核心功能：
    • GPU 推理（大模型计算核心）
    • 托管私有大模型（LLM / Vision / TTS / ASR / RVC）
    • 接收树莓派发来的 AI API 请求
    • 为 HomeAssistant 提供视觉识别、自动化推理
    • 家庭主要大文件存储区：
      • 素材
      • 数据
      • AI 模型
      • 多媒体文件
    • 高性能 Worker：处理 AI 任务
    • 可被 HomeAssistant 调用执行识图、识物、自动化联动
  • 需要外壳（配件）：
    • GP02A半身像1
    • GP02A半身像2
    • 最好能抽拉出主机
    • ITX主板
  • 硬件需求：
    • 强力 GPU（RTX 4070 / 4080 / 4090 或更高）
    • 至少 32GB RAM
    • NVMe SSD（1TB–2TB，模型加载更快）
    • 良好散热系统
    • 稳定供电

架构

步骤指南

1️⃣ 树莓派 4B —— 家庭中控

  1. 硬件组装

    • 使用 JVC3100r 3D 打印外壳
    • 安装小型显示屏（作为 AI 管家界面）
    • 接入喇叭 + 麦克风（语音助手）
    • 可选：风扇 / 铜片散热

  2. 系统安装

    • 安装 RPi OS（64 位版本，推荐 Raspberry Pi OS Lite + GUI 可选）
    • 配置网络：静态 IP / DHCP 保留，确保在家庭内网可访问
    • 有键盘和显示屏

  3. 软件安装

    • Docker & Docker Compose
    • HomeAssistant 容器：
      • 核心自动化中枢
      • 配置 Zigbee / MQTT 网关
    • Nextcloud 容器：
      • 轻量云盘，实现文件同步 / 云办公
    • Rhasspy / OpenVoiceOS：
      • 本地语音助手 = Home Assistant + ReSpeaker + Rhasspy + Vosk
      • 可调用 AI 服务
    • Mosquitto (MQTT broker)
    • Zigbee2MQTT（控制 Zigbee 设备）
    • VPN 客户端：
      • Tailscale / WireGuard / Zerotier，用于外网访问

  4. AI 前端代理

    • 配置树莓派将语音/文本请求通过 API 转发给 PC AI 工作站
    • 确保返回结果能被 HomeAssistant 或语音助手处理

  5. 智能家居集成

    • 配置所有 Zigbee / WiFi 设备
    • 创建基础自动化规则
    • 外出时可通过手机 / 平板 / 笔电控制

2️⃣ PC AI 工作站 —— AI / 计算中心

  1. 硬件组装

    • 使用半身像机箱（GP02A 或可抽拉式 ITX 机箱）
      • GP02A半身像1
      • GP02A半身像2
    • 安装强力 GPU（如 RTX 4070/4080/4090）
    • 配置 NVMe SSD（1–2TB）
    • 至少 32GB RAM
    • 良好散热 + 稳定电源

  2. 系统安装

    • Linux（Ubuntu / Pop!_OS / Debian 推荐）
    • 安装 GPU 驱动 + CUDA / cuDNN（支持 AI 推理）
    • 配置静态 IP（家庭内网访问）

  3. 软件安装

    • Docker & Docker Compose
    • AI 模型部署：
      • LLM（如 LLaMA、MPT、本地 Whisper）
      • Vision 模型（图像识别 / 视频分析）
      • TTS / RVC / ASR 模型
    • REST / WebSocket API 服务：
      • 接收树莓派发来的请求
      • 返回 AI 推理结果
    • 可选：VNC / RDP，用于远程桌面管理

  4. 与树莓派集成

    • 配置树莓派作为前端：
      • API 请求通过家庭内网发送
      • 结果回传到树莓派供 HomeAssistant 或语音助手使用
    • 监控 AI 任务负载
    • 存储大文件、素材、模型权重

3️⃣ 外网访问与安全

  1. VPN 设置

    • 在树莓派或路由器端配置 Tailscale / WireGuard
    • 手机 / 笔电通过 VPN 进入家庭内网
    • 访问 HomeAssistant、Nextcloud、AI 服务

  2. 文件访问

    • Nextcloud 提供 SFTP / WebDAV 接口
    • 上传、下载、备份工作文件
    • 支持外出办公

  3. 智能家居控制

    • HomeAssistant WebUI 或手机 App
    • 可控制灯光、空调、门锁、植物监控系统
    • 触发自动化场景

4️⃣ 流程概览

  1. 手机 / 笔电 → VPN → 树莓派
  2. 树莓派：
    • 处理 HomeAssistant 控制
    • Nextcloud 文件同步
    • AI 请求转发 → PC 工作站
  3. PC 工作站：
    • GPU 进行 AI 推理
    • 返回结果给树莓派
  4. 树莓派执行智能家居或语音助手动作
  5. 外出可上传 / 下载重要文件，远程管理家居

✅ 这样就形成了一个完整的家庭 AI 管家系统：

  • 树莓派 = 前端中控 + 轻量云盘 + HomeAssistant
  • PC 工作站 = 后端 AI 核心 + 高性能存储
  • VPN = 安全远程访问
  • Nextcloud = 云办公 / 文件同步
  • HomeAssistant + Zigbee / MQTT = 智能家居控制

  2. Ring Buffer 缓存
    • 可以用 collections.deque 或者 sounddevice.RawInputStream 自带的回调缓存。

  4. 提取音频片段（1~2秒）

    • 用 Vosk（支持离线运行，中文/英文等都有预训练模型）。

make和new区别

  • make和new都是golang用来分配内存的內建函数，且在堆上分配内存，make 即分配内存，也初始化内存。new只是将内存清零，并没有初始化内存。
  • make返回的还是引用类型本身；而new返回的是指向类型的指针。
  • make只能用来分配及初始化类型为slice，map，channel的数据；new可以分配任意类型的数据。

数组和切片区别

  • 数组是一个长度固定的数据类型，其长度在定义时就已经确定，内存空间大小是固定；切片是一个长度可变的数据类型，内存空间运行时动态分配，其长度在定义时可以为空，也可以指定一个初始长度 append追加切片
  • 当数组作为函数参数时，函数操作的是数组的一个副本，不会影响原始数组；当切片作为函数参数时，函数操作的是切片的引用，会影响原始切片

GMP协程调度器

内核线程-thread(Machine)，协程(Goroutine)，处理器-G的上下文环境（Processor）

  • G：goroutine协程，基于协程建立的用户态线程
  • M：machine，它直接关联一个os内核线程，用于执行G
  • P：processor处理器，P里面一般会存当前goroutine运行的上下文环境（函数指针，堆栈地址及地址边界），P会对自己管理的goroutine队列做一些调度

调度器策略

  • 全局G队列 - 通过go func()来创建一个goroutine,有两个存储G的队列，一个是局部调度器P的本地队列、一个是全局G队列。新创建的G会先保存在P的本地队列中，如果P的本地队列已经满了就会保存在全局的队列中
  • 复用线程 - work stealing机制和hand off机制（偷别人的去执行，和自己扔掉执行）,G只能运行在M中，一个M必须持有一个P,M与P是1：1的关系,

work stealing机制如果P的本地队列为空，就会想其他的MP组合偷取一个可执行的G来执行
hand off机制当本线程因为G进行系统调用阻塞时，线程释放绑定的P，把P转移给其他空闲的线程执行，此时M1如果长时间阻塞，可能会执行睡眠或销毁

  • 利用并行 - 我们可以使用GOMAXPROCS设置P的数量,这样的话最多有GOMAXPROCS个线程分布在多个CPU上同时运行。GOMAXPROCS也限制了并发的程度，比如GOMAXPROCS = 核数/2，则最多利用了一半的CPU核进行并行
  • 抢占策略 - 1对1模型的调度器，需要等待一个co-routine主动释放后才能轮到下一个进行使用, 如果一个goroutine使用10ms还没执行完，CPU资源就会被其他goroutine所抢占

调度器的生命周期

在了解调度器生命周期之前，我们需要了解两个新的角色M0和G0

M0（跟进程数量绑定，一比一）：

  • 启动程序后编号为0的主线程
  • 在全局变量runtime.m0中，不需要在heap上分配
  • 负责执行初始化操作和启动第一个G
  • 启动第一个G之后，M0就和其他的M一样了

G0（每个M都会有一个G0）：

  • 每次启动一个M，都会第一个创建的gourtine，就是G0
  • G0仅用于负责调度G
  • G0不指向任何可执行的函数
  • 每个M都会有一个自己的G0
  • 在调度或系统调用时会使用M切换到G0，再通过G0进行调度

M0和G0都是放在全局空间的

Kubernetes 提供能力

服务发现和负载均衡

Kubernetes 可以使用 DNS 名称或自己的 IP 地址来暴露容器。如果进入容器的流量很大, Kubernetes 可以负载均衡并分配网络流量, 从而使部署稳定。

自我修复

Kubernetes 将重新启动失败的容器、替换容器、杀死不响应用户定义的运行状况检查的容器,并且在准备好服务之前不将其通告给客户端。

自动完成装箱计算

你为 Kubernetes 提供许多节点组成的集群,在这个集群上运行容器化的任务。你告诉 Kubernetes 每个容器需要多少 CPU 和内存 (RAM), Kubernetes 可以将这些容器按实际情况调度到你的节点上,以最佳方式利用你的资源。

自动部署和回滚

你可以使用 Kubernetes 描述已部署容器的所需状态,它可以以受控的速率将实际状态更改为期望状态。例如,你可以自动化 Kubernetes 来为你的部署创建新容器,删除现有容器并将它们的所有资源用于新容器。

存储编排

Kubernetes 允许你自动挂载你选择的存储系统,例如本地存储、公共云提供商等。

密钥与配置管理

Kubernetes 允许你存储和管理敏感信息,例如密码、OAuth 令牌和 SSH 密钥。你可以在不重建容器镜像的情况下部署和更新密钥和应用程序配置,也无需在性样配置由星管密钥。

运行实际的负载机器

  • Mater 节点主要有以下组件：

    • kube-apiserver：负责对外暴露 Kubernetes API。
    • etcd：作为保存 Kubernetes 所有集群数据的后台数据库。

    • kube-controller-manager：负责监控调整调整集群的状态，比如故障检测、自动扩展、滚动更新等

  • Node 节点有以下组件：

    • kube-proxy：k8s 在每个节点上的网络代理，负责为 Service 提供集群内部的服务发现和负载均衡。

核心架构与稳定性基础

设计核心是“高可用+分布式”:
控制平面(Master)的所有核心组件(Api-server、Etcd、Controller Manager、Scheduler) 都通过集群化、主从选举、负载均衡,避免单点故障,保证“大脑不宕机”。
业务流量通过多层负载均衡+节点群,保证用户能稳定访问业务,且业务能横向扩展。
架构能支撑大规模、高可靠的生产级业务,是企业级 Kubernetes 集群的典型设计思路。

Scheduler调度器

1. 核心定义与角色

Scheduler 负责 Pod 的调度，在整个系统中起着 “承上启下” 的作用：

  • 承上：负责接收由 Controller Manager 创建的新 Pod，并为其选择一个合适的 Node（节点）。
  • 启下：调度完成后，目标 Node 上的 kubelet 接管 Pod 的生命周期，负责具体的启动与维护。

2. Pod 分配的核心流程

当一个 Pod 需要被调度时，kube-scheduler 会经历以下五个关键步骤：

  1. 监听待调度 Pod
    通过 kube-apiserver 持续监听（Watch）处于 Pending 状态、且未指定 Node 的 Pod。

  2. 过滤节点（预选 / Predicates）
    排除不符合 Pod 运行条件的节点，例如：

    • 资源不足（CPU / 内存等）
    • 节点标签不匹配
    • 污点与容忍度不满足

  3. 节点打分（优选 / Priorities）
    对通过预选的节点进行评分，综合多种调度策略，选出最优的节点。

  4. 绑定节点（Bind）
    将选定的 Node 信息写入 Pod 对象，并更新到 etcd 中。

  5. kubelet 启动 Pod
    目标节点的 kubelet 监听到调度结果后，在本地拉取镜像并启动容器，正式运行 Pod。

深度解析Scheduler

步骤 1 & 2：启动阶段

步骤 1：Pod 进入「待调度」状态
  • 新创建的 Pod 被写入 API Server
  • Pod 状态为 Pending
  • 尚未分配 spec.nodeName
步骤 2：调度器监听并选择待调度 Pod
  • kube-scheduler 通过 Watch 机制 监听 API Server
  • 获取所有处于 Pending 且未指定 Node 的 Pod
  • 将其加入调度队列，准备调度

步骤 3：预选（Filtering / Predicates）

目标：过滤不符合 Pod 运行要求的节点

常见过滤规则（Predicates）包括：

  • 资源充足性

    • 检查节点剩余 CPU、内存等资源
    • 是否满足 Pod 的 resources.requests

  • 节点标签匹配

    • 若 Pod 配置了 nodeSelector 或 nodeAffinity
    • 节点必须包含对应标签

  • 污点与容忍度（Taints & Tolerations）

    • 检查 Pod 是否能够容忍节点上的污点

  • 端口与存储兼容性

    • hostPort 是否已被其他 Pod 占用
    • 请求的持久化存储卷（PV）是否能在该节点挂载

  • 节点状态

    • 节点必须处于 Ready 状态
    • 不存在 MemoryPressure、DiskPressure 等异常

步骤 4：优选（Scoring / Priorities）

目标：为可行节点打分排序，选出最优节点

主要评分策略包括：

  • 资源均衡性

    • 倾向于让 CPU、内存使用更加均衡
    • 例如：BalancedResourceAllocation

  • 镜像本地性

    • 节点已存在所需容器镜像时获得加分
    • 减少镜像拉取时间，提高启动速度

  • Pod 亲和与反亲和性

    • podAffinity：希望某些 Pod 部署在一起
    • podAntiAffinity：避免某些 Pod 部署在同一节点

  • 节点负载

    • 优先选择 Pod 数量较少、资源更空闲的节点

  • 综合评分

    • 所有策略计算加权总分
    • 得分最高的节点成为最终候选

步骤 5：绑定（Binding）

  • Scheduler 选定最终节点
  • 将节点名称写入 Pod 的 spec.nodeName
  • 通过 API Server 更新 Pod 对象
  • 调度完成

步骤 6：kubelet 启动 Pod

目标节点上的 kubelet 开始接管 Pod 生命周期：

  • 拉取镜像

    • 下载 Pod 所需的容器镜像

  • 创建并启动容器

    • 通过容器运行时（如 containerd、Docker）

  • 持续监控

    • 监控 Pod 和容器运行状态
    • 向 API Server 汇报健康状态与资源使用情况

  • Node

    • 工作节点（物理机或虚拟机）
    • Pod 的 “硬件载体”

  • Namespace

    • 逻辑隔离资源
    • 常用于区分开发 / 测试 / 生产环境

  • Pod

    • K8s 最小部署单元
    • Pod 内容器共享网络与存储

  • ConfigMap / Secret

    • 配置管理，实现配置与 Pod 解耦
    • ConfigMap：非敏感配置（如数据库地址）
    • Secret：敏感信息（如密码、Token）

  • PV / PVC / StorageClass

    • 持久化存储三件套

  • Service / Ingress

    • 服务发现、服务暴露与负载均衡

4. 管理与限制

  • ServiceAccount

    • 为 Pod 中的应用提供身份认证
    • 解决“我是谁、我能做什么”

  • ResourceQuota

    • 限制 Namespace 级别资源总量
    • 防止 CPU、内存被单一业务耗尽

Docker的组成

  • docker client 客户端 👉 docker daemon 交互
  • docker daemon 守护进程 👉 一般在宿主主机后台运行，等待接收来自客户端的请求消息
  • docker container 容器 👉 镜像的运行实例，我们可以把镜像看成是一个个的构建块，容器根据这些构建块搭建起了一个隔离的，拥有整个包的应用程序。每一个容器都是一个标准化单元，确保了在不同机子上也能拥有一致的行为
  • docker image 镜像 👉 包含了操作系统的一张光碟，它是一个模板文件，除了提供容器运行时所需的程序、库、资源、配置等文件外，还包含了一些为运行时准备的一些配置参数（如匿名卷、环境变量、用户等）
  • 数据卷 👉 Docker 对数据持久化的解决方案，数据不会随着容器结束而丢失，通过将宿主机的某一文件目录载到容器里来实现 volumes：
  • 网络
    • bridge 模式 👉 Docker 在主机上会创建一个docker0的网桥
    • host 模式 👉 在建一个容器时，一般会为容器分配一个独立的 Network Namespace 以进行网络隔离。如果我们使用了 Host 模式，则不再分配 Network Namespace，而是和宿主机共用一个 Network Namespace。此时容器将不再拥有自己的虚拟网卡、IP 和端口，而是和宿主机共用一个 IP 和端口
    • none 模式 👉 使用 none 模式的容器拥有属于自己的 Network Namespace，但不做任何网络配置。它和宿主机以及其他容器是不互通的。如果需要和外部通信，则需要自定义网络驱动程序，自己添加网卡、配置 IP 等

Docker底层技术

  • Namespaces（资源隔离）：将系统的全局资源通过抽象划分，使得在同一 namespace 中的进程看起来拥有自己的全局资源。主要有 Mount namespaces（文件系统挂载）、Network namespaces（网络）、User namespaces（用户）等的资源隔离。
  • CGroups（资源限制）：对系统资源的限制，比如 CPU、内存等。
  • UnionFS（联合文件系统）：一次同时加载多个文件系统，但从外面看起来，只能看到一个文件系统，联合加载会把各层文件系统叠加起来，这样最终的文件系统会包含所有底层的文件和目录。便于镜像的分层继承。

export\import 与 save\load 的区别：

  • export\import 导出的镜像文件大小要小于 save\load 导出的镜像

  • export\import 是根据容器拿到的镜像，再导入时会丢失镜像所有的历史，所以无法进行回滚操作；而 save\load 的镜像，没有丢失镜像的历史，可以回滚到之前的层。

核心原因是 export 是针对容器的导出，所以只有所有层组合的最终版本；而 save 则是针对镜像的，所以可以看到每一层的信息。

Docker逃逸

  • 容器镜像存在的风险

  • 活动中的容器存在的风险

    • 不安全的容器应用

    • 不受限制的资源共享

    • 不安全的配置与挂载

      如果为容器设定了不安全的配置，会导致容器本身的隔离机制失效，容器的两大隔离机制如下：

      • Linux 命名空间（NameSpace）：实现文件系统、网络、进程、主机名等方面的隔离
      • Linux 控制组（cgroups）：实现 CPU、内存、硬盘等方面的隔离

      如果设定了以下配置就会导致相应的隔离机制失效：

      • –privileged：使容器内的 root 权限和宿主机上的 root 权限一致，权限隔离被打破
      • –net=host：使容器与宿主机处于同一网络命名空间，网络隔离被打破
      • –pid=host：使容器与宿主机处于同一进程命令空间，进程隔离被打破
      • –volume /:/host：宿主机根目录被挂载到容器内部，文件系统隔离被打破

  • 容器管理程序接口的风险

    Docker 守护进程主要监听 UNIX socket 和 TCP socket，默认情况下，Docker 只会监听 UNIX socket

    • UNIX socket
      UNIX socket 的风险主要在于 Docker 守护进程默认以宿主机的 root 权限运行，因此就可以借助这点进行提权或者容器逃逸。
      这类风险主要有两个利用场景：

      普通用户被加到 Docker 用户组内
      如果普通用户被加入到 Docker 用户组内，那么普通用户也将有权限访问 Docker UNIX socket，如果攻击者获得了这个普通用户权限，就可以借助 Docker 提权到 root 用户权限。

      具体的做法可以简单描述为：使用普通用户创建一个 privileged 为 true 的容器，在该容器内挂载宿主机硬盘并写入定时任务，然后将宿主机的 root 权限反弹回来，后期将详细介绍这种方法的使用。

      UNIX socket 挂载到容器内部
      有时为了实现容器内部管理容器，可能会将 Docker UNIX socket 挂载到容器内部，那么如果该容器被入侵，RT 就可以借助这个 socket 进行容器逃逸获得宿主机 root 权限。

    • TCP socket
      现在 Docker 守护进程默认不会监听 TCP socket，不过有时可能用户会因为方便开启 TCP socket 的监听，一般默认监听端口是 2375

      默认情况下，Docker 守护进程 TCP socket 是无加密无认证的，因此如果发现宿主机 Docker 开放了 TCP socket，就可以直接使用 docker -H 接管目标的容器
