make和new区别

  • make和new都是golang用来分配内存的內建函数，且在堆上分配内存，make 即分配内存，也初始化内存。new只是将内存清零，并没有初始化内存。
  • make返回的还是引用类型本身；而new返回的是指向类型的指针。
  • make只能用来分配及初始化类型为slice，map，channel的数据；new可以分配任意类型的数据。

数组和切片区别

  • 数组是一个长度固定的数据类型，其长度在定义时就已经确定，内存空间大小是固定；切片是一个长度可变的数据类型，内存空间运行时动态分配，其长度在定义时可以为空，也可以指定一个初始长度 append追加切片
  • 当数组作为函数参数时，函数操作的是数组的一个副本，不会影响原始数组；当切片作为函数参数时，函数操作的是切片的引用，会影响原始切片

GMP协程调度器

内核线程-thread(Machine)，协程(Goroutine)，处理器-G的上下文环境（Processor）

  • G：goroutine协程，基于协程建立的用户态线程
  • M：machine，它直接关联一个os内核线程，用于执行G
  • P：processor处理器，P里面一般会存当前goroutine运行的上下文环境（函数指针，堆栈地址及地址边界），P会对自己管理的goroutine队列做一些调度

调度器策略

  • 全局G队列 - 通过go func()来创建一个goroutine,有两个存储G的队列，一个是局部调度器P的本地队列、一个是全局G队列。新创建的G会先保存在P的本地队列中，如果P的本地队列已经满了就会保存在全局的队列中
  • 复用线程 - work stealing机制和hand off机制（偷别人的去执行，和自己扔掉执行）,G只能运行在M中，一个M必须持有一个P,M与P是1：1的关系,

work stealing机制如果P的本地队列为空，就会想其他的MP组合偷取一个可执行的G来执行
hand off机制当本线程因为G进行系统调用阻塞时，线程释放绑定的P，把P转移给其他空闲的线程执行，此时M1如果长时间阻塞，可能会执行睡眠或销毁

  • 利用并行 - 我们可以使用GOMAXPROCS设置P的数量,这样的话最多有GOMAXPROCS个线程分布在多个CPU上同时运行。GOMAXPROCS也限制了并发的程度，比如GOMAXPROCS = 核数/2，则最多利用了一半的CPU核进行并行
  • 抢占策略 - 1对1模型的调度器，需要等待一个co-routine主动释放后才能轮到下一个进行使用, 如果一个goroutine使用10ms还没执行完，CPU资源就会被其他goroutine所抢占

调度器的生命周期

在了解调度器生命周期之前，我们需要了解两个新的角色M0和G0

M0（跟进程数量绑定，一比一）：

  • 启动程序后编号为0的主线程
  • 在全局变量runtime.m0中，不需要在heap上分配
  • 负责执行初始化操作和启动第一个G
  • 启动第一个G之后，M0就和其他的M一样了

G0（每个M都会有一个G0）：

  • 每次启动一个M，都会第一个创建的gourtine，就是G0
  • G0仅用于负责调度G
  • G0不指向任何可执行的函数
  • 每个M都会有一个自己的G0
  • 在调度或系统调用时会使用M切换到G0，再通过G0进行调度

M0和G0都是放在全局空间的

演变历史


k8s的演变过程：首先从传统的服务–>虚拟机部署–>容器部署–>k8s

不是新轮子,而是运维自动化的集大成者:

  • 自动调度(把Pod 放到合适的机器)
  • 自我修复(Pod 挂了自动重建)
  • 服务发现&负载均衡(Service 自动分配IP和DNS)
  • 滚动更新&回滚(零停机发布)
  • 密钥&配置管理(ConfigMap / Secret)

对研发的意义:

  • 不再关心“部署在哪台机器”,只关心“我要几个副本、暴露什么端口、用什么配置”
  • 环境一致性:开发、测试、生产都跑在同一个抽象层上.

Kubernetes 提供能力

服务发现和负载均衡

Kubernetes 可以使用 DNS 名称或自己的 IP 地址来暴露容器。如果进入容器的流量很大, Kubernetes 可以负载均衡并分配网络流量, 从而使部署稳定。

自我修复

Kubernetes 将重新启动失败的容器、替换容器、杀死不响应用户定义的运行状况检查的容器,并且在准备好服务之前不将其通告给客户端。

自动完成装箱计算

你为 Kubernetes 提供许多节点组成的集群,在这个集群上运行容器化的任务。你告诉 Kubernetes 每个容器需要多少 CPU 和内存 (RAM), Kubernetes 可以将这些容器按实际情况调度到你的节点上,以最佳方式利用你的资源。

自动部署和回滚

你可以使用 Kubernetes 描述已部署容器的所需状态,它可以以受控的速率将实际状态更改为期望状态。例如,你可以自动化 Kubernetes 来为你的部署创建新容器,删除现有容器并将它们的所有资源用于新容器。

存储编排

Kubernetes 允许你自动挂载你选择的存储系统,例如本地存储、公共云提供商等。

密钥与配置管理

Kubernetes 允许你存储和管理敏感信息,例如密码、OAuth 令牌和 SSH 密钥。你可以在不重建容器镜像的情况下部署和更新密钥和应用程序配置,也无需在性样配置由星管密钥。

控制平面(control plane)：

集群🧠(比如调度) |master节点 以及检测和响应集群事件(例如资源不足，自动扩缩容)

节点平面(node plane)：

运行实际的负载机器

  • Mater 节点主要有以下组件：

    • kube-apiserver：负责对外暴露 Kubernetes API。
    • etcd：作为保存 Kubernetes 所有集群数据的后台数据库。
    • kube-scheduler：在适当的时候进行调度决策，让 Pod 在合适的节点上创建运行。
    • kube-controller-manager：负责监控调整调整集群的状态，比如故障检测、自动扩展、滚动更新等

  • Node 节点有以下组件：

    • kubelet：主要负责执行、监控由调度器分配的 Pod，相当于是 Master 在每个 Node 节点上的代理。保证 Pod 的运行状态与目标状态一致。
    • kube-proxy：k8s 在每个节点上的网络代理，负责为 Service 提供集群内部的服务发现和负载均衡。

核心架构与稳定性基础

设计核心是“高可用+分布式”:
控制平面(Master)的所有核心组件(Api-server、Etcd、Controller Manager、Scheduler) 都通过集群化、主从选举、负载均衡,避免单点故障,保证“大脑不宕机”。
业务流量通过多层负载均衡+节点群,保证用户能稳定访问业务,且业务能横向扩展。
架构能支撑大规模、高可靠的生产级业务,是企业级 Kubernetes 集群的典型设计思路。

控制平面组件（Control Plane）

组件 功能 类比 研发需知
kube-apiserver 集群所有操作的唯一入口（kubectl / controller / scheduler 都走它） 前台接待 ❗ 出问题 = 整个集群不可操作；所有鉴权、校验、写入都在这里
etcd 分布式键值数据库，存储所有集群状态 中央账本 ❗ 数据丢失 = 集群逻辑性死亡；必须定期备份、谨慎扩容
kube-scheduler 决定新 Pod 调度到哪台 Node 调度员 可通过 taint / toleration、nodeSelector、affinity 干预
kube-controller-manager 运行各种控制器（Deployment / Node / Job 等） 监工 核心职责：确保 实际状态 = 期望状态，问题多为“反复拉起/杀死”

工作节点组件（Worker Node）

组件 功能 类比 研发需知
kubelet Node 代理，负责 Pod 生命周期和健康检查 执行者 / 联络员 Node 宕机或 kubelet 异常 → 该节点上的 Pod 全部不可用
kube-proxy 维护网络规则，实现 Service 虚拟 IP 网络向导 依赖 iptables / ipvs；Service 不通时重点排查对象
Container Runtime
(containerd / CRI-O / Docker*)		 实际运行容器的底层组件 搬运工 是容器能跑起来的基础；K8s 通过 CRI 与其交互

相互之间的通讯

  • 每个Node节点都会启动kubelet进程, 处理Master节点下发到本节点的任务, 管理 Pod和其中的容器。
  • kubelet会在API Server上注册节点信息,定期向Master汇报节点资源使用情况,并通过cAdvisor监控容器和节点资源,可以把kubelet理解成Server/Agent架构中的agent,
  • kubelet是Node上的 pod管家。

Scheduler调度器

1. 核心定义与角色

Scheduler 负责 Pod 的调度，在整个系统中起着 “承上启下” 的作用：

  • 承上：负责接收由 Controller Manager 创建的新 Pod，并为其选择一个合适的 Node（节点）。
  • 启下：调度完成后，目标 Node 上的 kubelet 接管 Pod 的生命周期，负责具体的启动与维护。

2. Pod 分配的核心流程

当一个 Pod 需要被调度时，kube-scheduler 会经历以下五个关键步骤：

  1. 监听待调度 Pod
    通过 kube-apiserver 持续监听（Watch）处于 Pending 状态、且未指定 Node 的 Pod。

  2. 过滤节点（预选 / Predicates）
    排除不符合 Pod 运行条件的节点，例如：

    • 资源不足（CPU / 内存等）
    • 节点标签不匹配
    • 污点与容忍度不满足

  3. 节点打分（优选 / Priorities）
    对通过预选的节点进行评分，综合多种调度策略，选出最优的节点。

  4. 绑定节点（Bind）
    将选定的 Node 信息写入 Pod 对象，并更新到 etcd 中。

  5. kubelet 启动 Pod
    目标节点的 kubelet 监听到调度结果后，在本地拉取镜像并启动容器，正式运行 Pod。

深度解析Scheduler

步骤 1 & 2：启动阶段

步骤 1：Pod 进入「待调度」状态
  • 新创建的 Pod 被写入 API Server
  • Pod 状态为 Pending
  • 尚未分配 spec.nodeName
步骤 2：调度器监听并选择待调度 Pod
  • kube-scheduler 通过 Watch 机制 监听 API Server
  • 获取所有处于 Pending 且未指定 Node 的 Pod
  • 将其加入调度队列，准备调度

步骤 3：预选（Filtering / Predicates）

目标：过滤不符合 Pod 运行要求的节点

常见过滤规则（Predicates）包括：

  • 资源充足性

    • 检查节点剩余 CPU、内存等资源
    • 是否满足 Pod 的 resources.requests

  • 节点标签匹配

    • 若 Pod 配置了 nodeSelector 或 nodeAffinity
    • 节点必须包含对应标签

  • 污点与容忍度（Taints & Tolerations）

    • 检查 Pod 是否能够容忍节点上的污点

  • 端口与存储兼容性

    • hostPort 是否已被其他 Pod 占用
    • 请求的持久化存储卷（PV）是否能在该节点挂载

  • 节点状态

    • 节点必须处于 Ready 状态
    • 不存在 MemoryPressure、DiskPressure 等异常

步骤 4：优选（Scoring / Priorities）

目标：为可行节点打分排序，选出最优节点

主要评分策略包括：

  • 资源均衡性

    • 倾向于让 CPU、内存使用更加均衡
    • 例如：BalancedResourceAllocation

  • 镜像本地性

    • 节点已存在所需容器镜像时获得加分
    • 减少镜像拉取时间，提高启动速度

  • Pod 亲和与反亲和性

    • podAffinity：希望某些 Pod 部署在一起
    • podAntiAffinity：避免某些 Pod 部署在同一节点

  • 节点负载

    • 优先选择 Pod 数量较少、资源更空闲的节点

  • 综合评分

    • 所有策略计算加权总分
    • 得分最高的节点成为最终候选

步骤 5：绑定（Binding）

  • Scheduler 选定最终节点
  • 将节点名称写入 Pod 的 spec.nodeName
  • 通过 API Server 更新 Pod 对象
  • 调度完成

步骤 6：kubelet 启动 Pod

目标节点上的 kubelet 开始接管 Pod 生命周期：

  • 拉取镜像

    • 下载 Pod 所需的容器镜像

  • 创建并启动容器

    • 通过容器运行时（如 containerd、Docker）

  • 持续监控

    • 监控 Pod 和容器运行状态
    • 向 API Server 汇报健康状态与资源使用情况

最基础的核心对象

Kubernetes 的能力由多种 API 对象组合而成，以下是最基础的构建块：

1. 基础设施与隔离

  • Node

    • 工作节点（物理机或虚拟机）
    • Pod 的 “硬件载体”

  • Namespace

    • 逻辑隔离资源
    • 常用于区分开发 / 测试 / 生产环境

2. 应用与配置

  • Pod

    • K8s 最小部署单元
    • Pod 内容器共享网络与存储

  • ConfigMap / Secret

    • 配置管理，实现配置与 Pod 解耦
    • ConfigMap：非敏感配置（如数据库地址）
    • Secret：敏感信息（如密码、Token）

3. 存储与网络

  • PV / PVC / StorageClass

    • 持久化存储三件套
    • PV：实际存储资源
    • PVC：Pod 的存储申请
    • StorageClass：存储类型（如 SSD），支持动态分配

  • Service / Ingress

    • 服务发现、服务暴露与负载均衡

4. 管理与限制

  • ServiceAccount

    • 为 Pod 中的应用提供身份认证
    • 解决“我是谁、我能做什么”

  • ResourceQuota

    • 限制 Namespace 级别资源总量
    • 防止 CPU、内存被单一业务耗尽

/var/log/message 记录系统重要信息的日志。这个日志文件中会记录Linux系统的绝大多数重要信息，如果系统出现问题时，首先要检查的就应该是这个日志文件
/var/log/btmp 记录错误登录日志，这个文件是二进制文件，不能直接vi查看，而要使用lastb命令查看
/var/log/lastlog 记录系统中所有用户最后一次登录时间的日志，这个文件是二进制文件，不能直接vi，而要使用lastlog命令查看
/var/log/wtmp 永久记录所有用户的登录、注销信息，同时记录系统的启动、重启、关机事件。同样这个文件也是一个二进制文件，不能直接vi，而需要使用last命令来查看
/var/log/utmp 记录当前已经登录的用户信息，这个文件会随着用户的登录和注销不断变化，只记录当前登录用户的信息。同样这个文件不能直接vi，而要使用w,who,users等命令来查询
/var/log/secure 记录验证和授权方面的信息，只要涉及账号和密码的程序都会记录，比如SSH登录，su切换用户，sudo授权，甚至添加用户和修改用户密码都会记录在这个日志文件中

地基阶段注意事项

防水处理

  • 关键节点加强防水：厨房、卫生间的地面与墙面交界处，务必采用聚氨酯或水泥基防水涂料，并向上返高≥30cm。
  • 设置防潮层：一楼地面下应预铺防潮膜（如PVC或自粘式沥青卷材），有效阻隔地气上升。
  • 户外地面坡度设计：屋外地坪应高于周边排水沟至少10cm，地面向外倾斜2~3%，防止雨水回流。

热水/供水布局

  • 热水管道预埋：采用PPR或PE-RT热水专用管，外包保温棉，防止热量流失。
  • 太阳能热水系统预留：
    • 上水、回水、溢水管道预埋；
    • 储水箱位置尽量设于高处以确保自然水压；
  • 泵系统智能化：
    • 安装断电自停功能，避免干烧；
    • 可选变频恒压泵以提升用水舒适度与节能效果。

防蚊虫叮咬

  • 高离地设计：将地面层抬高 40–80 cm，有效减少地面湿气与虫害滋生源。
  • 水沟与排水坡度设计：避免积水死角，是预防蚊虫滋生的核心设计。
  • 屋顶排水顺畅设计：设置排水沟槽、防堵落叶网，防止雨后积水孳生蚊子。
  • 无死角阴暗空间：减少蚊虫栖息区域，尤其在厨房、厕所、天花板边缘。

节能导向的地基设计

  • 保温层预留：在地坪施工前铺设XPS 挤塑板或泡沫混凝土，减少地面热传导；
  • 太阳能系统预布线：地基预留光伏电缆通道、电池房管线槽；
  • 雨水收集系统接口：预埋雨水排入储水池的管道，用于冲厕、浇花等二次利用。

水资源节能设计方案

级别 水质要求 用水场景 推荐水源
✅ 一级水 可直接饮用 饮水、做饭 自来水 / 反渗透（RO）处理后的雨水或地下水
✅ 二级水 可接触皮肤 洗澡、泳池、洗手 雨水+三级过滤杀菌 / 污水深度处理水
✅ 三级水 无皮肤接触 冲厕、洗衣机、室内清洁 雨水+普通过滤 / 灰水处理出水
✅ 四级水 非接触景观水 浇花、冲地、喷泉、景观池补水 荷花池雨水原水 / 简单过滤的灰水

🔧 每级水处理建议方案

  • 🥇 一级水（饮用）
    • 推荐：自来水 或
      • RO膜+UV消毒雨水系统
      • 末端设置净水龙头（饮水分开）
    • 用于：厨房饮用水、泡茶、做饭
  • 🥈 二级水（洗澡 / 泳池）
    • 雨水处理需：
      • 多级砂滤 + 活性炭 + 紫外线（或臭氧）
    • 池水需循环过滤系统 + 定期杀菌
  • 🥉 三级水（冲厕 / 洗衣）
    • 雨水+简单过滤即可；
    • 或使用处理后的灰水（洗澡水）
  • 🧯 四级水（浇花 / 景观）
    • 不需杀菌；
    • 可直接从荷花池抽取或雨水初滤水

🌧️ 雨水管理与回用

  • 屋顶雨水收集系统（落水管 + 滤网 + 蓄水桶）。
  • 灰水（洗澡/洗衣水）过滤后回用：冲厕、浇花。
  • 智能水表 + 水流实时监控，漏水报警。

🚿 节水设备与生活用水优化

  • 节水型洁具（双档马桶、节水花洒、起泡龙头）。
  • 可降解洗涤剂（适配灰水系统，避免堵塞/污染）。
  • 花园微滴灌系统，减少水耗、提高效率。

♻️ 污水处理与再利用

  • 处理方式：

    • 三格式化粪池：基础版，适用于1~3户。
    • 一体化小型污水处理设备：出水可灌溉/冲厕。
    • MBR 膜处理系统：可达中水标准，回用广泛。

  • 运行优化：

    • 使用电曝气或风曝气系统提升处理效率。
    • 搭配太阳能曝气机节能运行。

  • 回用建议：

    • 出水仅用于非饮用途，如景观、花园、厕所冲水。
    • 设置绿植过滤带/湿地吸收，提升生态安全性。

室内装修阶段注意事项

🚽 卫生间设计

  • 洗手台面应有微斜排水设计，避免水滞留。
  • 地面坡度 ≥1.5%，设置地漏 ≥2个，防止积水。
  • 建议做干湿分离（玻璃隔断/推拉门）。

🪟 窗户设计

  • 落地窗滑轮推荐安装于上方，更防尘易维护。
  • 建议使用中空双层玻璃 + 隔热断桥铝材料。
  • 窗户加装密封条，提升隔音与保温性能。

🍳 厨房设计

  • 选 ≥17m³/min 吸力油烟机，配备止回阀。
  • 抽油烟口向外，带防虫防雨罩。
  • 橱柜下方设计通风口或百叶门，防潮防霉。

照明与配电系统设计

配电安全

  • 强电/弱电分离布线，避免干扰，布线使用阻燃线管。
  • 所有空调、热水器、厨房电器应设置独立回路 + 空气开关；
  • 建议安装漏电保护器（ELCB）+ 电涌保护器（SPD），应对雷击等风险。

照明布局

  • 主照明建议使用LED 吸顶灯或筒灯，高效节能；
  • 卧室、走廊、卫生间建议搭配感应灯或夜灯，便捷又节能；
  • 考虑预埋智能照明控制系统（如 Zigbee、Wi-Fi、KNX），后期可接入 Home Assistant 等智能中枢。

🌿 节能建筑设计辅助方案

🍃 通风与遮阳设计

  • 中庭通风井、开窗对流、屋檐挑出 ≥0.8m。
  • 百叶窗与高位排气窗配合，增强排热与遮阳效果。

🧱 材料与结构选择

  • 使用本地天然建材（竹、柚木、红土砖），低碳环保。
  • 坡屋顶利于排水与热对流。
  • 设置独立“设备房”：集中布置电池、泵、过滤设备等，方便维护与检修。

✅ 附加建议（施工实用）

  • 插座预留合理，避免后期拖线。
  • 弱电布线提前规划：摄像头、Wi-Fi、门禁等。
  • 屋顶可加绿植或设凉亭，降温又美观。
  • 建议双管排水（黑水/灰水分离），提升回用系统效率。

生态鱼缸系统总结与维护要点

这个系统之所以能接近“不用护理”的状态，核心在于构建了一个功能完备的食物链和分解链，实现了养分在系统内部的良性循环：

核心优势：完整的生态循环链

  • 生产者：

    • 水草和睡莲利用阳光和鱼的粪便生长。

  • 初级消费者：

    • 鱼和虾吃藻类和水草（少量）。

  • 分解者（关键）：

    • 黑壳虾是吃死鱼、死虾和死蚬的“主力军”，防止尸体腐烂污染水质。
    • 蚬滤食水中的微生物和碎屑。
    • 细菌最终分解所有有机物。

  • 养分循环：

    • 植物吸收分解后的废物，水质保持清澈，形成良性循环。

还需要注意什么？

虽然系统设计得很完善，但要实现完全“不用护理”是不可能的。您依然需要进行最基础的维护：

  • 光照管理：

    • 阳光充足的南向房是优势，但需要注意遮阳，避免阳光直射时间过长导致夏天水温过高或藻类大爆发。您可能需要拉一下窗帘。

  • 水量补充：

    • 瀑布蒸发会带走水分，需要定期（比如每周）补充蒸发掉的水分。

  • 生物密度控制：

    • 如果鱼和虾繁殖过多，系统可能会不堪重负，需要适度捕捞或移出部分生物。

  • 偶尔的清理：

    • 睡莲枯叶、堆积过多的螺壳（如前所述）等，偶尔需要手动清除一下。

结论：

这个配置方案非常棒，只要您控制好生物数量和光照，它确实能实现极低维护的状态，是您想要的“生态鱼缸”的理想模型。
