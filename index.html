Ollama 本地大模型运行框架：从部署到生产级实践

一、背景：为什么需要本地 LLM 运行时

在企业级 AI 应用场景中，我们面临三个核心矛盾：数据合规性（GDPR/等保要求禁止敏感数据上云）、成本可控性（OpenAI API 按 token 计费在高频调用场景下月账单可达数万美元）、服务稳定性（依赖第三方 API 存在限流、故障、网络抖动风险）。Ollama 作为轻量级本地推理框架，通过 Go 实现的高性能 HTTP 服务器 + llama.cpp 后端，支持在消费级硬件（16GB 内存 MacBook / 单张 RTX 4090）上运行 7B-70B 参数模型，推理延迟控制在 50-200ms/token。

典型应用场景包括：代码补全（Tabby/Continue 插件需要 <100ms 响应）、文档问答（RAG 系统需要离线向量化）、敏感数据分析（医疗/金融行业禁止数据外传）。相比云端 API，本地部署的 P99 延迟可降低 60%，但需要解决模型加载慢（冷启动 10-30 秒）、显存溢出（OOM）、并发能力弱（单实例 QPS < 10）等工程问题。

关键技术选型对比：Ollama 适合快速原型验证，vLLM 适合高并发生产环境（PagedAttention 算法可提升 24x 吞吐），Text-generation-webui 适合非技术团队可视化调试。本文聚焦 Ollama 在 SRE 视角下的生产化改造路径。

Linux 系统运维核心命令实战指南

一、背景与适用场景

在生产环境中，SRE 需要快速定位系统瓶颈、诊断故障并执行变更操作。典型场景包括：应用响应缓慢需要排查 CPU/内存/磁盘 IO 瓶颈；网络连接异常需要追踪路由和端口占用；进程异常退出需要分析日志和资源限制；磁盘空间告警需要清理和扩容；用户权限问题导致服务启动失败。

Linux 命令行工具是第一响应手段，相比 GUI 监控系统具有更低延迟、更精确的数据采集能力。掌握命令组合使用（管道、重定向、过滤）可将诊断效率提升 10 倍以上。本文聚焦生产环境高频使用的命令集，按故障诊断流程组织，强调只读验证优先原则。

关键原则：先观察后操作，先备份后变更，先局部后全局。所有破坏性操作必须在测试环境验证，生产环境需要 change ticket 和 rollback 预案。

九、架构层面的可观测性建议

9.1 监控与告警集成

生产环境不应依赖手动执行命令，需将关键指标接入监控系统：

  • Metrics 采集：部署 node_exporter（Prometheus）或 Telegraf（InfluxDB），采集 CPU/内存/磁盘/网络指标，设置 P95/P99 阈值告警
  • 日志聚合：使用 ELK/Loki 集中收集 /var/log 和应用日志，配置错误关键词告警规则（ERROR/FATAL/OOM）
  • APM 追踪：Java 应用集成 SkyWalking/Jaeger，自动关联慢查询和异常堆栈，减少 lsof/strace 手动排查

9.2 变更管理与灰度发布

所有生产变更必须遵循：

  • Pre-flight 检查：自动化脚本验证磁盘空间（df -h）、端口占用（ss -tlnp）、配置语法（nginx -t）
  • 金丝雀部署：先在 1% 流量节点执行变更，监控错误率和延迟 15 分钟，通过后逐步扩大到 10%/50%/100%
  • 自动回滚：设置 SLO 阈值（如错误率 >1%），触发时自动执行 systemctl restart 或切换旧版本二进制文件
  • 变更日志：所有 sed -i/chown/systemctl 操作记录到 Git 仓库，配合 Ansible/Terraform 实现 IaC

关键要点总结：

  1. 只读优先：所有诊断从 ps/top/df/ss 等只读命令开始，避免误操作
  2. 备份强制：任何 -i 参数（sed -i/rm -i）操作前必须备份，保留时间戳

现在这种话都会说得委婉一点了。

本期话题探讨了在网络安全领域中，针对渗透测试岗位与安全管理岗位面试时的一些考察方法及问题。对于渗透测试岗位，面试官倾向于通过实践操作来检验应聘者的实战能力，例如让他们在一个模拟环境中进行渗透测试，或是提问具体的漏洞利用技术和修复方案。此外，也会考察应聘者对于漏洞原理的理解、常用工具的掌握程度以及在特定场景下的问题解决能力。

而在安全管理岗位的面试中，则更多关注应聘者的理论水平、实践经验、实操能力和心理素质等方面。面试官可能会问及如何构建全面的信息安全管理体系(ISMS)，包括风险评估、政策制定等内容，并探讨应聘者在过去工作中遇到的具体挑战及其解决方案。此外，还会考察应聘者对于法律法规的认知、安全团队的建设和管理等综合能力。

两者的面试都强调了应聘者不仅要具备扎实的技术基础，还需要拥有良好的沟通协调能力，以便于在实际工作中与不同部门协作，推进安全项目的实施。

PHP

运行模式

  • CGI（通用网关接口/ Common Gateway Interface）
  • FastCGI（常驻型CGI / Long-Live CGI）lamp
  • CLI（命令行运行 / Command Line Interface）
  • Web模块模式（Apache等Web服务器运行的模式）
  • ISAPI（Internet Server Application Program Interface）

Nginx与Apache解析php文件

  • php是apache的一个模块，必须依靠web服务器才可以运行，在php引擎解析php文件，php引擎将html页面带给web服务器解析并返回客户端
  • cgi与fastcgi协议，CGI common gateway interface, CGI缺点，每处理一个请求都要fork一个全新的进程，就有了fastCGI，一个进程内可以处理多个请求
  • phpCGI是fastCGI管理器，后面就用了FPM已经集成到了php里(php-fpm进程管理)
  • php-fpm监听的事socket文件，nginx通过location将所有php文件交给fpm处理

设计模式（三大类）

优势：

  • 独立开发 – 所有微服务都可以根据各自的功能轻松开发
  • 独立部署 – 基于其服务，可以在任何应用程序中单独部署它们
  • 故障隔离 – 即使应用程序的一项服务不起作用，系统仍可继续运行
  • 混合技术堆栈 – 可以使用不同的语言和技术来构建同一应用程序的不同服务
  • 粒度缩放 – 单个组件可根据需要进行缩放，无需将所有组件缩放在一起

特点：

  • 解耦 – 系统内的服务很大程度上是分离的。因此，整个应用程序可以轻松构建，更改和扩展
  • 组件化 – 微服务被视为可以轻松更换和升级的独立组件
  • 业务能力 – 微服务非常简单，专注于单一功能
  • 自治 – 开发人员和团队可以彼此独立工作，从而提高速度
  • 持续交付 – 通过软件创建，测试和批准的系统自动化，允许频繁发布软件
  • 责任 – 微服务不关注应用程序作为项目。相反，他们将应用程序视为他们负责的产品
  • 分散治理 – 重点是使用正确的工具来做正确的工作。这意味着没有标准化模式或任何技术模式。开发人员可以自由选择最有用的工具来解决他们的问题
  • 敏捷 – 微服务支持敏捷开发。任何新功能都可以快速开发并再次丢弃

Redis缓存雪崩、缓存穿透、缓存击穿

  • 缓存雪崩
    大量用户请求，全部转向请求访问数据库，压力剧增，可能导致数据库宕机，造成系统崩溃，造成缓存雪崩

  • 缓存击穿
    业务中几个数据会频繁访问，比如秒杀数据，被称为热点数据
    如果某个热点数据过期了，此时大量用户请求，无法从缓存中读取，直接访问数据库，造成系统奔溃，缓存击穿

  • 缓存穿透
    当用户访问数据，既不在缓存中，也不在数据库，导致请求缓存时，发现缓存缺失，发现两者都没找到，没法构建缓存，

缓存异常 产生原因 应对方案
缓存雪崩 大量数据同时过期 1.均匀设置过期时间 - 过期时间后加随机数，保证不会再同一时间过期
2.互斥锁 - 保证同一时间只有一个请求来构建缓存
3.后台更新缓存
Redis 故障宕机 1.服务熔断或请求限流机制
2.构建 Redis 缓存高可靠集群
缓存击穿 热点数据过期 1.互斥锁
2.不给热点数据设置过期时间，由后台异步更新缓存
缓存穿透 访问的数据既不在缓存，也不在数据库 1.非法请求
2.缓存空值或者默认值
3.使用布隆过滤器快速判断数据是否存在

RabbitMQ,RocketMQ,Kafka区别

MQ消息队列 优点 缺点
RabbitMQ 轻量级、容易部署和使用、支持多种客户端开发语言、支持灵活的路由配置 对消息堆积的支持并不好、性能和吞吐量较差、使用 Erlang 语言编写，比较难进行二次开发
RocketMQ 性能好、稳定可靠、有活跃的中文社区、使用 Java 开发，容易进行二次开发、特点响应快 兼容性较差
Kafka 兼容性极好、设计上大量使用了批量和异步的思想，有超高的性能 由于 “先攒一波再一起处理” 的设计，时延较高，不太适合在线业务场景

php-cs-fixer

php-cs-fixer 是个代码格式化工具，格式化的标准是 PSR-1、PSR-2 以及一些 symfony 的标准。

  • –verbose 用于展示应用了的规则

    –verbose

  • –using-cache 不使用缓存

    –using-cache=no

  • –config 指定配置文件

    –config=.php-cs-fixer.php

  • –level 用于控制需要使用的规则层级（默认psr2）

    –level=psr0
    –level=psr1
    –level=psr2
    –level=symfony

  • –fixers 默认情况下执行的是 PSR-2 的所有选项以及一些附加选项（主要是 symfony 相关的）。还有一些属于『贡献级别』的选项，你可以通过 –fixers 选择性的添加，–fixers 的多个条件要用逗号分开

    –fixers=linefeed,short_tag,indentation

  • -name_of_fixer 设定禁用哪些选项。如果同时设定了 –fixers 和 -name_of_fixer，前者的优先级更高
  • –dry-run 和 –diff 可以显示出需要修改的汇总，但是并不实际修改

    ./vendor/bin/php-cs-fixer fix –verbose –diff –dry-run
