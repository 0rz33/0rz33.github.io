[expanded] [blog] vue2 大文件上传component(做成组件)

原始问题: [blog] vue2 大文件上传component(做成组件)

前端大文件分片上传组件实现技能清单

场景占位: 上传到 ，文件 MD5 用 ，分片索引用
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 批量上传必须串行校验每个文件的 MD5，不能并行

  • 规则: 用 for...of 循环逐个计算文件 MD5，不能用 forEach 或 map
  • 为什么: MD5 计算是异步操作，并行会导致内存爆炸（多个大文件同时读入内存）且无法保证上传顺序，串行能控制内存峰值在单文件大小
  • 踩坑: 用 files.forEach(async file => await getMd5()) 会立即触发所有文件读取，浏览器直接卡死
  • 例外: 小文件（<50MB）且数量少（<5个）可以并行

2. 文件唯一标识必须用”业务键+文件属性”混合 MD5，不能只用文件内容 MD5

  • 规则: md5(uploadkey + name + type + lastModifiedDate + size) 生成 uniqueFileName
  • 为什么: 纯文件内容 MD5 无法区分同一用户上传同一文件的不同批次，会导致秒传逻辑误判（上次上传失败的文件被当作已完成）
  • 踩坑: 只用文件 MD5 会让用户重新上传失败文件时直接跳过，实际服务端没有完整文件
  • 例外: 全局去重场景（如公共资源库）只需文件内容 MD5

3. 分片上传进度必须分两层计算：分片内字节进度 + 已完成分片数

  • 规则: progressPercent = (upchunk / blockNum * 100) + (chunkprogress.percent / blockNum)
  • 为什么: 只统计已完成分片会导致进度条长时间卡在某个百分比（当前分片上传中），用户误以为卡死
  • 踩坑: 直接用 upchunk / blockNum 会让 100MB 文件分 10 片时，每片上传 10 秒进度条都不动
  • 例外: 分片极小（<1MB）时可以忽略分片内进度

4. 文件类型校验必须在切片前做，不能在切片后或上传时做

  • 规则: 在 add() 方法最开始用 mimeTypes.indexOf(ext) 校验并 return
  • 为什么: 切片是 CPU 密集操作，大文件切片可能耗时数秒，校验失败会浪费计算资源且用户体验差（等了半天才提示格式错误）
  • 踩坑: 在切片后校验会让用户选择 1GB 文件后等 5 秒才看到”格式不支持”
  • 例外: 需要读取文件头魔数校验真实格式时必须在切片后

5. 秒传校验必须在服务端做文件级 MD5 比对，前端只做去重

  • 规则: 前端用 files.findIndex(item => item.md5 === fileMd5) 只防止重复添加，真正秒传逻辑在服务端返回”文件已存在”
  • 为什么: 前端无法知道服务端是否真的有完整文件，只能防止同一批次重复上传；服务端可能因存储迁移/清理导致文件丢失
  • 踩坑: 前端判断”MD5 存在就跳过”会导致服务端文件被误删后用户无法重新上传
  • 例外: 纯前端应用（如 IndexedDB 存储）可以前端做秒传

6. 视频时长获取必须用 Promise 包装 loadedmetadata 事件，不能用 async/await 直接读

  • 规则: 创建 video 元素，监听 loadedmetadata 事件，在回调中 resolve(video.duration)
  • 为什么: video.duration 只有在元数据加载完成后才有值，直接读取是 NaN；大视频文件元数据加载可能需要数秒
  • 踩坑: 直接 const duration = video.duration 永远得到 NaN，因为 src 赋值后元数据还没加载
  • 例外: 已知格式良好的小视频（<10MB）可以加 setTimeout 轮询

7. 分片大小必须根据文件大小动态调整，不能固定值

  • 规则: chunkSize = file.size < 100MB ? 2MB : 5MB，超大文件（>1GB）用 10MB
  • 为什么: 小文件用大分片会导致分片数过少无法利用并发；大文件用小分片会导致请求数爆炸（1GB 文件 2MB 分片需 500 个请求）
  • 踩坑: 固定 2MB 分片上传 5GB 文件会产生 2500 个 HTTP 请求，浏览器并发限制导致上传极慢
  • 例外: 服务端强制要求固定分片大小时（如 OSS 分片上传）

8. 断点续传必须存储”已上传分片索引数组”，不能只存已上传数量

  • 规则: 用 uploadedChunks: [0,1,3,5] 记录，不能只用 upchunk: 4
  • 为什么: 网络不稳定时分片可能乱序成功（第 2 片失败但第 3 片成功），只记数量会导致续传时重复上传已成功分片
  • 踩坑: 只用计数器会让第 2 片失败后，续传时从第 5 片开始（以为前 4 片都成功了），实际第 2 片丢失
  • 例外: 服务端强制顺序上传且会拒绝乱序分片时

9. 取消上传必须同时取消 XHR 请求和清理 FileReader，不能只清状态

  • 规则: 保存 xhr 引用调用 xhr.abort()，同时 fileReader.abort() 并清空 fileChunks 数组
  • 为什么: 只改状态不取消请求会导致后台继续上传浪费带宽；FileReader 不清理会持续占用内存（大文件切片会产生大量 Blob 对象）
  • 踩坑: 点取消后进度条停了但网络面板显示还在上传，内存持续增长最终崩溃
  • 例外: 使用 Fetch API 时用 AbortController 替代 xhr.abort()

10. 组件销毁前必须清理所有 Blob URL 和取消上传，不能依赖 GC

  • 规则: 在 beforeDestroy 钩子中遍历 files 调用 URL.revokeObjectURL(file.cover) 和取消上传
  • 为什么: Blob URL 不会自动释放，会导致内存泄漏；未取消的上传会在组件销毁后继续执行回调报错
  • 踩坑: 切换路由后内存不释放，上传 10 个大文件后切换页面内存占用还是 2GB
  • 例外: 单页应用且组件永不销毁时可以不清理

11. 进度条颜色必须根据状态动态变化，不能固定色

  • 规则: customColor = status === '上传中' ? '#409EFF' : status === '失败' ? '#F56C6C' : '#67C23A'
  • 为什么: 固定颜色无法让用户快速识别上传状态，尤其批量上传时需要一眼看出哪些失败
  • 踩坑: 所有进度条都是蓝色，用户以为都在上传，实际有 3 个已经失败了
  • 例外: 设计规范强制单一颜色时

12. 文件列表必须支持单个删除且删除时取消对应上传，不能只清空全部

  • 规则: deleteFile(index) 中先调用 files[index].cancel() 再 files.splice(index, 1)
  • 为什么: 批量上传时用户可能只想删除某个失败文件重新添加，清空全部会导致其他正在上传的文件也被中断
  • 踩坑: 删除一个文件后其他文件的索引错乱，导致删除第 2 个文件实际删了第 3 个
  • 例外: 明确只支持”全部取消”的简化场景

13. 上传完成后必须校验服务端返回的文件大小，不能只看 HTTP 200

  • 规则: 对比 response.fileSize === file.size，不一致时标记为失败并重传
  • 为什么: HTTP 200 只代表请求成功，不代表文件完整；网络中断、代理截断等会导致服务端收到不完整文件但返回 200
  • 踩坑: 上传显示成功但播放视频时发现只有前半段，服务端实际只收到 60% 数据
  • 例外: 服务端强制校验文件完整性且会返回 4xx 错误时

14. 分片上传失败必须重试当前分片，不能直接标记整个文件失败

  • 规则: 单个分片失败时重试 3 次，3 次都失败才标记文件状态为”失败”
  • 为什么: 网络抖动很常见，单次失败不代表文件无法上传；直接失败会让用户重新上传整个文件浪费已上传分片
  • 踩坑: 上传 1GB 文件到 95% 时一个分片失败，整个文件标记失败，用户重新上传又从 0 开始
  • 例外: 服务端返回 4xx 业务错误（如文件格式不支持）时不应重试

🔥 5 秒必记 5 条

  1. 批量上传必须串行计算 MD5，并行会内存爆炸
  2. 进度 = 已完成分片占比 + 当前分片内进度占比，缺一不可
  3. 文件唯一标识用业务键+属性混合 MD5，不能只用内容 MD5
  4. 断点续传存已上传分片索引数组，不能只存数量
  5. 组件销毁前必须清理 Blob URL 和取消上传，不能依赖 GC

原始问题: [blog] vue2 对比 vue3

Vue2 vs Vue3 核心差异与迁移技能点

场景占位: 组件用 、,数据用 、
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 生命周期钩子在 Vue3 setup 中需显式导入且改名

  • 规则: Vue3 的 setup() 替代 beforeCreate/created,其他钩子加 on 前缀且需从 vue 导入
  • 为什么: setup 在组件实例创建前执行,此时 this 不可用,Vue3 用函数式 API 替代 Options API 避免 this 绑定混乱
  • 踩坑: 在 setup 里写 this.xxx 永远是 undefined,mounted 要改成 onMounted 否则不触发
  • 例外: Vue3 仍支持 Options API 写法,可混用但不推荐(会导致逻辑分散)

2. 响应式初始化从 data() 改为 ref/reactive 且必须 .value 访问

  • 规则: Vue3 用 ref(基本类型) 或 reactive(对象) 替代 data(),ref 在 script 中访问需 .value
  • 为什么: Vue2 的 Object.defineProperty 无法监听新增属性,Vue3 用 Proxy 重写响应式系统,ref/reactive 是显式声明响应式的入口
  • 踩坑: template 中 ref 自动解包不需 .value,但 script 中忘记 .value 会拿到 RefImpl 对象导致判断失效
  • 例外: reactive 对象的属性访问不需 .value,但解构会丢失响应式(需用 toRefs 包裹)

3. 父子通信从 prop+$emit 改为 defineProps+defineEmits 宏

  • 规则: Vue3 setup 中用编译时宏 defineProps/defineEmits 替代 props 选项和 this.$emit
  • 为什么: 宏在编译阶段处理,无需导入且提供更好的 TypeScript 类型推导,避免运行时 this 查找开销
  • 踩坑: defineProps 返回的是响应式对象但不能解构(会丢失响应性),defineEmits 返回函数直接调用即可
  • 例外: Options API 写法仍用 props 配置项和 this.$emit

4. ref 模板引用从字符串改为同名变量声明

  • 规则: Vue3 中 ref=”“ 需在 setup 中声明 const = ref(null) 并返回
  • 为什么: Vue2 的 this.$refs 依赖运行时字符串查找,Vue3 编译时绑定变量提升性能且类型安全
  • 踩坑: 忘记在 setup return 中暴露 ref 变量会导致绑定失败,v-for 中的 ref 在 Vue3 会自动收集成数组
  • 例外: 组合式 API 的 ref 在 onMounted 后才有值,beforeMount 时仍是 null

5. watch 从配置对象改为独立导入函数且默认惰性执行

  • 规则: Vue3 的 watch 需从 vue 导入,默认不立即执行(需配置 immediate: true)
  • 为什么: Vue2 的 watch 选项在组件初始化时就建立依赖,Vue3 按需调用 watch 函数减少初始化开销
  • 踩坑: watch ref 对象需传入 getter 函数 () => .value,直接传 ref 监听不到变化
  • 例外: watchEffect 会立即执行且自动追踪依赖,适合副作用场景

6. 渲染函数从 $mount 改为 createApp 链式调用

  • 规则: Vue3 用 createApp().mount(‘‘) 替代 new Vue({ el })
  • 为什么: Vue2 的全局 Vue 实例会污染原型链,Vue3 的应用实例隔离避免多应用冲突
  • 踩坑: Vue3 移除了 $mount 的返回值链式调用,必须先 createApp 再 mount,且 mount 返回根组件实例而非应用实例
  • 例外: 测试环境可以不 mount 直接操作虚拟 DOM

  • 规则: Vue3 SFC 的
