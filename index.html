# P99 延迟飙升诊断：CPU/内存/QPS 均正常时的系统化根因推演 ## 背景与场景 线上服务 P99 延迟从 50ms 突然飙到 2s，但监控大盘上 CPU、内存、QPS 三项核心指标全部正常。这是一个极具迷惑性的场景——传统的"扩容/重启"本能反应在这里往往无效。核心线索恰恰藏在"三项正常"本身：**不是整体过载，是少数请求被卡住了**。这类问题在微服务架构、数据库密集型后端和 Go/JVM 服务中高频出现，定位不当容易浪费数小时。 --- ## 核心结论 **结论 1：P99 恶化而 P50 正常，锁竞争是第一嫌疑** 锁（DB 行锁、Go `sync.Mutex`、Redis 单线程脚本）的特征就是"少数持锁请求影响大量排队请求"。QPS 越高，尾部排队越长，P99 越烂。先查 `information_schema.innodb_lock_waits`（MySQL）或 `pg_locks`（PG），以及 Go 的 `db.Stats().WaitCount/WaitDuration`。 **结论 2：P99 值恰好等于某个超时配置，大概率是外部依赖问题** P99 ≈ 1s 或 P99 ≈ 2s 且呈"阶梯分布"（不是随机散点），说明是某个 timeout 配置在兜底。常见来源：下游服务偶发慢响应、容器内 DNS `ndots=5` 导致每次域名解析多跑 5 次无效查询。先看 `cat /etc/resolv.conf`，再用 `tcpdump -i any port 53` 抓 DNS 包确认。 **结论 3：GC 暂停在 CPU 指标上是隐形的** Go GC 和 JVM GC 的 Stop-the-World 阶段不计入请求线程的 CPU 时间，但会冻结所有 goroutine/线程。用 `GODEBUG=gctrace=1` 输出 GC 日志，对比 wall time 列与 P99 spike 的时间点是否吻合。Go GC 暂停 >50ms 即需关注。 **结论 4：重启短暂恢复后再度劣化，定性为资源泄漏** goroutine 泄漏或 FD 泄漏的特征是单调增长然后耗尽。访问 `/debug/pprof/goroutine?debug=2`，大量处于 `semacquire` 或 `chan receive` 状态的 goroutine 堆积 = 泄漏确认。goroutine 总数趋势图单调增长也是铁证。 **结论 5：Tracing 瀑布图是最快定位工具，30 秒内缩圈** 在 Jaeger/Tempo 里直接捞 P99 请求的 span 瀑布图。如果某个 span 有大段"空白"（span 存在但没有子 span 覆盖），说明是在等连接池或等锁，而不是真正在执行。这一步通常 30 秒内能把根因从六类缩到两类。 --- ## 实现方案 ### Step 1：用 Tracing 快速缩圈（首选） ### Step 2：DB 锁等待排查 ### Step 3：GC 暂停排查 ### Step 4：Goroutine 泄漏排查 ### Step 5：DNS 超时排查（容器内高发） ### Step 6：网络层排查 --- ## 避坑指南 **坑 1：不要在 P99 spike 时才开始收集数据** pprof block profile 和 goroutine dump 要在问题发生期间采集，之后 goroutine 可能已经退出、锁已经释放，dump 出来是正常状态。正确做法：在 service 里提前埋好 `/debug/pprof` 端点，问题复现时立刻采集，或者配置持续 profiling（如 Pyroscope）。 **坑 2：Go pprof block profile 默认关闭，不提前开启则无法采集** **坑 3：P99 恰好等于超时配置值时，不要只看"下游服务是否挂了"** 下游没挂不代表没超时。超时可能是偶发的（1% 请求慢了 1.9s，刚好没超 2s 超时，但 P99 就是这 1%）。正确的排查是：在 Tracing 里把下游调用的 latency 分位数单独拉出来看，不要只看 P50。DNS 超时尤其容易被忽视，因为它不出现在应用层 Tracing 里（DNS 在 `net.Dial` 里面，Go 标准库默认没有 span）。 --- ## 底层机制 **为什么 CPU/内存/QPS 正常，P99 还能烂？** P99 衡量的是"最慢的 1% 请求"，CPU/内存/QPS 衡量的是"整体均值/总量"。锁竞争的本质是串行化：持锁的请求在 CPU 上正常执行，等锁的请求在内核 futex 上休眠（不占 CPU），但它的 wall time 在增长。99 个请求中有 1 个等了 1.95s，整体 QPS 和 CPU 丝毫不受影响，但 P99 就被这 1 个拉到 1.95s。这就是为什么"三项正常"不代表服务健康，P99/P999 才是用户体验的真实镜像。 GC 暂停的机制类似：Go 的三色标记 GC 大部分工作与应用并发执行，CPU 利用率看起来只是略微升高。但 mark termination 阶段必须 STW（全部 goroutine 暂停），这个暂停时间不会体现在请求线程的 CPU 时间里，却直接叠加到所有正在处理中的请求的 latency 上。一次 200ms 的 STW = 当时所有在途请求各自增加 200ms 延迟，全部打进 P99。

# JumpServer 统一入口：所有机器 22 端口只对跳板机开放 ## 背景与场景 原有运维环境中，多台 Linode/AWS 机器对外开放了 22 端口，依赖 PAM OTP（`libpam-google-authenticator`）做双因子认证。这套方案的隐患在于：OTP 验证在每台目标机上各自配置，自动化脚本无法应答验证码弹窗，且多人共用 root 时 OTP 密钥同一把无法区分操作者。需要一套集中入口：用户只通过 JumpServer 进来，目标机 22 端口不对外暴露，审计日志统一管理。 ## 核心结论 1. **OTP 移到 JumpServer，目标机不再挂 PAM OTP**：JumpServer 自动化登录无法应答目标机的验证码弹窗，双因子在 JumpServer 层（系统设置 → 安全设置 → MFA 全局强制）一次解决。 2. **目标机 sshd 改为纯公钥认证**：`AuthenticationMethods publickey`，同时 `PasswordAuthentication no`、`KbdInteractiveAuthentication no`、`PermitRootLogin no`，写进 `/etc/ssh/sshd_config.d/99-jms.conf`。 3. **三层防火墙同时收紧**：云防火墙（AWS 安全组 / Linode Cloud Firewall）是主要手段，主机 `ufw` 是兜底，两者都把 22 端口来源限制为 `JMS_IP/32`，只靠其中一层不够。 4. **Docker 端口绕过 ufw**：JumpServer 用 Docker 部署，80/443/2222 要靠云防火墙限源，ufw 对这些端口无效。 5. **JumpServer 是新单点，是最高价值目标**：私钥和 `config.txt`（含 `SECRET_KEY`）加密备份，数据库定期备份；`SECRET_KEY` 丢失则托管的凭据无法解密。 ## 实现方案 ### 0. 动手前 ### 1. 安装 JumpServer 首次登录后立即执行： 1. 改管理员密码 2. 系统设置 → 安全设置 → **MFA 全局强制** 3. 配置 HTTPS，证书放 `/opt/jumpserver/config/nginx/cert/` 4. 备份 `/opt/jumpserver/config/config.txt`（含 `SECRET_KEY`） ### 2. 准备 JumpServer 访问目标机的密钥 在 JumpServer 控制台：**账号管理 → 账号模板 → 新建**，用户名 `jmsops`，类型 SSH 密钥，粘贴私钥内容。 ### 3. 在每台目标机上创建账号并放入公钥 ### 4. JumpServer 录入资产与授权 1. **资产管理 → 资产列表 → 创建 Linux 主机**：填 IP、端口 22、账号选 `jmsops` 模板 2. **用户管理**：每人独立账号（解决原手册"共用 root OTP 密钥"问题），强制绑定 MFA 3. **权限管理 → 资产授权**：用户组 → 节点/资产 → 账号 `jmsops` 4. 开启**会话录像**和**命令记录** ### 5. 验证连通（此时 22 端口还未关） **所有目标机验证通过后，才继续下一步。** ### 6. 收紧三层防火墙 #### 第 1 层：云防火墙（主要手段） **AWS 安全组**：入站 22，源改为 `JMS_IP/32`，删除 `0.0.0.0/0`。 **Linode Cloud Firewall 入站规则**： - 允许 TCP 22，来源 `JMS_IP/32` - 入站默认策略：Drop #### 第 2 层：主机防火墙 ufw（兜底） #### 第 3 层：sshd 加固（目标机） 验证实际生效值（`sshd -T` 展示的才是运行时值，不是文件里写的）： ### 7. 最终验证 ## 避坑指南 **1. ufw 对 Docker 端口无效，JumpServer 的 Web/SSH 端口必须在云防火墙收紧** JumpServer 通过 Docker 发布端口（`-p 443:443`），Docker 直接修改 iptables，绕过了 ufw 的 `INPUT` 链。如果只在目标机上加 ufw 规则而没有配云防火墙，80/443/2222 实际对全网开放。正确做法：云防火墙只放行运维固定 IP 访问这三个端口。 **2. 改 sshd 配置后不要 `systemctl restart`，要 `reload`** `restart` 会关闭所有现有 SSH 连接，包括你正在操作的会话。`reload` 让 sshd 重读配置、只对新连接生效，不影响已建立的会话。在改配置未验证时断开会话会有锁出门的风险。操作顺序：`sshd -t`（语法检查）→ `systemctl reload ssh` → 另开新会话验证 → 验证通过后才断旧会话。 **3. JumpServer IP 变化会导致所有目标机全部失联** 所有云防火墙和 ufw 规则都基于 `JMS_IP/32`。如果 JumpServer 机器重启、浮动 IP 漂移或迁移，22 端口白名单失效，只能靠带外控制台救援。部署前务必绑定固定 IP（Linode 的 Static IP、AWS 的 EIP），并在密码管理器里记录带外控制台入口。 ## 底层机制 **为什么原 PAM OTP 和 JumpServer 不兼容**：JumpServer 的 SSH 组件（koko）以自动化方式登录目标机，它持有私钥，登录时走 `publickey` 认证通道，整个流程没有人工交互。而 PAM `pam_google_authenticator.so` 要求在 `keyboard-interactive` 通道里弹出验证码提示并等待用户输入。两者相遇的结果是：koko 收到验证码提示但不知道如何应答，直接返回 `Permission denied`，表现为原手册的坑点 1/2。解决方式是把 OTP 层上移到 JumpServer 本身——用户登录 JumpServer 时完成 MFA，之后 JumpServer 对内部目标机的连接走纯公钥，完全自动化。 **三层防火墙的分工**：云防火墙（安全组/Cloud Firewall）在数据包到达虚拟机网卡之前就丢弃，是主要隔离手段，完全不依赖目标机的操作系统状态；ufw 在操作系统 iptables 层过滤，是系统被入侵后的最后一道防线；sshd 配置（禁密码、仅公钥）是认证层面的加固，三者功能互补，不可互相替代。

# Redis `max number of clients reached` 排查与连接池收敛 ## 背景与场景 生产环境 Redis 实例报 `max number of clients reached`，服务新建连接被拒绝。根因不是 `maxclients` 配置太小，而是项目内多处独立创建 `redis.NewClient` 且未调优池参数，叠加 mini / worker 多实例后连接总数超限。需要先确认泄漏源，再把分散的 client 收敛成共享单例并显式管控池参数。 --- ## 核心结论 1. **先诊断再止血**：用 `redis-cli CLIENT LIST` 聚合 IP 和 idle 时长，确认泄漏来自哪个服务，`CONFIG SET maxclients` 只是临时手段。 2. **go-redis 默认池 = 10×CPU 核数**：未显式设 `PoolSize` 时，每个 `redis.NewClient` 都会开出 `10×GOMAXPROCS` 个连接，多进程叠加容易打满。 3. **共享单例 + SSOT 构造函数**：项目内所有 client 应合并为一个，走 `shared/` 下的统一入口，显式设 `PoolSize`、`MinIdleConns`、`ConnMaxIdleTime`。 4. **`ClientName` 是唯一可观测点**：设置 `ClientName` 后，`CLIENT LIST` 能直接定位来源服务，不设则 IP 聚合也看不清。 5. **服务端两个必设参数**：`timeout 300`（服务端主动断空闲连接）+ `tcp-keepalive 60`（探活），这两个参数不设，客户端泄漏的连接会一直挂着。 --- ## 实现方案 ### 第一步：诊断连接状态 ### 第二步：临时止血 ### 第三步：代码层修复（以 shanggu 仓库为例） **当前泄漏点**： | 文件 | 问题 | |---|---| | `internal/memory/hubu.go:38` | 独立 client，PoolSize 20 | | `internal/adapter/zhukesi/chat_cache.go:51` | 独立 client，默认池（10×CPU核数） | | `internal/registry/llm/semantic_cache.go:70` | 独立 client，无池参数 | | `internal/registry/llm/gemini_usage.go:36` | 独立 client，无池参数 | **修复：收敛为共享单例** 其余各处改为： ### 第四步：服务端 redis.conf 补全 系统层： --- ## 避坑指南 **1. `CONFIG SET maxclients` 受 `ulimit -n` 上限约束，调大无效** Redis 建连时调用 `accept()`，受操作系统 fd 数限制。如果 `ulimit -n` 是 4096，`CONFIG SET maxclients 20000` 不会生效，Redis 启动日志会有 `You requested maxclients of X requiring at least Y max file descriptors` 警告。先调 `ulimit`，再调 `maxclients`。 **2. 不要在请求路径或循环里 `redis.NewClient()`** 每次调用都会创建新的连接池，函数返回后 client 若不显式 `Close()`，连接池不会回收。高 QPS 下几轮请求就能打满连接数。正确做法是进程启动时一次性初始化，全局复用。 **3. Pub/Sub 和 `BLPOP` 是独占连接，不走池** go-redis 的 Pub/Sub 和阻塞命令（`BLPop`、`BRPop`）各自持有一个独占连接，不归连接池管理。如果有 goroutine 泄漏或 context 未取消，这类连接不会被 `ConnMaxIdleTime` 回收，只能靠服务端 `timeout` 或重启清理。审查代码时需单独排查这两类模式。 --- ## 底层机制 go-redis 的连接池实现是惰性建连：`redis.NewClient` 本身不建连，第一次执行命令时才从池里取或新建连接。`PoolSize` 是每个 client 实例的上限，而非全局上限——这是多 client 实例共存时容易踩的坑：4 个 client 各自默认池（假设 10×4核=40），就是 160 个潜在连接，再叠上 mini/worker 两个进程，总数直接 320+，远超预期。 Redis 服务端的 `maxclients` 是全局值，所有来源的连接共享这个上限。连接到达上限后，新的 `accept()` 直接返回错误，客户端收到 `ERR max number of clients reached`，表现为请求立即失败而非超时排队。因此这类故障来得突然，需要在监控层提前对 `connected_clients / maxclients` 比值设告警（建议 > 80% 告警）。

# Claude 拒绝响应的分类处理:误拒可解、真拒勿绕、本地当兜底 ## 背景与场景 在把 Claude 接入安全研究/漏洞挖掘工作流时,团队遇到了"Claude 被拒怎么办"的问题。场景是:用 Claude 辅助授权 pentest、漏洞 triage、代码审计,偶尔触发拒绝,工程上想知道该怎么设计后备路径。这是一个典型的"工具可用性 vs 安全边界"的架构决策问题。 --- ## 核心结论 1. **Claude 的拒绝分两类,处理方式完全不同**:误拒(授权合法活被过度谨慎拒)有解;真拒(武器化 exploit / 打未授权目标)是正确行为,不绕。 2. **误拒的三条正规解法**:① 给授权上下文("这是我自己的系统 / bounty scope 是 X");② 脱敏泛化——抹目标信息、问技术本身再本地套用;③ 换问法——"怎么分析/检测/复现"而不是"帮我写武器化 exploit"。 3. **本地未审模型(MLX/Ollama)的定位是 availability 兜底,不是"做 Claude 不肯做的事"的出口**:Claude 误拒或临时挂,本地接着答保流程不断线;但这是降级保可用,不是绕过安全边界的机制。 4. **授权挖洞的大头价值(分析/审计/triage/方法论)Claude 几乎不拒**:真正被拒的窄片(武器化/未授权)本就不是 bounty 价值所在,还踩法律线。可用性压力远小于预期。 5. **不要把系统设计成"云拒就甩本地"的绕过管线**:这条架构决策影响的是系统的法律责任边界,不只是技术问题。 --- ## 实现方案 ### 场景一:误拒 — 给授权上下文 关键点: - 明确说明"授权"/"自己的系统"/"bounty scope" - 把真实目标域名/IP 从问题里移除 - Claude 对**授权**安全研究配合度很高:代码审计、CVE 原理、复现方法、检测规则、CTF 全做 --- ### 场景二:误拒 — 换问法 同一个漏洞,不同角度问,结果不同: | 问法 | Claude 是否响应 | |------|----------------| | "帮我写武器化 exploit" | 拒 | | "这个洞的原理是什么" | ✅ | | "怎么在测试环境复现" | ✅ | | "怎么写检测规则" | ✅ | | "POC 和 weaponized exploit 的区别" | ✅ | --- ### 场景三:availability 兜底架构(正确设计) **这个架构的设计约束**: - 本地模型是 **availability** 兜底,处理的是"Claude 临时挂了"或"轻度误拒"场景 - 本地模型**不是**"云拒就换它做"的绕过出口 - 实现上:在意图判断层做路由,而不是在响应层做"拒了重试本地" --- ### shanggu 现有实现参考 `pentest-lookup` 的双脱敏方案已落地: 1. 用户输入 → 意图识别层捕获 pentest 类请求 2. 双脱敏处理:抹域名/IP/具体目标,保留技术关键词 3. 泛化后的技术问题 → Gemini 分析 → 返回原理/方法论层答案 4. 用户本地套用到具体目标 这条路径避开了敏感目标信息上云的问题,同时保证了分析质量。 --- ## 避坑指南 **1. 不要把"本地接住"设计成隐式绕过** 如果路由逻辑是"Claude 拒 → 自动转本地未审模型继续做同样的事",这个管线在架构上等于设计了一条绕过 Claude 安全边界的通道。哪怕本地模型自己也会拒,**这个设计意图**本身在法律/合规层面有问题。正确的降级是:Claude 挂了/超时/配额满 → 本地接;Claude 主动拒 → 要么换问法、要么就是不该做。 **2. 不要低估授权上下文的效果** 很多人在触发拒绝后直接判定"Claude 不能做这类事",但大量情况是措辞触发了过度谨慎。先试授权上下文 + 脱敏,再下结论。Claude 对合法安全研究的配合度比一般认知高很多。 **3. 真拒的边界不要去测** 武器化 exploit、未授权目标、大规模自动化打点 —— 这窄片云拒是正确的。尝试绕过云拒(换 prompt / 换模型 / 拆分请求)的收益几乎是零(这类活本就不是 bounty 价值所在),风险是实打实的法律责任。时间投入应该放在授权范围内的高质量分析上。 --- ## 底层机制 Claude 的拒绝判断不是关键词过滤,而是对**意图 + 上下文**的综合评估。同样是"SQL 注入 payload",问"这类漏洞的技术原理"和"帮我打 target.com"的意图信号完全不同,前者几乎不会触发拒绝。这就是为什么授权上下文和换问法有效 —— 它们改变的是请求的**意图信号**,而不是在绕过什么机制。 本地模型(MLX Qwen3-Coder / Ollama)作为兜底的价值来自于它的**可用性**:不依赖网络、不受云端限速、不受 Claude 配额约束。但它的知识面和推理深度与 Claude/Gemini 有实质差距。把它定位为"断网时能继续跑"而不是"高质量分析的替代品",是符合实际能力边界的。
