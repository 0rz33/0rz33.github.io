# Flutter 嵌套导航重排:把 showDialog 弹框"扶正"成 Tab 页 ## 背景与场景 shanggu 是一套自用移动端 AI 终端 App(Flutter)。早期「CLI 档」只有一个 SSH 终端,Claude 会话通过绿机器人按钮触发 `showDialog` 弹出。随着弹框功能越来越重(状态上色、删除确认、流式聊天、历史加载),弹框变成了一个藏在二级入口的完整页面,导航层级错乱、用户路径多跳。本次重排的目的是**纯结构性搬迁**:把弹框里的内容提升为顶层 tab,不改任何功能逻辑。 ## 核心结论 1. **旧结构的根本问题是"功能藏在弹框里"**:`showDialog` 只是一个临时 overlay,不适合承载有状态的流式聊天和项目列表——切换/返回会丢状态,且缺乏返回导航语义。 2. **`IndexedStack` 是 Flutter 多 tab 保活的标准做法**:三个子 tab(`CLI` / `Chat` / `Code`)全部放进 `IndexedStack`,切 tab 时 widget 不 unmount,SSH 连接不断、聊天流不中断、列表不重拉。 3. **把 `_ClaudeSessionPicker` 的 body 抽成可嵌入 widget 是最小改动路径**:只抽 UI 层(`ClaudeSessionsPanel` / `ClaudeProjectsPanel`),删掉 `showClaudeSessionPicker` 入口函数,原来的状态逻辑、API 调用、回调全部原封不动。 4. **`/cli/` 路径在 `.gitignore` 里,新文件必须 `git add -f`**:不加会导致文件不进 commit,PR 看起来只有删改没有新增。 5. **Code tab 独立后凭据入口发生了变化**:旧 Code 嵌聊天时默认复用 CLI tab 的 SSH 会话;新结构中 Code 是独立 tab,首次点项目需主动弹 `promptSshCredentials` 获取凭据——这是结构性变化带来的**必要新行为**,不是 bug。 ## 实现方案 ### 1. 新增三 tab 容器 `mobile_worker_screen.dart` **核心行**:`IndexedStack` 而非 `PageView` 或条件渲染——保证 SSH 终端不因切 tab 而断连。 ### 2. 修改顶层壳 `mobile_home_shell.dart` 顶部 `Chat`(shanggu AI 对话)完全不动。 ### 3. 拆 `ai_terminals_screen.dart`:抽两个可嵌入面板 **关键约束**:只改容器边界,不碰以下逻辑: - 项目行的 `BorderSide` 颜色映射(状态上色) - `showDialog(ConfirmDelete...)` 确认弹框 - 流式聊天的 `StreamBuilder` + `ScrollController` - `loadHistory()` 进入时预拉历史 - 聊天视图的「返回列表」按钮 ### 4. 移除 `MobileCliScreen` 里的机器人入口 ### 5. git add -f 处理 gitignore ## 避坑指南 **1. Code tab 凭据入口变化须告知用户** 旧结构下,Code 嵌聊天时 `promptSshCredentials` 从未显式弹出——因为用户总是先在 CLI tab 建立 SSH 会话,Code 弹框复用了同一 context。新结构 Code 是独立 tab,没有隐式继承的 SSH 会话,首次点击项目**会弹凭据框**。这不是回归,但如果用户实测时没心理准备会以为出了 bug。PR 描述里必须明确标注。 **2. 不能用 `PageView` 替代 `IndexedStack`** `PageView` 默认懒加载——切到第三页时前两页 widget 可能被回收,SSH 连接断掉、聊天 `StreamController` 关闭。`IndexedStack` 一次性 mount 所有子树并保持存活,代价是稍高的初始内存,对三个 tab 完全可接受。 **3. 整树 analyze 要注意范围** `flutter analyze` 在 `cli/app/app/` 下只分析本 package。如果在 repo 根运行会扫其他 package 的遗留告警,容易误判为本次引入。本次改动的 5 个文件单独 analyze **No issues found**;全量 analyze 剩余 10 条均在其他文件、无 error,不属于本次责任范围。顺手清掉的既有告警(`r1`/`tab`/`__`/死代码 `_SettingsPage`)属于无害清理,不影响行为。 ## 底层机制 Flutter 的 `showDialog` 在路由栈上压一个 `DialogRoute`——它本质上是一个独立的路由页,自带自己的 `BuildContext` 和生命周期。放在 `Dialog` 里的 `StatefulWidget` 在 `Navigator.pop` 时会 unmount 并 dispose,所有本地状态(滚动位置、缓冲的流数据、SSH 会话引用)全部丢失。这就是为什么「弹框承载重状态」是反模式:每次关闭再打开等于重置一遍。 把内容移进 `IndexedStack` 之后,widget 树从 overlay 层落入了主路由的 widget 树,生命周期绑定到整个 `MobileWorkerScreen` 的存活周期。只要用户没有退出 Worker 大 tab,三个子 tab 的状态永远保活。这也是为什么这次重排在功能上是**纯收益**:不仅导航路径变短,状态稳定性也同步提升。

# OpenResty + Certbot 多域名 SSL 自动化：三条路的选型与实现 ## 背景与场景 在 SEO 卫星站场景下，业务要求频繁上线新域名（每批少则数个、多则数十个），每次都需要手动三步操作：改 nginx vhost 配置 → 执行 `certbot --nginx -d xxx` → `nginx -s reload`。随着站点规模增长，手工操作变成瓶颈，需要一套自动发证 + 自动配置的机制。当前环境：OpenResty 跑 443 端口按 `server_name` 分流，certbot 已在 VPS 上，`seo.a3owc.com` 和 `hub.daslgwni.top` 均已用 certbot 签发证书。 ## 核心结论 1. **不改架构的最小方案（方案 A）**：后端暴露 `GET /api/satellites/manifest` 返回所有启用域名列表，VPS 上跑 `sync-satellites.sh` 轮询该接口、自动生成 vhost + 签证书 + reload。权限干净，容器不碰 nginx。 2. **方案 A 的关键顺序约束**：ACME HTTP-01 挑战必须先有 nginx vhost 把 `/.well-known/acme-challenge/` 路由对，才能让 Let's Encrypt 回调验证。脚本必须**先写 vhost、再调 certbot**，顺序不可反。 3. **Caddy on-demand TLS（方案 B）** 是长期最优：一行 `on_demand_tls { ask ... }` 配置，新域名 DNS 指向服务器后自动签发、零手动干预。代价是引入新组件，需设计 `openresty → caddy → upstream` 的双 proxy 链路。 4. **DNS-01 + Cloudflare API（方案 C）** 彻底与 nginx 解耦：`certbot --dns-cloudflare` 插件不依赖 vhost 存在，支持通配符 `*.yourdomain.com`，但要求所有域名托管到 Cloudflare 且服务器持有 CF API token（权限收敛到 `Zone:DNS:Edit`）。 5. **DNS A 记录是所有方案的前提**：域名注册商控制台的 A 记录指向，无论哪条路都无法绕过，除非所有域名全托管到 CF 并给后端 API token。 ## 实现方案 ### 方案 A：后端清单 + 服务器端脚本（推荐起步） **Step 1：后端加 manifest 接口** **Step 2：编写 `scripts/sync-satellites.sh`** **Step 3：加 cron** --- ### 方案 B：Caddy on-demand TLS（长期方案） 在 `Caddyfile` 中加： 后端实现 `/api/satellites/check`：域名在启用列表里返回 `200`，否则 `403`，Caddy 只对 `200` 的域名自动签发。 OpenResty 侧将卫星域名流量 proxy 到 Caddy（以免改动 admin panel 的现有配置）： --- ### 方案 C：DNS-01 + Cloudflare ## 避坑指南 **1. HTTP-01 挑战顺序陷阱（方案 A 最常踩）** 错误做法：直接调 `certbot --nginx -d xxx` 而没有先写好 vhost。 表现：`certbot` 返回 `Connection refused` 或 `404`，Let's Encrypt 无法访问 `/.well-known/acme-challenge/`，签发失败。 正确顺序：**写 vhost → `nginx -s reload` → certbot**，三步缺一不可。 **2. certbot `--expand` vs 单独签发** `--expand` 会把新域名追加到已有证书的 SAN 列表里，导致证书越来越大、续签时所有域名必须同时在线可达。卫星站场景下建议**每个域名单独签发独立证书**，避免一个域名 DNS 失效拖垮全部续签。 **3. Caddy on-demand TLS 必须有 `ask` 鉴权** 不加 `ask` 直接开 on-demand，任何 SNI 请求都会触发自动签发，会瞬间打爆 Let's Encrypt 频率限制（同 IP 每小时 5 个失败请求限制，每注册域名每周 50 张证书）。`ask` 接口必须严格白名单，不能返回 `200` 给未知域名。 ## 底层机制 **ACME HTTP-01 挑战的工作流**：客户端（certbot）向 Let's Encrypt CA 请求签发 → CA 下发一个 token → 客户端把 `token:thumbprint` 写到服务器的 `/.well-known/acme-challenge/` 路径 → CA 通过 HTTP 访问该 URL 验证控制权 → 签发证书。这意味着 **nginx 必须在挑战期间能响应该路径**，所以 vhost 必须先于 certbot 存在，reload 也不可省略（nginx worker 重载前新 `server_name` 不生效）。 **Caddy on-demand TLS 的 TLS 握手拦截机制**：Caddy 在 TLS ClientHello 阶段拦截 SNI，调用 `ask` 接口确认该域名是否被授权，通过后异步触发 ACME 流程并缓存证书。首次握手会有 2-5 秒延迟（等证书签发），此后命中缓存毫秒级响应。这与 HTTP-01 的"先有 vhost"约束完全不同——Caddy 在 TCP 层就介入，不依赖任何预配置路由。

# 前台优先门：用进程级 inflight 计数治本地 LLM 生成慢 ## 背景与场景 mac-mini M4 16GB 是 shanggu 的本地推理节点，只跑单个 7B 模型（MLX/Ollama 各一路），内存预算极紧。用户反馈「发完一条消息、下一条明显卡顿」。最初怀疑夜间蒸馏/探活任务抢资源，全量排查后发现假设错误——真凶是 **Layer A pattern sink**：每条 chat 结束后起 goroutine 直连本地 HTTP 跑 `qwen3:4b` 做模式沉淀，前后台共用同一个推理入口，前台 chat 请求打到已被后台占满的 MLX/Ollama 进程上，表现为「发完卡 1-2 秒才开始回复」。 此 PR（`ai-agent#314`，分支 `claude/sleepy-hofstadter-7824ee`）借鉴 linger 项目的「前台优先调度」思路，在进程层引入零锁、非饿死的前台让路门，7 文件 +317/-1 行。 --- ## 核心结论 **1. 夜间任务根本不碰本地模型，排查生成慢不要怀疑它们。** `nightly-reflect`/`nightly-expand`（`CloudGenerate`/claude-CLI）、brain consolidate（Haiku）、subscription sentinel（claude-CLI）、llm probe（Gemini Flash）、红队 review（Gemini→Haiku）全走云端路由；`nightly-prune` 是纯 DB 写。 **2. 真正和前台 chat 抢本地 7B 的只有两路。** ① `internal/agent/pattern/pattern.go` 的 `Sinker.Sink`——每条 chat 完成后异步调本地模型，**头号元凶**；② Gemini 配额耗尽时 `internal/adapter/zhukesi/http_background.go:301` 的 `GenerateLocal` 兜底——偶发低频。 **3. 前台优先门核心数据结构：inflight 计数 + lastActive 时间戳。** 新文件 `internal/shared/fg_gate.go`：一个 `atomic.Int32` inflight 计数 + `atomic.Int64` lastActive UnixMilli，前台生成时 `MarkForegroundBusy()`，后台入口调 `WaitForForegroundIdle()` 轮询让路，封顶 `FG_PRIORITY_MAX_WAIT_MS`（默认 120s）不饿死。 **4. 挂点只有四处，前台路径零延迟零锁。** `mlx.go:GenerateStream`、`ollama.go:streamGenerate`（各覆盖 Generate+Stream 两路）、`pattern.Sink` 入口、crawler 本地兜底入口。`accelerator.go` 预热 ctx 打 `WithBackground` 标。云端 chat 不经本地推理路径，完全不受影响。 **5. 全部 env 开关，默认开启。** `FG_PRIORITY`（0 关）、`FG_PRIORITY_COOLDOWN_MS`（6000）、`FG_PRIORITY_MAX_WAIT_MS`（120000）、`FG_PRIORITY_POLL_MS`（250）。 --- ## 实现方案 ### 1. `internal/shared/fg_gate.go`（核心，零外部依赖） ### 2. 前台挂点：`internal/registry/llm/mlx.go` `ollama.go:streamGenerate` 完全对称，不赘述。 ### 3. 后台挂点：`internal/agent/pattern/pattern.go` crawler 兜底（`http_background.go:GenerateLocal`）同理。 ### 4. 预热打标：`internal/registry/llm/accelerator.go` ### 5. 验证命令 --- ## 避坑指南 **1. 不要用互斥锁替代 inflight 计数** 互斥锁会让前后台完全串行——后台拿锁后，前台必须等它跑完整个推理（可能 10-30s）才能开始。inflight 计数 + cooldown 是「让路」而非「阻塞」：前台永远不等后台，后台等前台。两者语义截然不同，误用互斥锁反而让前台体验更差。 **2. `TestDispatchRemote_LocalPath` 偶发失败与此 PR 无关，不要因它卡合入** 该测试查真实 Ollama `/api/ps` 判断常驻显存 vs 30% RAM 预算，在两个 session 同跑时内存紧张会失败。关掉前台门（`FG_PRIORITY=0`）照样失败——环境相关，实锤非此 PR 引入。 **3. embed / placement-bench / pentest cascade 不纳入门控** embed 耗时极短（向量化，毫秒级），placement-bench 是独立进程，pentest cascade 触发极罕见。过度纳入会让门控逻辑变重，违反「初阶别过度工程」原则。只管头号元凶 pattern sink 和 crawler 兜底，够用。 --- ## 底层机制 **为什么 cooldown 比 `inflight=0` 更重要** MLX 的流式推理增量写管道，inflight 计数在 `GenerateStream` 完整 stream 结束才通过 `defer` 归零。但即便 stream 结束，MLX 进程的 GPU/ANE 权重释放有几百毫秒尾部。cooldown（默认 6000ms）确保模型权重从加速器缓存中完全腾出后，后台任务再上。如果只判断 `inflight=0`，后台可能在前台最后一个 token 刚输出的瞬间插进来，依然产生抖动。 此外，agent loop 多轮推理之间存在自然间隙：前一轮 stream 结束，下一轮 prompt 还没打过来，`inflight` 瞬间为 0。cooldown 窗口覆盖了这段间隙，防止后台在两轮之间抢入再让下一轮前台请求延迟。这是 `fgLastActive` 时间戳的核心用途。 **为什么后台不饿死** `maxWait`（默认 120s）是安全网：用户持续聊天时，pattern sink 不可能永远等——超时后强制放行。实践中 6s cooldown + 自然发消息停顿（通常 3-10s）的场景，后台几乎不会等超过 15s。极端情况（用户连续快速发 100 条）下，后台最多积压 120s 后批量执行，不影响前台体验，KB 质量也不会因延迟降级。

# Cloudflare Tunnel 替代 DNS 切换实现 MMS 支付系统双机热备 ## 背景与场景 MMS 支付系统单点部署在 `139.162.39.128`，新增 site4（`172.104.51.20`）作备机，需要对支付 API、收银台、管理后台、演示站四个生产域名实现自动故障切换。传统做法是改 DNS A 记录或双 A round-robin，但两种方案都有硬伤：TTL 等待（最快 60s）、故障时客户端仍有概率命中故障节点、真实 IP 对外暴露。本文记录用 Cloudflare Tunnel 替代传统 DNS 切换的完整实施路径，实现毫秒级故障转移且服务器不暴露公网 IP。 --- ## 核心结论 1. **同一 Tunnel Token 可在多台服务器同时运行**：两台服务器都跑同一个 Token 的 cloudflared，Cloudflare 视为同一 Tunnel 的两个 connector，自动做健康检测和故障转移，这是实现双机热备的关键机制。 2. **DNS 切换由 Cloudflare 控制面完成，不依赖 TTL**：域名绑定 Tunnel 后，DNS 记录变成 CNAME 指向 `.cfargotunnel.com`，故障时 Cloudflare 毫秒级感知 connector 断开，立即停止路由，客户端无感知。 3. **服务器零入站端口**：cloudflared 主动向 Cloudflare 边缘建立出站长连接（QUIC/HTTP2），服务器不开任何入站端口，真实 IP 完全不可见。 4. **迁移分四阶段，生产 DNS 变更是最后一步**：建 Tunnel → 两台接入 → 测试域名验证 → 验收后统一切换 Public Hostname，全程不影响生产流量。 5. **Docker 部署加 `--network=host` 才能访问宿主机端口**：cloudflared 容器内的 `localhost` 是容器自身网络，服务跑在宿主机时必须加 `--network=host` 或改用宿主机网关 IP `172.17.0.1`。 --- ## 实现方案 ### 阶段一：Cloudflare 控制台创建 Tunnel（运维操作） 1. 登录 `dash.cloudflare.com` → 选 `a3owc.com` 账号 2. **Zero Trust** → **Networks** → **Tunnels** → **Create a tunnel** - Connector 类型：**Cloudflared** - Tunnel 名称：`mms-ha` 3. 安装方式选 **Docker**，页面生成命令含 Tunnel Token： **将 Token 通过密码管理工具私下交给开发，不要在公开频道传输。** --- ### 阶段二：两台服务器接入同一 Tunnel（开发操作） 在 `139.162.39.128` 和 `172.104.51.20` **各执行同一条命令**： 两台服务器跑同一 Token → 同一 Tunnel → Cloudflare 自动轮询两个 connector，任意一台下线流量自动切到另一台。 --- ### 阶段三：测试域名验证（不动生产 DNS） 在 Tunnel 的 **Public Hostname** 标签页添加临时测试域名： 验证两台服务器均能通过该测试域名正常响应后，进入下一阶段。 --- ### 阶段四：验收通过后统一切换四个生产域名（运维操作） 在 Tunnel **Public Hostname** 标签页添加四条记录： | Domain | Service | |--------|---------| | `mms-api.a3owc.com` | `http://localhost:支付API端口` | | `guodong.a3owc.com` | `http://localhost:收银台端口` | | `zqadmin.a3owc.com` | `http://localhost:管理后台端口` | | `zqpay.a3owc.com` | `http://localhost:演示站端口` | Cloudflare 自动将 DNS 改为： 原 A 记录（`139.162.39.128`）由 Cloudflare 自动替换，无需手动删除。 --- ## 避坑指南 **1. 不要在验收前改生产 DNS，也不要同时挂两个 A 记录** 双 A round-robin 不等于热备。DNS 层面没有健康检查，故障时客户端仍有概率（取决于本地 TTL 缓存）命中故障节点，且切换最快也要等 TTL 过期（60s 起）。Cloudflare Tunnel 的切换在控制面主动探测，与 TTL 完全无关。 **2.
