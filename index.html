Ollama 本地大模型运行框架：从部署到生产级 MCP 集成实践

一、背景：为什么需要本地化大模型推理能力

在云原生架构演进过程中，SRE 团队面临三个核心痛点：数据主权合规（金融/医疗行业禁止敏感数据出境）、API 成本控制（GPT-4 API 月账单可达数万美元）、推理延迟优化（跨洋 API 调用 P99 延迟 >2s）。Ollama 作为轻量级本地推理框架，通过 Go 实现的高效模型加载器和统一 REST 接口，解决了传统方案的三大问题：PyTorch 环境依赖复杂、CUDA 版本冲突频发、多模型切换需重启服务。

典型场景包括：CI/CD 流水线中的代码审查（需要 7B 模型实时分析 diff）、Kubernetes 集群的智能告警降噪（需要本地 3B 模型做日志聚类）、离线环境的文档问答系统（需要完全断网运行 13B 模型）。相比 vLLM 的高并发优化或 Text-generation-webui 的 UI 友好性，Ollama 的核心优势在于零配置启动和跨平台一致性（macOS Metal、Linux CUDA、Windows DirectML 使用相同命令）。

从架构视角看，Ollama 本质是模型运行时的标准化抽象层，类似容器技术对应用运行时的封装。其设计哲学遵循 Unix 哲学：单一职责（仅负责模型推理）、管道友好（stdin/stdout 可直接对接脚本）、可组合性（通过 HTTP API 与任意语言栈集成）。这使得 SRE 可以像管理 Nginx 一样管理 LLM 服务，而无需深入 Transformer 架构细节。

五、常见陷阱与排错指南

5.1 模型加载失败：GGUF 格式不兼容

现象：ollama run 报错 incompatible quantization version
根因：Ollama 0.1.x 仅支持 GGUF v2，HuggingFace 部分模型使用 v3 格式
解决：使用 llama.cpp 工具转换格式

预防：优先使用 Ollama 官方模型库（ollama pull），自定义模型需验证 GGUF 版本（file model.gguf | grep GGUF）。

5.2 推理速度异常慢：CPU Fallback 未察觉

现象：7B 模型推理耗时 >10s/token（正常应 <0.1s）
诊断：检查 Metal/CUDA 是否正确启用

根因：常见于 Docker 部署时未传递 GPU 设备（缺少 --gpus all）或驱动版本不匹配
解决：重新创建容器并挂载 GPU；macOS 需确保 Xcode Command Line Tools 已安装（Metal 依赖）

5.3 内存溢出：模型量化配置错误

现象：ollama run 触发 OOM Killer，系统日志显示 Out of memory: Killed process
根因：未使用量化模型或量化位数过高（如 16-bit 模型在 8GB 内存机器运行）
解决：切换到 4-bit 量化版本

预防：生产环境强制使用量化模型，通过 Modelfile 锁定版本（FROM llama3.2:7b-q4_0）；配置 cgroup 内存限制（docker run -m 8g）触发优雅降级而非 OOM。

5.4 微调后模型退化：灾难性遗忘

现象：微调后模型在特定任务表现提升，但通用能力显著下降（如无法回答常识问题）
根因：训练数据分布单一 + 学习率过高导致覆盖预训练知识
解决：混合通用数据集训练

预防：使用 LoRA 而非全量微调（保留主干参数）；设置较小学习率（5e-5 而非 1e-4）；每 500 步在验证集评估通用能力（MMLU benchmark）。

5.5 API 调用超时：流式输出未启用

现象：长文本生成时客户端超时（如生成 2000 token 文档）
根因：使用同步 API 等待完整响应，超过 Nginx/LB 的 proxy_read_timeout
解决：启用 Server-Sent Events 流式输出

预防：客户端库默认启用流式（如 langchain-ollama 的 streaming=True）；监控 P99 延迟并设置合理超时（建议 120s）。

原始问题: [blog] Linux命令

Linux 系统运维核心命令体系与生产实践

一、背景：为什么 SRE 必须精通 Linux 命令体系

在现代云原生架构中，无论是容器编排平台（Kubernetes）还是传统虚拟机集群，底层操作系统仍然是 Linux。当生产环境出现 CPU 飙升、内存泄漏、磁盘 I/O 瓶颈或网络丢包时，GUI 监控工具往往只能提供表象数据，真正的根因分析必须依赖命令行工具深入内核层面。典型场景包括：容器 OOM Killed 需要通过 dmesg 和 journalctl 追溯内核日志；微服务间调用超时需要用 ss 和 lsof 排查 TCP 连接状态；数据库慢查询可能源于磁盘 IOPS 耗尽，需结合 iostat 和 sar 定位。

Linux 文件系统层次标准（FHS）定义了关键目录的职责边界：/var/log 存储应用日志但会快速膨胀导致磁盘满；/proc 和 /sys 是内核暴露的虚拟文件系统，实时反映进程状态和硬件信息；/etc 保存配置文件，误操作可能导致服务无法启动。理解这些目录的语义是故障排查的基础，例如当 df -h 显示根分区使用率 100% 时，需要快速定位是 /var/log 日志堆积还是 /tmp 临时文件未清理。

生产环境的复杂性在于多租户、高并发和分布式特性。单个节点可能运行数百个容器，进程树深度超过 10 层；网络拓扑涉及 VXLAN 隧道、iptables 规则链和 BGP 路由；存储层可能是 Ceph 分布式存储或云厂商的块存储服务。这要求 SRE 不仅会用命令，更要理解命令背后的系统调用、内核机制和性能开销，避免在高负载时执行 find / 这类会触发全盘扫描的操作。

二、诊断步骤：只读命令的黄金 5 分钟

故障响应的第一原则是 非侵入式观测，避免执行任何可能改变系统状态的操作。标准诊断流程从全局视图开始，逐步聚焦到具体资源：

针对特定异常的深度诊断需要结合多个维度。例如应用响应慢，先用 sar -u 1 10 确认 CPU 是否存在 %iowait 高企（表示等待磁盘 I/O），再用 pidstat -d 1 定位具体进程的读写速率，最后通过 lsof -p <PID> 查看该进程打开的文件描述符，判断是否在频繁读取大文件或等待网络 socket。

内存问题的诊断需要区分物理内存不足与内存泄漏。free 命令的 available 列才是真实可用内存（包含可回收的 cache），而 used 列包含了文件系统缓存。若 available 持续下降且伴随 si/so（swap in/out）非零，说明发生了页面交换，需用 vmstat 1 监控交换频率，并通过 smem -tk 或 pmap -x <PID> 分析进程的 PSS（Proportional Set Size）内存占用。

对于生产数据库或存储服务，需要验证备份的完整性。例如备份 MySQL 配置后，应执行 mysqld --help --verbose | grep -A1 'Default options' 确认配置文件路径，并用 diff 对比备份文件与当前文件的差异。LVM 快照是文件系统级备份的利器，可在秒级创建一致性快照：lvcreate -L 10G -s -n snap_root /dev/vg0/root。

四、常见坑：生产环境的 5 个典型陷阱

4.1 误判：df 与 du 的数据不一致

现象：df -h 显示磁盘使用 90%，但 du -sh /* 累加后只有 50%。根因是进程持有已删除文件的文件描述符，磁盘空间未释放。诊断命令：lsof | grep deleted，找到对应进程后需重启服务或发送 kill -HUP 信号触发日志轮转。典型场景是应用日志被 rm 删除但进程未关闭文件句柄，或 Docker 容器删除后 overlay2 层未清理。

4.2 踩坑：find 命令引发的 I/O 风暴

在根目录执行 find / -name "*.log" 会遍历所有挂载点，包括网络文件系统（NFS）和 /proc、/sys 虚拟文件系统，导致大量无效 I/O。正确做法是限定搜索路径并排除特殊目录：find /var/log -maxdepth 3 -name "*.log" -mtime +7。生产环境应优先使用 locate 命令（基于预建索引）或 mlocate 数据库，但需注意索引更新频率（默认每日凌晨）。

4.3 误判：top 命令的 CPU 百分比陷阱

top 显示的 %CPU 是多核累加值，单进程可能超过 100%（如 4 核机器上某进程显示 350% 表示占用 3.5 个核）。判断是否 CPU 瓶颈需结合 load average 与核心数对比，以及 %wa（I/O 等待）和 %st（虚拟化窃取时间）。云主机上 %st 持续高于 10% 说明宿主机超卖严重，需联系云厂商或迁移实例。

4.4 踩坑：kill -9 导致的资源泄漏

kill -9 发送 SIGKILL 信号强制终止进程，但无法触发应用的清理逻辑（如释放文件锁、关闭数据库连接、删除 PID 文件）。正确流程是先发送 SIGTERM（kill <PID>）等待 30 秒，再升级为 SIGKILL。对于 Java 应用，应使用 jstack 获取线程堆栈后再决定是否强杀，避免丢失故障现场。

4.5 误判：netstat 的 TIME_WAIT 恐慌

大量 TIME_WAIT 状态连接（如 10000+）常被误认为异常，实际上这是 TCP 主动关闭方的正常状态，持续 2MSL（约 60 秒）。真正需要关注的是 CLOSE_WAIT（被动关闭方未调用 close()，通常是应用 bug）和 SYN_RECV（可能遭受 SYN Flood 攻击）。调整 net.ipv4.tcp_tw_reuse=1 可复用 TIME_WAIT 连接，但需确保时间戳选项开启（net.ipv4.tcp_timestamps=1）。

Vi编辑器是所有Unix及Linux系统下标准的编辑器，

vi和vim都是Linux中的编辑器，不同的是，vim比较高级，可以视为vi的升级版本。vi使用于文本编辑，但是vim更适用于coding（写代码的）。

Vim重点是光标的移动，模式切换，删除，查找，替换，复制，粘贴，撤销命令的使用。

三种模式

  • 命令模式：在该模式下是不能对文件直接编辑，可以输入快捷键进行一些操作（删除行，复制行，移动光标，粘贴等等）【打开文件之后默认进入的模式】；
  • 编辑模式：在该模式下可以对文件的内容进行编辑；
  • 末行模式：可以在末行输入命令来对文件进行操作（搜索、替换、保存、退出、撤销、高亮等等）；

XSS跨站脚本攻击

2026-09-19 渗透

XSS漏洞原理

XSS属于客户端攻击，受害者最终是用户，但特别要注意的是网站管理人员也属于用户之一。这就意味着XSS可以进行“服务端”攻击，因为管理员要比普通用户的权限大得多，一般管理员都可以对网站进行文件管理，数据管理等操作，而攻击者一般也是靠管理员身份作为“跳板”进行实施攻击。

XSS的重点不在于跨站点，而在于脚本的执行。那么XSS的原理是：
恶意攻击者在web页面中会插入一些恶意的script代码。当用户浏览该页面的时候，那么嵌入到web页面中script代码会执行，因此会达到恶意攻击用户的目的。那么XSS攻击最主要有如下分类：反射型、存储型、及 DOM-based型。 反射性和DOM-baseed型可以归类为非持久性XSS攻击。存储型可以归类为持久性XSS攻击。

  1. XSS漏洞出现的原因

程序对输入和输出的控制不够严格,导致”精心构造“的脚本输入后,在输到前端时被浏览器当作有效代码解析执行从而产生危害。

  1. XSS的分类
  • 反射型XSS或不持久型XSS(中危)
  • 储存型XSS 或持久型 XSS（高危）
  • DOM XSS
  1. 测试方法
    1、工具扫描：APPscan、AWVS

2、手工测试：Burpsuite、firefox(hackbar)、XSSER XSSF

使用手工检测Web应用程序是否存在XSS漏洞时，最重要的是考虑那里有输入，输入的数据在什么地方输出。在进行手工检测XSS时，人毕竟不像软件那样不知疲惫，所以一定要选择有特殊意义的字符，这样可以快速测试是否存在XSS。

（1）在目标站点上找到输入点,比如查询接口,留言板等;

（2）输入一组”特殊字符+唯一识别字符”,点击提交后,查看返回的源码,是否有做对应的处理;

（3）通过搜索定位到唯一字符,结合唯一字符前后语法确认是否可以构造执行js的条件(构造闭合);提交构造的脚本代码,看是否可以成功执行,如果成功执行则说明存在XSS漏洞;
