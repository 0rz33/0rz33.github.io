Linux 系统运维核心命令实战指南

一、背景与适用场景

在生产环境中，SRE 团队面临的典型场景包括：应用突然无响应需要快速定位进程状态、磁盘空间告警需要紧急清理、网络连接异常需要排查路由和端口占用、系统负载飙升需要分析资源瓶颈。这些问题往往发生在业务高峰期，要求工程师在 5 分钟内完成初步诊断，15 分钟内给出根因分析。

传统的图形化监控工具存在延迟（通常 30-60 秒采集间隔），且在系统资源紧张时可能无法正常工作。此时必须依赖 SSH 登录后的命令行工具进行实时诊断。掌握核心命令的组合使用，能够在单台服务器或跨集群场景下快速收集证据链，避免盲目重启导致现场丢失。

本文聚焦于 Red Hat 系（RHEL/CentOS/Rocky）和 Debian 系（Ubuntu）的通用命令集，覆盖从系统信息采集、进程管理、网络诊断到日志分析的完整链路。所有命令均经过生产环境验证，适用于物理机、虚拟机和容器环境。

二、诊断步骤：只读命令优先原则

在任何变更操作前，必须先执行只读命令建立基线。首先运行 uptime && w 查看系统负载和当前登录用户，避免与其他运维人员操作冲突。接着执行 df -hT && lsblk 确认磁盘空间和分区挂载状态，特别关注根分区和 /var 分区使用率是否超过 85%。

进程诊断阶段运行 ps auxf --sort=-%mem | head -20 和 ps auxf --sort=-%cpu | head -20，分别按内存和 CPU 排序查看 TOP 20 进程。同时执行 pgrep -a java 或 pgrep -a python 定位目标应用进程 PID，再通过 lsof -p <PID> | wc -l 检查文件句柄数是否接近 ulimit -n 限制。

网络层面先运行 ss -tunlp 查看所有监听端口和对应进程，再用 ss -tn state established | wc -l 统计当前 TCP 连接数。如果怀疑网络不通，依次执行 ip addr show、ip route show、ping -c 3 <gateway> 验证本地网卡、路由表和网关连通性。最后通过 journalctl -xe --no-pager | tail -100 查看系统日志最新 100 条记录，寻找 OOM、segfault 等关键错误。

三、核心操作实战：进程管理

3.1 备份当前状态

在终止任何进程前，必须保存现场快照。执行以下命令将关键信息导出到时间戳目录：

对于 Java 应用，额外执行 jstack <PID> > "$SNAPSHOT_DIR/jstack.txt" 和 jmap -heap <PID> > "$SNAPSHOT_DIR/jmap.txt" 保存线程栈和堆信息。这些文件在事后分析和故障复盘时不可或缺。

3.2 安全终止进程

优先使用 SIGTERM 信号让进程优雅退出：kill -15 <PID>，等待 30 秒后检查进程是否仍存在 ps -p <PID>。如果进程未响应，再升级为 kill -9 <PID> 强制终止。对于批量终止场景，使用 pkill -15 -f "pattern" 按进程名模糊匹配，但务必先用 pgrep -a -f "pattern" 预览将被终止的进程列表。

对于僵尸进程（状态为 Z），直接 kill 无效，需要终止其父进程。通过 ps -eo pid,ppid,stat,comm | grep defunct 找到父进程 PID，评估是否可以安全重启父进程。如果父进程是 systemd 管理的服务，使用 systemctl restart <service> 而非直接 kill。

3.3 回滚与验证

进程重启后，立即执行 systemctl status <service> 或 ps aux | grep <process> 确认新进程已启动。检查监听端口是否恢复：ss -tunlp | grep <port>。查看应用日志最新 50 行：journalctl -u <service> -n 50 --no-pager 或 tail -50 /var/log/<app>.log，确认无启动错误。

如果服务启动失败，立即执行 journalctl -u <service> --since "5 minutes ago" --no-pager 查看详细错误。常见问题包括端口被占用（用 lsof -i :<port> 排查）、配置文件语法错误（用服务自带的 <app> -t 或 configtest 验证）、权限不足（检查 ls -lZ SELinux 上下文）。

四、核心操作实战：磁盘空间清理

4.1 定位大文件

当磁盘使用率超过 90% 时，首先运行 du -hx --max-depth=2 / | sort -hr | head -20 找出根分区下最大的 20 个目录（-x 参数避免跨文件系统）。针对 /var 分区，重点检查 /var/log、/var/tmp 和 /var/lib/docker。

使用 find /var/log -type f -size +100M -exec ls -lh {} \; 列出所有超过 100MB 的日志文件。对于应用日志，检查是否启用了 logrotate：ls -lh /etc/logrotate.d/ 和 cat /var/lib/logrotate/status。如果日志轮转失败，手动执行 logrotate -f /etc/logrotate.conf 强制轮转。

4.2 安全删除文件

删除前必须确认文件未被进程打开。运行 lsof +L1 查找所有已删除但仍被占用的文件（这些文件虽然 ls 看不到，但仍占用磁盘空间）。如果发现目标文件被占用，先重启对应进程释放句柄。

对于日志文件，使用 truncate -s 0 <file> 清空内容而非删除，避免进程因文件描述符失效而报错。删除临时文件时，使用 find /tmp -type f -atime +7 -delete 删除 7 天未访问的文件，-delete 参数比 -exec rm 更安全。删除后立即执行 df -h 验证空间是否释放，如果未释放则需要 lsof +L1 排查。

4.3 紧急扩容方案

如果清理后空间仍不足，检查是否有未挂载的 LVM 卷：lvdisplay 和 vgdisplay。如果 VG 有剩余空间，执行 lvextend -L +10G /dev/mapper/vg-lv && resize2fs /dev/mapper/vg-lv（ext4）或 xfs_growfs /mount/point（XFS）在线扩容。

对于容器环境，检查 Docker 镜像和容器占用：docker system df 和 docker image prune -a --filter "until=168h"（删除 7 天前的未使用镜像）。清理后执行 docker system prune -a --volumes --force 回收所有悬空资源，但务必确认无重要数据。

五、常见陷阱与误判

陷阱 1：误杀关键进程。使用 pkill 或 killall 时未充分验证匹配范围，例如 pkill java 会终止所有 Java 进程包括监控 Agent。正确做法是先 pgrep -a java 预览，再用完整命令行匹配：pkill -f "java.*my-app.jar"。生产环境禁止使用 kill -9 1 或 pkill -9 systemd，这会导致系统立即重启。

陷阱 2：磁盘空间假释放。删除大文件后 df 显示空间未释放，原因是进程仍持有文件句柄。必须通过 lsof +L1 找到进程并重启，或者使用 lsof | grep deleted 定位。另一个常见场景是删除了硬链接文件，但原始文件仍存在，需要 find / -inum <inode> 找到所有硬链接。

陷阱 3：网络诊断工具版本差异。CentOS 7 默认使用 netstat，CentOS 8+ 推荐 ss，两者输出格式不同。netstat -tunlp 等价于 ss -tunlp，但 ss 性能更高且支持过滤器：ss -tn state established '( dport = :80 or sport = :80 )'。使用 telnet 测试端口时，如果未安装需改用 nc -zv <host> <port> 或 timeout 3 bash -c "</dev/tcp/<host>/<port>"。

陷阱 4：日志查看时间范围错误。journalctl 默认显示所有历史日志，在日志量大时会卡死终端。必须加时间过滤：journalctl --since "10 minutes ago" 或 journalctl --since "2024-01-15 14:00" --until "2024-01-15 15:00"。使用 tail -f 实时查看日志时，如果日志轮转会导致跟踪中断，需改用 tail -F（大写 F）自动重新打开文件。

陷阱 5：权限与 SELinux 混淆。文件权限正确但仍无法访问，可能是 SELinux 阻止。运行 getenforce 检查 SELinux 状态，ausearch -m avc -ts recent 查看最近的拒绝日志。临时禁用 SELinux 用于测试：setenforce 0，但生产环境应通过 chcon 或 semanage 修正上下文，而非永久关闭 SELinux。

六、架构层面的可观测性建设

在单机命令行诊断之外，成熟的 SRE 体系需要建立分层监控。基础设施层部署 Node Exporter + Prometheus 采集 CPU、内存、磁盘、网络四大黄金指标，设置 P95 延迟和错误率 SLO。应用层通过 APM（如 Jaeger、SkyWalking）追踪分布式调用链，结合 Loki 或 ELK 实现日志聚合查询，避免逐台 SSH 登录。

灰度发布策略至关重要。使用 Kubernetes 的 Deployment 滚动更新时，设置 maxUnavailable: 1 和 minReadySeconds: 30，确保新 Pod 通过健康检查后再继续。对于虚拟机环境，通过 HAProxy/Nginx 的权重调整实现金丝雀发布：先将 5% 流量路由到新版本，观察 1 小时后逐步扩大到 50%、100%。每个阶段都需要验证关键业务指标（订单成功率、支付成功率）无异常。

自动化 Runbook 应将常见故障的诊断命令固化为脚本。例如创建 /usr/local/bin/diagnose-disk.sh 包含 df -hT、du 排序、lsof +L1 等命令组合，输出结构化 JSON 供监控系统解析。对于需要人工决策的操作（如 kill 进程），脚本应生成待执行命令清单并要求二次确认，记录所有操作到审计日志 /var/log/runbook-audit.log。

建立 Post-Mortem 文化，每次生产故障后 48 小时内完成复盘文档，包含时间线、根因分析、命令执行记录、改进措施。将高频故障的诊断命令整理为团队 Wiki，新人 Onboarding 时必须完成模拟演练，在测试环境中复现磁盘满、进程僵死、网络分区等场景并独立完成排查。

Ollama 本地大模型运行框架：从部署到生产级 MCP 集成实践

一、背景：为什么需要本地化大模型推理能力

在云原生架构演进过程中，SRE 团队面临三个核心痛点：数据主权合规（金融/医疗行业禁止敏感数据出境）、API 成本控制（GPT-4 API 月账单可达数万美元）、推理延迟优化（跨洋 API 调用 P99 延迟 >2s）。Ollama 作为轻量级本地推理框架，通过 Go 实现的高效模型加载器和统一 REST 接口，解决了传统方案的三大问题：PyTorch 环境依赖复杂、CUDA 版本冲突频发、多模型切换需重启服务。

典型场景包括：CI/CD 流水线中的代码审查（需要 7B 模型实时分析 diff）、Kubernetes 集群的智能告警降噪（需要本地 3B 模型做日志聚类）、离线环境的文档问答系统（需要完全断网运行 13B 模型）。相比 vLLM 的高并发优化或 Text-generation-webui 的 UI 友好性，Ollama 的核心优势在于零配置启动和跨平台一致性（macOS Metal、Linux CUDA、Windows DirectML 使用相同命令）。

从架构视角看，Ollama 本质是模型运行时的标准化抽象层，类似容器技术对应用运行时的封装。其设计哲学遵循 Unix 哲学：单一职责（仅负责模型推理）、管道友好（stdin/stdout 可直接对接脚本）、可组合性（通过 HTTP API 与任意语言栈集成）。这使得 SRE 可以像管理 Nginx 一样管理 LLM 服务，而无需深入 Transformer 架构细节。

五、常见陷阱与排错指南

5.1 模型加载失败：GGUF 格式不兼容

现象：ollama run 报错 incompatible quantization version
根因：Ollama 0.1.x 仅支持 GGUF v2，HuggingFace 部分模型使用 v3 格式
解决：使用 llama.cpp 工具转换格式

预防：优先使用 Ollama 官方模型库（ollama pull），自定义模型需验证 GGUF 版本（file model.gguf | grep GGUF）。

5.2 推理速度异常慢：CPU Fallback 未察觉

现象：7B 模型推理耗时 >10s/token（正常应 <0.1s）
诊断：检查 Metal/CUDA 是否正确启用

根因：常见于 Docker 部署时未传递 GPU 设备（缺少 --gpus all）或驱动版本不匹配
解决：重新创建容器并挂载 GPU；macOS 需确保 Xcode Command Line Tools 已安装（Metal 依赖）

5.3 内存溢出：模型量化配置错误

现象：ollama run 触发 OOM Killer，系统日志显示 Out of memory: Killed process
根因：未使用量化模型或量化位数过高（如 16-bit 模型在 8GB 内存机器运行）
解决：切换到 4-bit 量化版本

预防：生产环境强制使用量化模型，通过 Modelfile 锁定版本（FROM llama3.2:7b-q4_0）；配置 cgroup 内存限制（docker run -m 8g）触发优雅降级而非 OOM。

5.4 微调后模型退化：灾难性遗忘

现象：微调后模型在特定任务表现提升，但通用能力显著下降（如无法回答常识问题）
根因：训练数据分布单一 + 学习率过高导致覆盖预训练知识
解决：混合通用数据集训练

预防：使用 LoRA 而非全量微调（保留主干参数）；设置较小学习率（5e-5 而非 1e-4）；每 500 步在验证集评估通用能力（MMLU benchmark）。

5.5 API 调用超时：流式输出未启用

现象：长文本生成时客户端超时（如生成 2000 token 文档）
根因：使用同步 API 等待完整响应，超过 Nginx/LB 的 proxy_read_timeout
解决：启用 Server-Sent Events 流式输出

预防：客户端库默认启用流式（如 langchain-ollama 的 streaming=True）；监控 P99 延迟并设置合理超时（建议 120s）。

2026-09-19 Linux

Vi编辑器是所有Unix及Linux系统下标准的编辑器，

vi和vim都是Linux中的编辑器，不同的是，vim比较高级，可以视为vi的升级版本。vi使用于文本编辑，但是vim更适用于coding（写代码的）。

Vim重点是光标的移动，模式切换，删除，查找，替换，复制，粘贴，撤销命令的使用。

三种模式

  • 命令模式：在该模式下是不能对文件直接编辑，可以输入快捷键进行一些操作（删除行，复制行，移动光标，粘贴等等）【打开文件之后默认进入的模式】；
  • 编辑模式：在该模式下可以对文件的内容进行编辑；
  • 末行模式：可以在末行输入命令来对文件进行操作（搜索、替换、保存、退出、撤销、高亮等等）；

命令模式

光标移动

  • 行首 按键shift + 6 或 ^
  • 行尾 按键shift + 4 或 $
  • 首行 gg
  • 末行 G
  • 翻屏
    • 向上翻屏 按键ctrl + b （before） 或 PgUp
    • 向下翻屏 按键ctrl + f （after） 或 PgDn

复制操作

  • 所在行 yy
  • 粘贴：在想要粘贴的地方按下p键

剪切/删除

  • 剪切/删除光标所在行 dd
  • 剪切/删除光标所在的当前行之后的内容，但是删除之后下一行不上移 D

撤销/恢复

  • 撤销 u （undo）
  • 撤销5个改变 :undo 5
  • 你的撤销历史 :undolist
  • 重做最后的改动 按键ctrl + r:
  • 取消当前行中所有的改动 U:
  • 回到4分钟前 :earlier 4m
  • 前进55秒 :later 55s

替换

r: 替换光标处的字符，同样支持汉字。
R: 进入替换模式，按esc回到正常模式。

末行模式

进入方式：由命令模式进入，按下:或者/（表示查找）即可进入
退出方式：

  1. 按下按键esc
  2. 连按2次按键esc键
  3. 删除末行全部输入字符
  • 保存文件:w
  • 另存为:w 路径
  • 退出文件:q
  • 保存并且退出:wq
  • 表示强制退出，刚才做的修改操作不做保存:q!
  • :!外部命令
  • /关键词 搜索查找
  • 替换 -> %表示整个文件 g表示全局（global）
    • :s/搜索的关键词/新的内容 (替换光标所在行的第一处符合条件的内容)
    • :s/搜索的关键词/新的内容/g (替换光标所在行的全部符合条件的内容)
    • :%s/搜索的关键词/新的内容 (替换整个文档中每行第一个符合条件的内容)
    • :%s/搜索的关键词/新的内容/g (替换整个文档的符合条件的内容)
  • 显示行号（临时）

    • :set nonu
  • 文件多开:files

XSS跨站脚本攻击

2026-09-19 渗透

XSS漏洞原理

XSS属于客户端攻击，受害者最终是用户，但特别要注意的是网站管理人员也属于用户之一。这就意味着XSS可以进行“服务端”攻击，因为管理员要比普通用户的权限大得多，一般管理员都可以对网站进行文件管理，数据管理等操作，而攻击者一般也是靠管理员身份作为“跳板”进行实施攻击。

XSS的重点不在于跨站点，而在于脚本的执行。那么XSS的原理是：
恶意攻击者在web页面中会插入一些恶意的script代码。当用户浏览该页面的时候，那么嵌入到web页面中script代码会执行，因此会达到恶意攻击用户的目的。那么XSS攻击最主要有如下分类：反射型、存储型、及 DOM-based型。 反射性和DOM-baseed型可以归类为非持久性XSS攻击。存储型可以归类为持久性XSS攻击。

  1. XSS漏洞出现的原因

程序对输入和输出的控制不够严格,导致”精心构造“的脚本输入后,在输到前端时被浏览器当作有效代码解析执行从而产生危害。

  1. XSS的分类
  • 反射型XSS或不持久型XSS(中危)
  • 储存型XSS 或持久型 XSS（高危）
  • DOM XSS
  1. 测试方法
    1、工具扫描：APPscan、AWVS

2、手工测试：Burpsuite、firefox(hackbar)、XSSER XSSF

使用手工检测Web应用程序是否存在XSS漏洞时，最重要的是考虑那里有输入，输入的数据在什么地方输出。在进行手工检测XSS时，人毕竟不像软件那样不知疲惫，所以一定要选择有特殊意义的字符，这样可以快速测试是否存在XSS。

（1）在目标站点上找到输入点,比如查询接口,留言板等;

（2）输入一组”特殊字符+唯一识别字符”,点击提交后,查看返回的源码,是否有做对应的处理;

（3）通过搜索定位到唯一字符,结合唯一字符前后语法确认是否可以构造执行js的条件(构造闭合);提交构造的脚本代码,看是否可以成功执行,如果成功执行则说明存在XSS漏洞;
