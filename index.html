原始问题: [blog] VIM

Vim 编辑器技能点清单

场景占位: 编辑 , 修改 , 搜索
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 打开文件默认进命令模式,不能直接打字

  • 规则: 打开文件后先按 i 进编辑模式,编辑完按 Esc 回命令模式
  • 为什么: Vim 设计哲学是”阅读时间 > 编辑时间”,命令模式让光标移动和批量操作更高效
  • 踩坑: 新手打开文件直接敲字符,结果触发了删除/跳转等命令,文件被改得面目全非
  • 例外: vim -c startinsert <FILE> 可直接进编辑模式,但失去了 Vim 核心优势

2. dd 是剪切不是删除,误删内容还在剪贴板

  • 规则: dd 删除行后用 p 可粘贴回来,真删除用 "_dd (黑洞寄存器)
  • 为什么: Vim 所有删除操作都会进剪贴板,方便移动文本,但会覆盖之前复制的内容
  • 踩坑: 复制了 A 行,删除 B 行后想粘贴 A,结果粘贴出 B

3. 末行模式替换默认只替换每行第一个匹配

  • 规则: 全局替换必须用 :%s/<OLD>/<NEW>/g,缺 % 只改当前行,缺 g 只改每行首个
  • 为什么: Vim 继承 sed 语法,默认保守操作避免误改
  • 踩坑: :s/http/https/ 只改了当前行第一个 http,其他 999 行未动

4. 撤销后再编辑会丢失被撤销的分支

  • 规则: 撤销 (u) 后想恢复用 Ctrl+r,但撤销后编辑新内容会永久丢失被撤销的历史
  • 为什么: Vim 默认是线性 undo 树,不保留分支 (除非开启 undofile)
  • 踩坑: 撤销 5 步,改了一个字,想回到撤销前的状态,发现那 5 步永远找不回了
  • 例外: :earlier 4m 可基于时间回溯,但需要 undofile 持久化

5. 分屏后 :q 只关当前窗口不退出 Vim

  • 规则: 分屏环境用 :qa 退出所有窗口,:q 只关当前分屏
  • 为什么: Vim 把每个分屏视为独立窗口,:q 是 quit window 不是 quit vim
  • 踩坑: 开了 3 个分屏,按 :q 以为退出了,结果 Vim 还在后台占着文件锁

6. 搜索后高亮不会自动消失

  • 规则: / 搜索后用 :noh 取消高亮,或 :set nohlsearch 永久关闭
  • 为什么: Vim 认为高亮是有用的视觉提示,不会因为光标移动而清除
  • 踩坑: 搜索 error 后满屏黄色高亮,看其他内容时干扰视线

7. D 删除到行尾但不删除换行符

  • 规则: D 等价于 d$,删除光标到行尾内容但保留空行,dd 才删整行含换行符
  • 为什么: Vim 区分”行内容”和”行本身”,D 是行内操作,dd 是行操作
  • 踩坑: 用 D 想删除整行,结果留下一堆空行

8. :w <PATH> 另存为不会切换当前编辑文件

  • 规则: :w <NEW_FILE> 后当前缓冲区仍是原文件,要切换需 :e <NEW_FILE>
  • 为什么: Vim 的 :w 只是写入操作,不改变缓冲区绑定
  • 踩坑: 另存为 后继续编辑,以为在改备份,实际还在改原文件

9. 多文件编辑时 :bn/:bp 切换的是缓冲区不是标签页

  • 规则: vim <FILE1> <FILE2> 打开的是缓冲区列表,:bn/:bp 切换,:ls 查看列表
  • 为什么: Vim 的 buffer/window/tab 是三层概念,多文件默认进 buffer 不是 tab
  • 踩坑: 以为 :bn 会像浏览器切标签,结果当前窗口内容直接被替换

10. yy 复制整行包括换行符

  • 规则: yy 复制后 p 粘贴会插入新行,想粘贴到行内用 ^y$ 只复制内容不含换行
  • 为什么: Vim 的行操作 (yy/dd/p) 都是面向”完整行”的,包括不可见的换行符
  • 踩坑: 复制配置行想拼接成一行,p 后发现自动换行了

11. 分屏尺寸调整只对当前窗口生效

  • 规则: Ctrl+w +/- 调整当前窗口高度,其他窗口会自动压缩,Ctrl+w = 平均分配
  • 为什么: Vim 终端空间有限,调整一个窗口必然挤压其他窗口
  • 踩坑: 调大上方窗口后,下方窗口只剩 1 行看不清内容

12. :set nu 只在当前会话生效

  • 规则: 临时设置用 :set nu,永久生效需写入 ~/.vimrc
  • 为什么: Vim 启动时只读取配置文件,运行时的 :set 命令不会持久化
  • 踩坑: 每次打开文件都要手动 :set nu,以为 Vim 记不住设置

13. r 替换单字符后自动回命令模式,R 进入持续替换模式

  • 规则: 改一个字符用 r<NEW_CHAR>,改多个字符用 R 进替换模式后按 Esc 退出
  • 为什么: r 是原子操作,R 是模式切换,设计上避免误操作
  • 踩坑: 想连续替换多个字符,按 r 后只改了一个就停了

14. 分屏移动光标和移动分屏是不同的快捷键

  • 规则: Ctrl+w hjkl 移动光标到其他分屏,Ctrl+w HJKL (大写) 移动分屏本身
  • 为什么: Vim 区分”我去哪个窗口”和”把窗口移到哪”,大小写区分操作对象
  • 踩坑: 想把右侧分屏移到左侧,按 Ctrl+w h 结果只是光标跳过去了

15. :!<COMMAND> 执行外部命令会暂停 Vim

  • 规则: :!ls 执行后需按回车返回 Vim,想在 Vim 内看输出用 :r !<COMMAND>
  • 为什么: Vim 把控制权交给 shell,执行完等待用户确认再返回
  • 踩坑: 执行 :!<LONG_SCRIPT> 后黑屏,以为 Vim 卡死了,其实在等按键

  2. 全局替换必须 :%s/<OLD>/<NEW>/g,缺 % 或 g 都不是全局
  3. dd 是剪切不是删除,误删用 p 粘贴回来
  4. 撤销后编辑新内容会丢失被撤销的分支
  5. 分屏环境 :q 只关当前窗口,:qa 才退出 Vim

[expanded] [blog] vue2 大文件上传component(做成组件)

原始问题: [blog] vue2 大文件上传component(做成组件)

前端大文件分片上传组件技能点清单(Vue2)

场景占位: 上传至 , 文件标识用 , 分片索引用
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 先算文件 MD5 再切片,阻塞式串行处理多文件

  • 规则: 每个文件必须先完整计算 MD5(秒传判断依据)再切片,多文件用 for 循环串行处理而非 Promise.all
  • 为什么: 并行计算多个大文件 MD5 会撑爆浏览器内存(FileReader 同时读取多个 GB 文件),串行虽慢但稳定;MD5 必须先算完才能判断服务端是否已存在(秒传)
  • 踩坑: 用 files.map(async) 并行处理 5 个 2GB 文件直接卡死标签页
  • 例外: 文件小于 100MB 且数量少于 3 个时可并行

2. 分片上传进度用”已上传分片数/总分片数”,不用字节累加

  • 规则: 进度条绑定 upchunk / blockNum 而非 uploaded / file.size,每个分片成功回调后 upchunk++
  • 为什么: 字节累加需要监听每个分片的 xhr.upload.onprogress,在断点续传场景下已上传分片的进度无法复现,分片计数更可靠且实现简单
  • 踩坑: 断点续传后进度条从 0 开始重新跑,用户以为上传失败重新开始
  • 例外: 需要精确到字节的实时速率显示时必须用 onprogress

3. 文件唯一标识用”上传密钥+文件元信息”的 MD5,不直接用文件内容 MD5

  • 规则: uniqueFileName = md5(uploadkey + name + type + lastModifiedDate + size),与文件内容 MD5(fileMd5)分开
  • 为什么: 文件内容 MD5 用于秒传判断(服务端去重),uniqueFileName 用于前端断点续传状态恢复(localStorage key);同一文件被不同用户上传时 fileMd5 相同但 uniqueFileName 不同,避免状态混乱
  • 踩坑: 多用户上传同一文件时断点续传状态互相覆盖,A 用户续传了 B 用户的进度

4. 视频时长和 MD5 计算必须用 await 串行,不能依赖 Promise 链式

  • 规则: 用 await getFileMd5(file).then() 而非单独 getFileMd5(file).then(),确保 fileMd5 变量在后续代码执行前已赋值
  • 为什么: 示例代码中 let fileMd5 = "" 在 await 外层声明,如果不 await 直接进入下一步,fileMd5 仍是空字符串导致秒传判断失效
  • 踩坑: 文件明明已存在服务端,前端仍然重新上传所有分片,因为 fileMd5 为空字符串跳过了秒传检查

5. 文件类型校验用 MIME type 的扩展名部分,不用 file.name 后缀

  • 规则: const ext = '.' + file.type.split('/')[1] 然后匹配白名单,不用正则提取 file.name 的 .mp4
  • 为什么: file.name 可被用户随意修改(改后缀欺骗),file.type 是浏览器根据文件头判断的 MIME 类型更可靠
  • 踩坑: 用户把 .exe 改成 .mp4 绕过前端校验上传恶意文件
  • 例外: 需要支持无扩展名文件或浏览器无法识别的自定义格式时必须结合后端二次校验

6. 分片大小固定为构造函数参数,不根据文件大小动态调整

  • 规则: this.chunkSize 在组件初始化时设定(如 5MB),所有文件用同一分片大小,最后一片用 file.size % chunkSize
  • 为什么: 动态分片(大文件用大分片)会导致断点续传时分片边界对不上,服务端合并文件时校验失败;固定分片简化状态管理
  • 踩坑: 用户上传 10GB 文件时前端自动改用 50MB 分片,断点续传时服务端期望 5MB 分片导致合并失败

7. 上传列表用 MD5 去重而非文件名,允许同名不同内容文件

  • 规则: files.findIndex(item => item.md5 === fileMd5) 判断重复,不用 item.name === file.name
  • 为什么: 用户可能上传多个同名但内容不同的文件(如不同版本的 video.mp4),用文件名去重会误杀;MD5 相同才是真正的重复文件
  • 踩坑: 用户选择新版本 final.mp4 覆盖旧版本,前端因文件名相同拒绝添加

8. 每个文件对象必须包含独立的 cancel 令牌,不共用全局取消器

  • 规则: fileblock 结构中 cancel: null 字段存储该文件的 axios CancelToken,删除文件时调用 file.cancel()
  • 为什么: 多文件并行上传时,取消单个文件不应影响其他文件;共用全局 CancelToken 会导致取消一个文件时所有上传中断
  • 踩坑: 用户删除列表中第 2 个文件,结果所有文件上传都停止

9. 视频时长获取用 video 元素 loadedmetadata 事件,不用 canplaythrough

  • 规则: 创建临时 <video> 元素,监听 loadedmetadata 事件读取 duration,不等待 canplaythrough
  • 为什么: loadedmetadata 只需加载元数据(几百 KB)即可获取时长,canplaythrough 需要缓冲足够播放数据(可能几十 MB),大文件会等很久
  • 踩坑: 获取 5GB 视频时长等待 30 秒,因为浏览器在缓冲可播放数据

10. 文件切片用 Blob.slice 而非读取到内存再分割

  • 规则: file.slice(start, end) 返回原文件的视图(不复制数据),循环生成分片数组
  • 为什么: slice 是零拷贝操作,10GB 文件切 2000 片只生成 2000 个指针;如果用 FileReader 读取再 split 会瞬间占用 10GB 内存
  • 踩坑: 切片 8GB 文件时浏览器标签页崩溃,因为尝试把整个文件读入 ArrayBuffer

11. 上传状态用枚举字符串而非数字,方便调试和日志

  • 规则: status: '准备' | '上传中' | '暂停' | '完成' | '失败',不用 status: 0 | 1 | 2 | 3 | 4
  • 为什么: 控制台和日志直接显示 "上传中" 比 1 可读性强,排查问题时不需要查状态码映射表
  • 踩坑: 生产环境日志显示 status: 2,3 个月后没人记得 2 代表什么状态

12. 进度条颜色用函数返回而非固定值,根据状态动态变化

  • 规则: :color="customColor" 绑定方法,根据 status 返回不同颜色(上传中蓝色/完成绿色/失败红色)
  • 为什么: 用户需要快速识别哪些文件上传失败需要重试,颜色是最直观的视觉反馈
  • 例外: 严格遵循设计规范要求统一进度条颜色时不适用

13. 文件添加事件用 out() 方法触发父组件回调,不用 $emit

  • 规则: this.out('OnFileAddStart', files) 触发自定义事件,父组件通过配置对象传入回调函数
  • 为什么: 组件用 Vue.component 全局注册而非单文件组件,out() 是封装的事件总线方法,比 $emit 更灵活(支持非父子组件通信)
  • 踩坑: 用 this.$emit('OnFileAddStart') 发现父组件收不到事件,因为不是标准的父子组件关系

14. 多文件上传用 v-for 渲染独立进度条,不用单一进度条显示总进度

  • 规则: v-for="(file, index) in files" 为每个文件渲染独立的进度条和操作按钮
  • 为什么: 用户需要知道每个文件的具体进度和状态,单一总进度条无法体现哪个文件失败需要重试,也无法单独取消某个文件
  • 踩坑: 10 个文件上传时只显示总进度 60%,用户不知道是哪个文件卡住了

15. 文件 URL 和时长用 v-model 双向绑定输入框,支持手动修改

  • 规则: <el-input v-model="file.url"> 和 <el-input v-model="file.playtime"> 允许用户编辑
  • 为什么: 自动获取的视频时长可能不准确(编码问题),URL 可能需要手动调整路径或添加 CDN 前缀,给用户修正机会
  • 例外: 严格的数据一致性要求(如金融场景)禁止手动修改时不适用

🔥 5 秒必记 5 条

  1. 先算 MD5 再切片,多文件串行处理防内存爆
  2. 进度用分片计数(upchunk/blockNum)不用字节累加,断点续传才准确
  3. 文件内容 MD5(秒传)和唯一标识 MD5(断点续传)必须分开
  4. 分片大小固定不动态调整,否则断点续传边界对不上
  5. 每个文件独立 cancel 令牌,删除单个不影响其他

原始问题: [blog] vue2 对比 vue3

Vue2 vs Vue3 核心差异速查

场景占位: 组件用 、,数据用 、
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 生命周期钩子在 Vue3 需显式导入且改名

  • 规则: Vue3 中 beforeDestroy 改为 onBeforeUnmount,destroyed 改为 onUnmounted,且需从 vue 包导入
  • 为什么: Vue3 Composition API 设计哲学要求显式依赖,避免全局魔法变量;销毁语义改为”卸载”更准确
  • 踩坑: 直接在 setup() 里写 beforeDestroy() 不会报错但永远不执行,因为 Vue3 根本不认这个名字
  • 例外: Options API 模式下仍可用旧名称,但不推荐混用

2. setup 函数替代 beforeCreate 和 created

  • 规则: Vue3 的 setup() 在组件实例创建前执行,无需再写 beforeCreate 和 created
  • 为什么: setup() 执行时机就在这两个钩子之间,重复定义会造成逻辑分散和 this 指向混乱
  • 踩坑: 在 setup() 里访问 this 是 undefined,因为组件实例还未创建完成

3. 父子通信在 Vue3 需用 defineProps 和 defineEmits

  • 规则: Vue3 script setup 中用编译宏 defineProps 接收父组件数据,用 defineEmits 定义向父发送的事件
  • 为什么: 编译时宏可做静态分析和类型推导,比 Vue2 运行时 props 选项更高效且 TypeScript 友好
  • 踩坑: defineProps 不需要 import 就能用,手动导入反而报错,因为它是编译器注入的
  • 例外: Options API 模式仍用 props 和 $emit

4. ref 在 Vue3 有双重含义需区分场景

  • 规则: 模板中 ref="<refName>" 仍用于获取 DOM/组件实例,但 <script> 中 ref() 是响应式数据包装器
  • 为什么: Vue3 用 ref() 统一基本类型响应式,模板 ref 通过同名变量自动绑定,两者命名空间独立
  • 踩坑: 在 setup() 中访问 ref 包装的值必须 .value,但模板中自动解包不需要
  • 例外: reactive() 包装的对象不需要 .value

5. 渲染 Watcher 在 Vue3 改为 effect 副作用系统

  • 规则: Vue2 的 Watcher 类在 Vue3 被 ReactiveEffect 替代,初始化渲染不再显式创建 watcher 实例
  • 为什么: Vue3 响应式系统基于 Proxy 重写,effect 追踪更细粒度,性能提升 1.3-2 倍
  • 踩坑: Vue2 可以手动 new Watcher(),Vue3 必须通过 watchEffect 或 watch API,直接操作内部 effect 会破坏依赖追踪

6. data 选项在 Vue3 必须是函数不能是对象

  • 规则: Vue3 彻底移除 data 对象写法,只接受返回对象的函数
  • 为什么: 防止多个组件实例共享同一数据对象,虽然 Vue2 也推荐函数但仍允许对象(根实例除外)
  • 踩坑: 迁移时全局搜索 data: { 会漏掉根实例,因为 Vue2 根实例允许对象
  • 例外: Composition API 中直接用 ref/reactive 无此限制

7. watch 在 Vue3 需显式指定深度监听且返回值不同

  • 规则: Vue3 watch 默认浅监听,监听对象需配置 { deep: true },且返回停止函数而非 Vue2 的 unwatch
  • 为什么: 默认浅监听避免大对象性能陷阱,返回函数符合现代 JS 清理模式(类似 useEffect)
  • 踩坑: Vue2 this.$watch 返回的 unwatch 函数在 Vue3 中仍叫 unwatch 但实现完全不同,不可混用

8. 组件注册在 Vue3 局部注册优先于全局

  • 规则: Vue3 推荐在 <script setup> 中直接 import 组件即自动注册,全局 app.component() 仅用于基础组件
  • 为什么: Tree-shaking 友好,未使用的组件不会打包;Vue2 的 components 选项仍可用但不推荐
  • 踩坑: <script setup> 中 import 的组件名必须是 PascalCase,kebab-case 在模板中自动转换但变量名不行

9. $mount 在 Vue3 改为 app.mount 且不可链式调用

  • 规则: Vue3 用 createApp(<Component>).mount(<selector>) 替代 new Vue().$mount(),mount 返回根组件实例而非 app
  • 为什么: 应用实例(app)和组件实例分离,一个页面可创建多个独立 Vue 应用互不干扰
  • 踩坑: app.mount() 只能调用一次,Vue2 可以先 new Vue() 后多次 $mount 到不同元素

10. methods 在 Composition API 中退化为普通函数

  • 规则: <script setup> 中直接定义函数即可在模板使用,无需 methods 选项包裹
  • 为什么: methods 本质是为了绑定 this,Composition API 无 this 概念,普通函数更直观
  • 踩坑: 普通函数没有自动 this 绑定,需要的状态必须显式从 setup 作用域捕获

11. 动态组件 component 标签的 is 属性需用 v-bind

  • 规则: Vue3 中 <component is="<ComponentName>"> 必须写成 :is="<ComponentName>",字符串形式仅用于原生 HTML 标签
  • 为什么: 区分组件对象和 HTML 标签字符串,避免安全风险(Vue2 会尝试解析字符串为组件)
  • 踩坑: 迁移时 is="ComponentA" 会被渲染为自定义元素而非组件,必须改为 :is="ComponentA"

12. 响应式丢失在解构 props 时必须用 toRefs

  • 规则: const { <propName> } = defineProps() 会丢失响应式,需 const { <propName> } = toRefs(props)
  • 为什么: 解构是值拷贝,切断了 Proxy 代理链;toRefs 为每个属性创建独立 ref 保持响应
  • 踩坑: 模板中直接用 props 正常,但解构后传给 computed 或 watch 会失效

🔥 5 秒必记 5 条

  1. setup 替代 beforeCreate/created,内部无 this
  2. 生命周期钩子改名且需导入: onBeforeUnmount/onUnmounted
  3. ref() 的值在 script 中要 .value,模板中自动解包
  4. defineProps/defineEmits 是编译宏,不需要 import
  5. 解构 props 必须 toRefs 否则丢失响应式

Wireshark 网络抓包分析技能清单

场景占位: 用 表示本机地址, 表示远端地址, 表示服务端口
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 过滤器写在捕获前还是捕获后决定性能和完整性

  • 规则: 捕获过滤器(Capture Filter)丢弃不符合条件的包且不可恢复,显示过滤器(Display Filter)仅隐藏但数据仍在
  • 为什么: 捕获过滤器用 BPF 语法在内核层丢包,显示过滤器用 Wireshark 语法在应用层过滤,90% 的人混用导致抓不到关键包或文件过大
  • 踩坑: 生产环境用捕获过滤器 host <REMOTE_IP> 后发现漏抓了中间代理的包,因为真实通信经过
  • 例外: 排查未知问题时先全量捕获再用显示过滤器,避免过早丢弃线索

2. ip.addr 是双向匹配会抓到意料外的流量

  • 规则: ip.addr == <TARGET_IP> 匹配源地址或目的地址,需要单向过滤必须用 ip.src 或 ip.dst
  • 为什么: 大部分协议是双向的,用 ip.addr 会同时抓到请求和响应,导致包数量翻倍且难以区分主动连接方
  • 踩坑: 想抓客户端主动发起的连接用了 ip.addr == <CLIENT_IP>,结果把服务端响应也抓进来,误判为客户端发包频率异常
  • 例外: 分析完整会话时 ip.addr 更方便,配合 tcp.stream eq <N> 追踪单条流

3. 包编号(No.)在过滤后不连续是正常的

  • 规则: Wireshark 的 No. 列是捕获时的全局序号,应用显示过滤器后编号会跳跃但不会重新编号
  • 为什么: 编号对应 pcap 文件中的物理位置,重新编号会导致无法与原始文件对应,这是设计而非 bug
  • 踩坑: 过滤后看到 No. 从 1234 跳到 5678,以为中间的包丢失了,实际是被过滤条件隐藏
  • 例外: 导出过滤后的包为新文件时,新文件会重新从 1 开始编号

4. TCP 三次握手的 Seq 不是从 0 开始是安全机制

  • 规则: SYN 包的 Seq 是随机初始序列号(ISN),Wireshark 默认显示相对序列号(从 0 开始),需要看真实值要关闭 “Relative sequence numbers”
  • 为什么: 随机 ISN 防止序列号预测攻击,相对序列号是 Wireshark 为了方便人类阅读做的转换
  • 踩坑: 对比两端抓包时发现 Seq 不一致,因为一端开了相对序列号显示,另一端显示的是绝对值
  • 例外: 分析 TCP 劫持或序列号预测攻击时必须看绝对序列号

5. Len=0 的包不是空包而是控制包

  • 规则: TCP 包的 Len 字段表示有效载荷长度,SYN/ACK/FIN 等控制包 Len=0 但仍然消耗序列号
  • 为什么: TCP 头部的控制标志位(SYN/FIN)本身占用 1 个序列号,但不计入 Len,这是协议设计
  • 踩坑: 看到大量 Len=0 的包以为网络空转,实际是正常的 keepalive 或连接管理
  • 例外: ACK 纯确认包既不消耗序列号也 Len=0,但会推进确认号(Ack)

6. 时间戳格式影响问题定位效率

  • 规则: 默认时间戳是相对第一个包的偏移量,排查超时问题改用 “Time of Day” 格式对照日志
  • 为什么: 相对时间适合看包间隔,绝对时间适合与应用日志、数据库慢查询日志对齐
  • 踩坑: 应用日志显示 14:32:15 超时,但 Wireshark 显示 +125.334s 无法快速定位到对应的包
  • 例外: 分析重传间隔、RTT 时相对时间更直观

7. 同一个 TCP 流的包可能分散在文件各处

  • 规则: 使用 “Follow TCP Stream” 或过滤 tcp.stream eq <N> 聚合同一条连接的所有包
  • 为什么: Wireshark 按时间顺序捕获所有网卡流量,多条并发连接的包会交错出现
  • 踩坑: 手动用 ip.addr and tcp.port 过滤后仍看到多条连接混在一起,因为客户端用了不同的源端口
  • 例外: UDP 没有流的概念,需要用 ip.addr and udp.port 手动组合过滤

8. 抓包文件过大时先用 editcap 切割再分析

  • 规则: 超过 500MB 的 pcap 文件会导致 Wireshark 卡顿,用 editcap -c <包数> <输入> <输出前缀> 按包数切割
  • 为什么: Wireshark 会将整个文件加载到内存建索引,大文件会耗尽内存或导致 GUI 无响应
  • 踩坑: 直接打开 5GB 的抓包文件,Wireshark 卡死 10 分钟后系统 OOM
  • 例外: 只需要统计信息时用 capinfos 或 tshark -q -z 无需加载完整文件

9. 显示过滤器支持逻辑运算但优先级反直觉

  • 规则: and 优先级高于 or,复杂条件必须加括号,如 (ip.src == <IP_A> or ip.src == <IP_B>) and tcp.port == <PORT>
  • 为什么: 不加括号时 ip.src == <IP_A> or ip.src == <IP_B> and tcp.port == <PORT> 会被解析为 ip.src == <IP_A> or (ip.src == <IP_B> and tcp.port == <PORT>)
  • 踩坑: 想过滤两个 IP 的 80 端口流量,写成 ip.addr == <IP_A> or ip.addr == <IP_B> and tcp.port == 80,结果把 的所有端口都抓进来了
  • 例外: 单一条件无需考虑优先级

10. 重传包(Retransmission)出现不一定是网络问题

  • 规则: TCP 重传可能由接收窗口满、应用层处理慢导致,需结合 “TCP Window Full” 和 “TCP ZeroWindow” 分析
  • 为什么: 网络丢包和接收端来不及处理都会导致重传,但根因不同,前者查网络设备,后者查应用性能
  • 踩坑: 看到大量 Retransmission 就升级带宽,实际是数据库查询慢导致应用接收缓冲区满
  • 例外: 无线网络环境下少量重传(< 1%)是正常的

11. Expert Info 的 Warning 不等于故障

  • 规则: Expert Info 中的 “TCP Previous segment not captured” 可能是抓包点不完整,不一定是真丢包
  • 为什么: 在客户端抓包时看不到服务端发出但未到达的包,在中间设备抓包时可能因端口镜像丢包
  • 踩坑: 在负载均衡器后的服务器抓包,看到大量 “Previous segment not captured”,实际是流量分散到其他服务器了
  • 例外: 在发送端抓包仍出现此告警,大概率是真丢包

12. 解密 HTTPS 流量需要提前配置不能事后补救

  • 规则: 必须在抓包前设置环境变量 SSLKEYLOGFILE=<路径> 让应用记录会话密钥,或导入服务器私钥(仅 RSA 且无前向保密)
  • 为什么: TLS 1.3 和使用 ECDHE 的 TLS 1.2 有完美前向保密,抓包后无法通过私钥解密
  • 踩坑: 抓完包才想起来要解密 HTTPS,即使有服务器私钥也解不开,因为用了 ECDHE 密钥交换
  • 例外: 中间人代理(如 mitmproxy)可以实时解密,但会改变证书链

13. 协议解析错误时手动指定 “Decode As”

  • 规则: 非标准端口的协议(如 8080 跑 HTTP)需要右键包选择 “Decode As” 指定协议类型
  • 为什么: Wireshark 默认靠端口号判断协议,自定义端口会被识别为 TCP 原始数据
  • 踩坑: 抓到 的流量显示为乱码,实际是 HTTP 协议但 Wireshark 不认识
  • 例外: 部分协议有特征字节(如 HTTP 的 “GET”),Wireshark 会启发式识别

14. 导出对象功能只对完整流有效

  • 规则: “File -> Export Objects -> HTTP” 导出文件时,如果 TCP 流不完整(缺 SYN 或 FIN)会导出失败
  • 为什么: Wireshark 需要完整的 HTTP 请求响应对才能重组文件,中途开始抓包会缺少流的起始部分
  • 踩坑: 抓包过程中才打开 Wireshark,想导出传输的文件时发现列表为空
  • 例外: 使用 “Follow TCP Stream” 手动复制 payload 可以绕过此限制

15. 统计功能比逐包分析更快定位瓶颈

  • 规则: 用 “Statistics -> Conversations” 找出流量最大的连接,”Statistics -> IO Graph” 看流量趋势
  • 为什么: 逐包分析 10 万个包需要数小时,统计视图 10 秒内就能发现异常连接或流量突刺
  • 踩坑: 网络慢但不知道哪个服务占带宽,逐个过滤 IP 查了半天,用 Conversations 按 Bytes 排序 5 秒找到
  • 例外: 分析协议细节(如异常标志位)时仍需逐包检查

原始问题: [blog] XSS跨站脚本攻击

XSS 跨站脚本攻击技能点清单

场景占位: 攻击者向 注入 , 用户 浏览触发, 管理员 成为提权跳板
阅读顺序: 扫标题 → 记住反直觉 3-5 条即可动手

1. 把管理员当首要攻击目标而非普通用户

  • 规则: XSS 攻击优先瞄准管理员账户, 利用其高权限作为服务端攻击跳板
  • 为什么: 管理员浏览留言板/日志页面时触发 XSS 可直接获得文件管理/数据库操作权限, 本质是把客户端漏洞转化为服务端突破口
  • 踩坑: 只盯着普通用户 Cookie 窃取, 忽略管理后台才是真正价值目标
  • 例外: 目标是批量钓鱼或流量劫持时才优先覆盖普通用户

2. 输出点比输入点更关键

  • 规则: 手工测试时先追踪数据在哪里输出(HTML/JS/属性), 再考虑输入绕过
  • 为什么: 同一个输入可能在多处输出且上下文不同, 输出在 <script> 标签内和在 href 属性里的闭合方式完全不同
  • 踩坑: 只在输入框测试 <script>alert(1)</script>, 不看源码里实际插入位置导致误判无漏洞

3. 存储型 XSS 危害等级远超反射型

  • 规则: 存储型(持久化到数据库)评为高危, 反射型(URL 参数触发)评为中危
  • 为什么: 存储型一次注入永久生效, 所有访问该页面的用户自动中招, 反射型需要诱骗点击特制链接
  • 踩坑: 看到需要构造 URL 的 XSS 就认为是低危, 忽略留言板/评论区的存储型才是批量收割

4. 用唯一标识符定位而非直接测 Payload

  • 规则: 输入 特殊字符+<UNIQUE_ID_12345>, 在响应源码搜索 <UNIQUE_ID_12345> 查看过滤情况
  • 为什么: 直接测 <script>alert(1)</script> 被 WAF 拦截时无法区分是输入过滤还是输出编码, 唯一 ID 能精确定位数据流
  • 踩坑: 测试 Payload 被拦截就放弃, 不知道用无害字符串先探路

5. DOM 型 XSS 不经过服务端

  • 规则: DOM 型漏洞的输入输出全在浏览器 JS 执行, 抓包看不到 Payload
  • 为什么: document.location.hash 或 window.name 等客户端数据源直接被 innerHTML 使用, 服务端日志和 WAF 完全失效
  • 踩坑: 用 Burp 改包测试 DOM 型 XSS, 实际需要在浏览器 Console 直接操作 DOM API

6. 特殊字符组合比完整 Payload 更有效

  • 规则: 手工测试先输入 '";><() 观察哪些被过滤, 再针对性构造闭合
  • 为什么: 完整 <script> 标签容易被正则拦截, 但单引号闭合属性值或尖括号逃逸标签的组合常被遗漏
  • 踩坑: 只测试教科书式的 <script>alert(1)</script>, 遇到标签过滤就认为安全

7. 输出在 JS 上下文时用反斜杠逃逸

  • 规则: 数据输出在 <script>var x='<USER_INPUT>'</script> 时, 测试 \';alert(1)//
  • 为什么: HTML 实体编码在 JS 字符串内不生效, 需要用反斜杠逃逸单引号再注入代码
  • 踩坑: 在 JS 上下文里测试 &lt;script&gt; 这种 HTML 编码, 浏览器不会解析

8. 属性上下文优先测试事件处理器

  • 规则: 输出在 <input value="<USER_INPUT>"> 时, 测试 " onmouseover="alert(1)
  • 为什么: 闭合双引号后可直接添加事件属性, 比构造完整标签更隐蔽且绕过部分过滤
  • 踩坑: 在属性里还想插入 <script> 标签, 不知道事件处理器才是正确姿势

9. 反射型 XSS 需要社会工程学配合

  • 规则: 发现反射型漏洞后必须构造短链接或伪装成正常功能诱导点击
  • 为什么: URL 里明文 <script> 会被邮件客户端/IM 工具拦截, 需要编码或跳转混淆
  • 踩坑: 直接把带 Payload 的长 URL 发给目标, 对方一眼识破或被安全软件拦截

10. 工具扫描只能发现 30% 的 XSS

  • 规则: AWVS/AppScan 跑完后必须手工复测输入输出点
  • 为什么: 扫描器无法理解业务逻辑(如多步骤表单/异步加载), 且对 DOM 型和复杂编码场景误报率高
  • 踩坑: 扫描器报告显示无漏洞就认为安全, 实际留言板/富文本编辑器等高危点需人工深挖

11. HttpOnly 标志只防 Cookie 窃取不防 XSS

  • 规则: 看到 Cookie 设置 HttpOnly 不代表 XSS 无危害
  • 为什么: XSS 还能读取页面内容(CSRF Token)/发起请求(修改密码)/键盘记录, Cookie 窃取只是利用方式之一
  • 踩坑: 防御方只加 HttpOnly 就以为高枕无忧, 攻击方放弃 XSS 利用

12. CSP 策略需检查 unsafe-inline 和 unsafe-eval

  • 规则: 遇到 Content-Security-Policy 响应头, 重点看是否包含 'unsafe-inline' 或 'unsafe-eval'
  • 为什么: 这两个指令允许内联脚本和 eval 执行, 使 CSP 形同虚设
  • 踩坑: 看到有 CSP 就认为 XSS 无法利用, 不检查具体策略配置

13. 富文本编辑器是存储型 XSS 重灾区

  • 规则: 测试文章发布/评论系统时, 优先在富文本编辑器源码模式插入 Payload
  • 为什么: 富文本需要保留部分 HTML 标签(如 <img> <a>), 过滤逻辑复杂容易遗漏 onerror 等事件属性
  • 踩坑: 只测试纯文本输入框, 忽略编辑器的 HTML 模式和 Markdown 解析

14. 测试时用 alert(document.domain) 而非 alert(1)

  • 规则: PoC 里用 alert(document.domain) 证明代码执行
  • 为什么: 证明脚本在目标域执行而非本地测试环境, 且能绕过某些基于关键词的 WAF
  • 踩坑: 用 alert(1) 被 WAF 特征匹配拦截, 或无法向甲方证明是在其域名下执行

15. JSON 接口的 XSS 需要 Content-Type 配合

  • 规则: API 返回 {"data":"<USER_INPUT>"} 时, 检查 Content-Type 是否为 text/html
  • 为什么: application/json 类型浏览器不会解析 HTML, 只有错误配置成 text/html 才能触发 XSS
  • 踩坑: 在 JSON 响应里发现未过滤的 <script> 就报漏洞, 实际浏览器不执行

🔥 5 秒必记 5 条

  1. 管理员是 XSS 的真正目标, 客户端漏洞可转化为服务端突破
  2. 存储型(高危)一次注入全员中招, 反射型(中危)需诱导点击
  3. 先用唯一 ID 定位输出点和过滤情况, 再构造闭合 Payload
  4. DOM 型 XSS 不过服务端, 抓包测不出来要看 JS 代码
  5. 工具扫描只能发现 30%, 富文本编辑器/管理后台必须手工深测

VIM

Vi编辑器是所有Unix及Linux系统下标准的编辑器，

vi和vim都是Linux中的编辑器，不同的是，vim比较高级，可以视为vi的升级版本。vi使用于文本编辑，但是vim更适用于coding（写代码的）。

Vim重点是光标的移动，模式切换，删除，查找，替换，复制，粘贴，撤销命令的使用。

三种模式

  • 命令模式：在该模式下是不能对文件直接编辑，可以输入快捷键进行一些操作（删除行，复制行，移动光标，粘贴等等）【打开文件之后默认进入的模式】；
  • 编辑模式：在该模式下可以对文件的内容进行编辑；
  • 末行模式：可以在末行输入命令来对文件进行操作（搜索、替换、保存、退出、撤销、高亮等等）；

命令模式

光标移动

  • 行首 按键shift + 6 或 ^
  • 行尾 按键shift + 4 或 $
  • 首行 gg
  • 末行 G
  • 翻屏
    • 向上翻屏 按键ctrl + b （before） 或 PgUp
    • 向下翻屏 按键ctrl + f （after） 或 PgDn

复制操作

  • 所在行 yy
  • 粘贴：在想要粘贴的地方按下p键

剪切/删除

  • 剪切/删除光标所在行 dd
  • 剪切/删除光标所在的当前行之后的内容，但是删除之后下一行不上移 D

撤销/恢复

  • 撤销 u （undo）
  • 撤销5个改变 :undo 5
  • 你的撤销历史 :undolist
  • 重做最后的改动 按键ctrl + r:
  • 取消当前行中所有的改动 U:
  • 回到4分钟前 :earlier 4m
  • 前进55秒 :later 55s

替换

r: 替换光标处的字符，同样支持汉字。
R: 进入替换模式，按esc回到正常模式。

末行模式

进入方式：由命令模式进入，按下:或者/（表示查找）即可进入
退出方式：

  1. 按下按键esc
  2. 连按2次按键esc键
  3. 删除末行全部输入字符
  • 保存文件:w
  • 另存为:w 路径
  • 退出文件:q
  • 保存并且退出:wq
  • 表示强制退出，刚才做的修改操作不做保存:q!
  • :!外部命令
  • /关键词 搜索查找
  • 替换 -> %表示整个文件 g表示全局（global）
    • :s/搜索的关键词/新的内容 (替换光标所在行的第一处符合条件的内容)
    • :s/搜索的关键词/新的内容/g (替换光标所在行的全部符合条件的内容)
    • :%s/搜索的关键词/新的内容 (替换整个文档中每行第一个符合条件的内容)
    • :%s/搜索的关键词/新的内容/g (替换整个文档的符合条件的内容)
  • 显示行号（临时）
    • :set nu[number]
    • :set nonu
  • 文件多开:files
    • 果需要指定切换文件的名称，则可以输入:open 已经打开的文件名
    • “:bn”切换到下一个文件（back next）
    • “:bp”切换到上一个文件（back prev）
分屏功能

  • 分屏

    • 水平方向分屏打开新文件 横向切分 :sp文件名 :split文件名
    • 垂直方向分屏打开新文件 竖向切分 :vsp文件名 :vsplit文件名
    • 上下分割当前打开的文件 按键Ctrl+w s
    • 左右分割当前打开的文件 按键Ctrl+w v

  • 关闭分屏

    • 关闭当前窗口按键Ctrl+w c
    • 关闭当前窗口，如果只剩最后一个了，则退出Vim按键Ctrl+w q

  • 移动光标

    • 把光标移到右边的屏 按键Ctrl+w l
    • 把光标移到左边的屏中 按键Ctrl+w h
    • 把光标移到上边的屏中 按键Ctrl+w k
    • 把光标移到下边的屏中 按键Ctrl+w j
    • 把光标移到下一个的屏中 按键Ctrl+w w

  • 移动分屏

    • 向右移动 按键Ctrl+w L
    • 向左移动 按键Ctrl+w H
    • 向上移动 按键Ctrl+w K
    • 向下移动 按键Ctrl+w J

  • 屏幕尺寸

    • 让所有的屏都有一样的高度 按键Ctrl+w =
    • 增加高度 按键Ctrl+w +
    • 减少高度 按键Ctrl+w -
